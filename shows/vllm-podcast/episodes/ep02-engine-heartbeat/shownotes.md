# 第 2 期：引擎的一次心跳——谁进这一拍，谁饿在门口

> 调度器不认请求数，只认 token 数。这一拍谁上桌、谁被踢、谁被饿，全在一圈四步里定了。

## 本期简介

同时开 100 个 chat 会话打爆 vLLM，调度器根本不在乎你有几个请求——它每一拍只问一个问题：GPU 能吃下多少个 token。一个 2000 token 的系统提示词可能一口吃掉整拍预算，剩下 99 个请求全饿在后面。这不是 bug，是设计——但这个设计的代价，被严重低估了。

本期把引擎的一次「心跳」完整拆开：调度、前向、采样、更新，四步一步不少。

## 本期要点

- **一拍是什么**：引擎服务活着就停不下来的忙循环，一次完整心跳 = schedule 调度 → execute_model 前向 → sample_tokens 采样 → update_from_output 更新；同步路径则直接调 step 一拍一拍推
- **数 token，不数请求**：批大小上限是 max_num_batched_tokens（默认 8192），不是请求数——GPU 一拍的容量单位就是 token，电梯载重按重量不按人数
- **两阶段调度**：先给所有在途 RUNNING 请求各补一颗 token 的配额，再用剩余预算接纳 WAITING 新请求；长 prompt 一口吃掉预算，短请求全饿在外面——「长请求暴政」
- **KV 块分配失败**：触发抢占循环，按 LIFO 踢 RUNNING 队尾（算得最少、重算成本最低），被抢请求回队头插队补偿；分配失败的请求单独进 skipped_waiting 双队列，不许堵队头
- **execute_model 的叛逆**：发起前向却不等结果，全部产出先存进 ExecuteModelState「盒子」——拆开才能重叠，调度器不等 logits 就能规划下一拍；入口断言强制两阶段严格配对
- **update_from_output 收尾**：推进已算 token 数、check_stop 四道关卡判停（EOS / 停止词 / 停止编号 / max_tokens 硬上限）、完成请求释放 KV 块、未完成的下轮重新竞争预算——闭环，心跳
- **代价与判据**：Marcus Chen 实测连续批处理 p50 从 340ms 降到 190ms，但 p99 从 1.2s 飙到 9.8s、p99.9 从 2.1s 跳到 27s——尾延迟 SLA 敏感就配 chunked prefill + 优先级队列；离线批处理裸的 token 调度最省显存
- **本期也没搞清楚的事**：8192 这个默认值到底谁定的、抢占之后重算的浪费有多大——显存、批形状、GPU 型号一堆权衡搅在一起，我们没见到系统的数据，欢迎评论区懂行的说说

## 引用的社区声音

- **Interview Baba（2026 年 vLLM 面试高频题）**：调度器不认请求数只认 token 数，为什么？考的是「为什么这样设计」，不是 API 怎么用
- **Marcus Chen（dev.to 生产 trace，2026-05）**：一次 60ms 的 prefill 让 23 个在飞的 decode 流全排队，GPU 利用率 81%，瓶颈不在算力在调度
- **vLLM 官方论坛用户（2025-12）**：token budget 下调度行为不一致，某些请求被无限期推迟，哪怕预算看起来还够
- **Sarathi-Serve（OSDI 2024 论文）**：prefill 与 decode 共享前向时 token 间隔可推高 28 倍；chunked prefill 带来 2.6x（Mistral-7B）到 6.9x（Falcon-180B）的吞吐提升
- **牛客面经（2026-06）**：prefill 与 decode 各自的计算、访存瓶颈，PD 分离优化策略——大模型推理岗必问题，能完整答出来的人不到三分之一

## 下期预告

显存不是被模型吃光的，是被「笔记」吃光的。下一期从操作系统偷一个主意：把 KV cache 像虚拟内存一样切成固定大小的页，换入换出，甚至跨请求共享相同的前缀。
