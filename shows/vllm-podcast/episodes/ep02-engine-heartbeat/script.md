# 引擎的一次心跳：谁进这一拍，谁饿在门口

[S1] 大家好，我是老张。欢迎回来。上期我们把 EngineCore 锁进了独立进程，一整期都在它门口转悠，没进去。留了个悬念：它里面那个忙循环，一拍四步，到底怎么排兵布阵？这期就进去。还是老两位：阿凯，这本书的作者，AI infra 一线老兵；阿哲，传统后端程序员，替你们读者来的。[/S1]

[S2] 大家好。这期拆的是引擎里最核心的一拍——从调度到更新，一个完整的心跳。我尽量讲慢点，你们俩随时掐我。[/S2]

[S3] 我是阿哲。我的活儿还是替读者拍桌子——讲快了、讲飘了，我直接打断。[/S3]

[S1] 好，进正题。我昨天干了件事：同时开了 100 个 chat 会话，一起往 vLLM 发请求。结果你猜怎么着——那调度器，根本不在乎你有几个请求。[/S1]

[S2] 对。它只问一个问题：这一拍，GPU 能吞下多少个 token。[/S2]

[S3] 等等，「调度器」是谁？是不是就是排桌子的那个？[/S3]

[S2] 对，调度器就是负责排这一拍桌子的组件，谁上桌它说了算。[/S2]

[S3] 等等，100 个请求它不看数量？那要是一个请求带着 2000 token 的系统提示词，一口吃掉整拍预算呢？[/S3]

[S1] 剩下 99 个全饿在后面？[/S1]

[S2] 不一定，这得看那 99 个各自多长。但这不是 bug，是设计。这句话我要说全——这个设计的代价，被严重低估了。[/S2]

[S3] 被低估？我听着这就是长请求欺负短请求啊。[/S3]

[S2] 你这话，跟 2026 年的面试市场撞一块儿了。面试备考网站把今年 vLLM 的高频题整理了一遍，关于调度器最典型的一道是这么问的——{{voice:voice-005}}调度器不认请求数、只认 token 数，为什么？连续批处理和静态批处理在 GPU 那一步到底差在哪？——它还有一句总结：考的就是「为什么这样设计」，不是 API 怎么用。原话大概这个意思。[/S2]

[S1] 你这话我得记下来。所以听众里的传统程序员注意：这期听完，这道面试题你能答上一半。上期收尾那句话我还记着——每一步都可能决定一个请求是被喂饱还是被饿死。这期，我盯着这个。[/S1]

[S3] 我也盯着。那就别站着了，把这一拍拆开看吧。[/S3]

[S2] 好。从 schedule 开始，到 update from output<break 300ms>收尾——一整拍四步，一步都不少。[/S2]

[S1] 先给全景。这一拍，在引擎里是怎么跑起来的？[/S1]

[S2] 服务模式下，引擎进程跑一个忙循环：取一个输入、算一拍、送一批输出，不停。这一拍就是四步，四步在代码里各有名字——schedule，调度；<break 300ms>execute model，前向；<break 300ms>sample tokens，采样；<break 300ms>update from output，更新。[/S2]

[S3] 先别管哪四步——「一拍」对应到物理上，是什么？[/S3]

[S2] 一次完整的前向计算。——嗯，这么说太抽象。说人话：这一批请求的 token，从输入到输出，GPU 整体走一趟。拍，就是这一趟。[/S2]

[S3] 嗯，这个「拍」我有感觉了。那为什么叫「心跳」？这名字起得有点吓人。[/S3]

[S2] 心脏每跳一次，泵一次血；引擎每跳一拍，把一批 token 往前推一步。而且这个心跳不敢停——它是忙循环，服务活着，它就一直转。停一拍，GPU 空转，排队的全堵着。[/S2]

[S1] 四步的顺序是死的？[/S1]

[S2] 死的。每步的活还不一样：调度定人，前向算分，采样选词，更新记账。[/S2]

[S1] 「定人、算分、选词、记账」——你这话我得记下来，结尾我要考的。[/S1]

[S3] 那离线批量那种用法呢？没有忙循环，这一拍谁来推？[/S3]

[S2] 同步路径直接调 step，一拍一拍自己推；多机并行或者异步调度的时候，走 step with batch queue。内核是同一个，只是驱动方式不同。[/S2]

[S1] 那我先挑个刺：采样干嘛要从前向里拆出来？算完顺手选个词不行吗？[/S1]

[S2] 行，但会慢。拆出来的理由是：调度器不等模型输出，就能提前规划下一拍。schedule 不依赖 logits——谁在跑、每人几颗 token 的预算，不算前向也算得出来。[/S2]

[S3] 等等，你是说前向还在 GPU 上跑着，调度器就已经在盘算下一桌的座位了？不等结果，就敢排下一批？[/S3]

[S2] 对。这是拆采样的全部理由：等结果再调度，就是每步都串行；不等，调度和计算就叠起来了。[/S2]

[S3] 我能不能这么理解——采样从前向里拆出来，不是工程洁癖，是为了让调度不等前向的结果，两边叠着跑。对吧？[/S3]

[S2] 对，就是这个意思。你抓得很准。[/S2]

[S1] 好，那钻进第一步，调度。它到底按什么决定谁上桌？[/S1]

[S2] 简单来说一句话：数 token，不数请求。这一拍所有请求的 token 加起来，不许超过一个预算——代码里叫 max num batched tokens<break 300ms>，默认值是 8192 颗 token。[/S2]

[S3] 为什么是 token？数请求不是更直观吗？[/S3]

[S2] 因为 GPU 一拍的容量单位就是 token——前向张量的形状按 token 数定，跟请求数没关系。就好比电梯载重按重量不按人数：一个 200 公斤的大箱子上去，剩下三百公斤，只够再挤两个瘦子。[/S2]

[S3] 我能不能这么理解：电梯报警看的是总重，不是人头数——所以长 prompt 就是那个大箱子。[/S3]

[S2] 对，就是这个大箱子。而且这里没有先集中喂新请求、再逐个续写的两个阶段之分——所有请求统一按 token 数一视同仁。[/S2]

[S3] 停一下。你刚才说的「集中喂、再续写」，是不是就是书里说的 prefill 和 decode？这两个词我还不太懂，能不能展开说说？[/S3]

[S2] 好，这俩词得钉死。——展开来说。prefill，是第一次把整段提示词喂进去、算出第一颗 token 的那一趟；decode，是之后每拍续写一颗新 token 的那一趟。vLLM 的调度器不分这两个相——它眼里只有 token 数。[/S2]

[S1] 你说的这套，就是连续批处理吧？它跟老式的静态批处理，在 GPU 那一步到底差在哪？[/S1]

[S2] 静态批处理：一批凑齐了才跑，跑完一批再凑下一批——中间 GPU 有喘气。连续批处理：每拍往正在跑的批里塞新请求、送走完成的——批是活的，GPU 不用等谁。[/S2]

[S3] 那除了 token 预算，就没有「最多几个请求」的限制吗？总得画个上界吧。[/S3]

[S2] 也有——请求数上限是另一回事——但真正决定这一拍多满的，是 token 预算，不是请求数。上限画的是天花板，预算画的是这一拍能走多远。[/S2]

[S1] 那 8192 是个什么量级？给我个感觉。[/S1]

[S2] 大概这么算：一个 2000 token 的系统提示词，第一次喂进去就要吃掉四分之一预算。剩下四分之三，才轮得到别人。[/S2]

[S1] 那剩下的预算怎么分？总有个先来后到吧。[/S1]

[S2] 分两阶段。阶段一：所有在途的 RUNNING 请求，先各追加一颗 token 的配额——正在算的不能断粮。阶段二：剩多少预算，再从 WAITING 队列里接纳新请求。[/S2]

[S3] 等等，为什么每人只补一颗？多补几颗不是更爽快？[/S3]

[S2] 因为 decode 一次前向，每个请求刚好吐一颗新 token——补多了也用不上。补一颗，正好让每个在途请求都往前走一步，谁都不掉队。[/S2]

[S1] 让我来捋一下：先伺候在途的，再放新来的。正干着活的不能停；还在排队的，只能等下一趟电梯。这顺序我懂。[/S1]

[S2] 对。所以新请求的 prompt 越长，能挤进这一批的新请求越少。长请求一口吃掉预算，短请求全饿在外面——这就是「长请求暴政」。这词你们先记下，一会儿拿它开刀。[/S2]

[S3] 记下了。那要是这一拍请求不多，8192 用不满呢？[/S3]

[S2] 上限不是定额。请求少，这一拍就小，GPU 轻载；请求多，就挤破头抢这 8192。预算只负责画天花板，不负责硬凑。[/S2]

[S1] 还有一个事：这一批里新旧请求混着，GPU 那边怎么知道谁是谁？[/S1]

[S2] 调度器产出一个单子，代码里叫 Scheduler Output<break 300ms>：首次调度的请求发全量——prompt、采样参数、块号全给；已经跑过的只发增量——新 token、新块号。全量只发一次，之后全是 diff。[/S2]

[S3] 这不跟 git 一样吗？第一次全量 clone，之后只推变更。[/S3]

[S2] 对，就是为了省通信。一拍八千多颗 token，每拍全量重发，谁也扛不住。[/S2]

[S1] 那 worker 那边收到全量，是不是得自己存着？[/S1]

[S2] 对，首次调度把全量缓存下来，之后的每一拍只收 diff——不用重复解析，通信量压到最小。[/S2]

[S3] 哎，「worker」是谁？你俩都说得跟常识似的。[/S3]

[S2] worker 就是引擎进程里真正拿 GPU 干活的执行单元。这一期你记住这名字就行，它的身世后面专门拆。[/S2]

[S3] 哎，我问一个。要是新请求带着结构化输出，比如要求模型吐 JSON，调度的时候要不要管？[/S3]

[S2] 要管，但绝不在调度循环里管。语法编译可能要上百毫秒——把 JSON 的规矩编成一台状态机——这种慢活要是堵在热路径里，整拍都得等它。怎么绕开，我们后面专门有一期要拆，先记个账。[/S2]

[S3] 好，记账上。不过我还有个问题：连续批处理这么好，为什么不是所有框架都默认开？[/S3]

[S2] 因为它不是免费的——代价是什么，这就到开刀时间了。「长请求暴政」，真有那么严重吗？[/S2]

[S1] 严重不严重，你说了不算。拿数据。[/S1]

[S2] 有实测。技术博主 Marcus Chen，今年五月在自己线上系统抓的 trace，他是这么说的——{{voice:voice-027}}开了连续批处理，p50 从 340 毫秒降到 190 毫秒。p99 从 1.2 秒飙到 9.8 秒，p99.9 从 2.1 秒跳到 27 秒。他给的就是这些数字。[/S2]

[S3] 停一下，p50、p99 是什么？这俩数我还不太懂。[/S3]

[S2] 好，这个得先钉。把所有请求的延迟从快到慢排个队——p50 是站正中间那个，一半人比他快，一半人比他慢；p99 是一百个里排第九十九个。尾部的体验，看的就是它。[/S2]

[S1] 那这组数字的意思就是：中间那位变快了，队尾那位被坑惨了——p99 翻了八倍，p99.9 翻了十三倍。这还叫优化？[/S1]

[S2] 对。他给的根因是：一次 60 毫秒的 prefill，让 23 个在飞的 decode 流全排队——GPU 利用率才 81%，瓶颈不在算力，在调度。[/S2]

[S3] 个案？还是普遍现象？[/S3]

[S2] 普遍。vLLM 官方论坛上，去年就有用户反映——{{voice:voice-003}}token budget 下调度行为不一致，某些请求被无限期推迟，哪怕预算看起来还够。大意是这样。这条是匿名用户的反馈，具体场景我们没核实到，但方向跟 Marcus 的 trace 一致。[/S2]

[S1] 无限期推迟？排队排到天荒地老？这跟 Marcus 的 trace，是同一个病？[/S1]

[S2] 同一个方向：预算总数是对的，但默认配置下，请求之间的公平没人替你保证——所以等会儿判据你会看到：实时服务得自己加优先级队列。[/S2]

[S3] 那我先认罪：连续批处理保了吞吐，丢了尾延迟。这是设计缺陷吧？[/S3]

[S2] 我先不护短：长 prefill 堵 decode，是真问题，Marcus 的 trace 就是证据。但反方也得说——GPU 的算力，不关心 token 来自哪个请求。[/S2]

[S1] 这话什么意思？[/S1]

[S2] 在 GPU 眼里，decode 的 token 和 prefill 的 token 一样沉——FLOPS 只看总量，按 token 调度，才能把 GPU 喂饱。[/S2]

[S3] 喂饱了又怎样？光说理论，拿证据。[/S3]

[S2] 反证在这。Sarathi-Serve 在 OSDI 2024 发了篇论文，里面是这么写的——{{voice:voice-028}}prefill 和 decode 共用一个前向时，两颗 token 的间隔能推高 28 倍；把长 prefill 切成小块、插在 decode 批中间跑，也就是 chunked prefill。——吞吐提升 2.6 倍到 6.9 倍，尾延迟回归正常。这两组数字，都是论文里的实测。[/S2]

[S3] 等等，28 倍是论文里的实测数据？OSDI 又是什么来头？[/S3]

[S2] 系统领域的顶级会议，同行评审过的数据。28 倍是共享前向最坏情况的推高，chunked prefill 就是解药。[/S2]

[S1] 先问个数据：2.6 倍到 6.9 倍，跨度怎么这么大？[/S1]

[S2] 你注意这两个数：Mistral-7B 提升 2.6 倍，Falcon-180B 提升 6.9 倍——模型越大，长 prefill 堵得越狠，切块的收益越猛。这组数据本身就在说：问题随规模放大。[/S2]

[S3] 那 chunked prefill 具体怎么解？切成小块，切完插哪儿？[/S3]

[S2] 把超长的 prefill 切成小块，插在 decode 之间跑——一个大请求不再一口气堵死整批，大家轮流吃，谁也不让谁等穿。[/S2]

[S1] 那 vLLM 自己有没有这味药？[/S1]

[S2] 有。问题不是设计错了，是默认配置没开——chunked prefill 这些都有，但默认值不会替你选。[/S2]

[S1] 那我到底开不开？给我判据，别和稀泥。[/S1]

[S2] 判据是你的尾延迟 SLA。卖实时 API、p99 必须压在两秒内——token 调度必须配 chunked prefill，再加优先级队列；做离线批处理、尾延迟无所谓——裸的 token 调度最省显存。[/S2]

[S3] 明白了：调度器没错，错的是「不调参就上生产」。[/S3]

[S1] 这句话可以裱起来。[/S1]

[S3] 那我问个现实的：prefill 和 decode 的瓶颈，面试要是问到，该答到什么程度？我听说这已经是必考题了。[/S3]

[S2] 是。牛客上一位做后端的前辈，说他公司面大模型推理岗，面试完把这些必问题记了下来——{{voice:voice-004}}prefill 与 decode 各自的计算、访存瓶颈是什么？PD 分离后的优化策略？chunked prefill 与一次性 prefill 的对比优势？这是我们公司面大模型推理岗位的必问题，能完整答出来的人不到三分之一。这是他的原话。[/S2]

[S1] 不到三分之一。行，那这期讲的这些，够不够答？[/S1]

[S2] 够答「是什么」。至于各自的瓶颈细节，那是后面讲 GPU 执行那期的事，今天先不展开。[/S2]

[S1] 行，回到心跳。调度定完人，真能把人送上桌吗？还是说，名单定了，人也未必上得去？[/S1]

[S2] 不一定。上桌要显存——每个请求要分 KV cache 块，就是上期说的那本「笔记」。笔记的块分不出来，麻烦就来了。[/S2]

[S3] 块是什么？[/S3]

[S2] 笔记按块住进显存，一块是一个固定大小的分配单位。调度时给请求分块，分不出来——代码里 allocate slots<break 300ms>返回空——这一步就触发抢占循环。[/S2]

[S1] 抢占？抢谁的？[/S1]

[S2] 按 LIFO，后进先出——把 RUNNING 队尾请求的 KV 块释放掉，请求状态标成「被抢占」，回流到 waiting 队头，下一拍重新排队。[/S2]

[S3] 等一下，你刚才那句我没跟上——为什么踢队尾？新来的不是算得最少吗？踢最老的不是更合理？[/S3]

[S2] 反直觉就在这：踢队尾，正因为它是最后进来的、算得最少——重算成本最低。踢个算了一半的，前功尽弃，浪费更大。[/S2]

[S3] 那被抢的请求重新上桌，之前算的还留着吗？笔记还在不在？总不能白算一遍吧。[/S3]

[S2] 不在了。KV 块都释放了，重新上桌就得重写笔记、重新算——这就是抢占的代价，拿时间换显存。所以挑算得最少的踢，这笔账才划算。[/S2]

[S1] 拿时间换显存——这个我懂了。那被踢的请求冤不冤？排半天队，全白算了。[/S1]

[S2] 冤，但有补偿：FCFS，就是先到先得的排队模式；抢占请求靠 prepend request<break 300ms>直接回队头——下一拍优先重新上桌，相当于插队补偿。[/S2]

[S3] 那要是开了优先级队列呢？「回队头」还成立吗？[/S3]

[S2] 会退化：优先级队列是个堆，prepend 变成按优先级和到达时间重新入堆——补偿照给，但排位按优先级来。[/S2]

[S1] 还有一个细节：抢占之后，本拍还放新请求吗？还是先缓一缓？[/S1]

[S2] 不放。显存已经挤爆过一次，再塞新的只会更糟。这一拍先消化，下一拍再开门。[/S2]

[S1] 我记下来：抢占是急刹车，不是常规操作——踩了一脚，这一拍就别再踩油门。[/S1]

[S3] 那我再挑个刺：要是 WAITING 队头那个请求，它自己分不到块呢？它堵在队头，后面是不是全等？[/S3]

[S2] 你问到点子上了。分配失败的请求，不许堵队头——单独扔进一个 skipped waiting 队列，下一拍再试。就好比银行柜台：材料不齐，先请到旁边补齐，后面的人继续办，不许一个人卡死一个窗口。[/S2]

[S1] 双队列——防的就是队头阻塞。[/S1]

[S2] 对。一个分不到块的请求，不许饿死整队。skipped 的请求也靠 prepend request<break 300ms>重新排回队列，公平不受影响。[/S2]

[S1] 好，调度这关过了。第二步，前向——execute model<break 300ms>。这名字听着就是「执行模型」。[/S1]

[S2] 对，但它是全书最反直觉的方法之一：发起前向，却不等结果。代码里写作 execute 下划线 model<break 300ms>——e-x-e-c-u-t-e，下划线，m-o-d-e-l。[/S2]

[S3] 啊？发起不等结果？那 logits 呢，白算了？[/S3]

[S2] 没白算。所有输出——logits、hidden states——缓存在一个盒子里，代码里叫 Execute Model State，十个字段。execute model<break 300ms>只负责把活发下去，结果先存在盒子里，函数直接返回。[/S2]

[S3] 盒子里到底装了些啥？就 logits 一样？[/S3]

[S2] logits 只是其中一个。还有 hidden states、采样要用的中间状态、插槽映射……十个字段，装着前向的全部产出，等第二步来取。[/S2]

[S3] 等等，这个「先把活发下去、结果存盒子里」——跟我们前面说的采样拆出来，是不是一个思路？都是发出去先不等？[/S3]

[S2] 你联系得很对——就是同一个思路：能不等就不等，让 CPU 和 GPU 各干各的。盒子是给这个「不等」配的保险柜。[/S2]

[S1] 那活是怎么发下去的？「发下去」具体是啥？[/S1]

[S2] 靠的就是 collective RPC<break 300ms>——向所有 GPU worker 广播一条指令，开会喊一嗓子，全组同时开工。[/S2]

[S3] 开会喊一嗓子——行，那谁负责把结果取回来？[/S3]

[S2] 到第三步了——sample tokens<break 300ms>。它解包盒子，取出 logits 做采样，挑一颗 token 出门。[/S2]

[S3] 这拆两步，怎么保证不乱套？万一上一拍的没取干净，新的一盒又来了呢？[/S3]

[S2] 有硬规矩：execute model<break 300ms>入口先断言盒子必须是空的——上一拍没取走，下一拍不许放。强制两阶段严格配对。[/S2]

[S3] 断言，就是「不满足就报错」——这个我们写代码的熟。[/S3]

[S2] 对，而且它是保险丝：万一两阶段真没配对好，直接炸给你看——宁可停下来，不许拿错数据继续跑。[/S2]

[S1] 那采样是怎么挑的？直接选概率最大的那个词？[/S1]

[S2] 不完全是。是从模型算出的概率分布里抽一颗——温度、随机种子这些采样参数都在这里起作用。怎么个抽法，后面采样那期单独拆，今天知道「挑一颗出门」就够了。[/S2]

[S3] 可我还是没懂：前向算完顺手采样，不也顺路吗？拆开图什么？[/S3]

[S2] 又回到开头那句了——拆开才能重叠。execute model<break 300ms>把活发出去，调度器马上开始规划下一拍；它不需要 logits 就能决定谁进下一批。等结果，每一步就都串行了。[/S2]

[S1] 三班倒：GPU 算着，CPU 盘着下一桌。[/S1]

[S2] 对，谁都不等谁。[/S2]

[S3] 那我较个真：采样采出来的新 token，放哪？GPU 不会自己记住吧。[/S3]

[S2] 写回。sample tokens<break 300ms>收尾有个记账动作——把新 token 追加进每个请求的输出记录，同时更新持久批次的 CPU 镜像。[/S2]

[S3] 等等，CPU 镜像？GPU 上跑着的东西，CPU 那边还要留一本账？[/S3]

[S2] 要。持久批次——请求批不每拍重建，请求来了装进空位、完事留个洞、下次填洞复用。CPU 镜像就是这本账，下一拍准备输入时，把新 token 从账本搬回 GPU。[/S2]

[S1] 那 GPU 上的记录和 CPU 的账本，岂不是两份？同步不麻烦？[/S1]

[S2] 有个细节：它们其实是同一份数据——输出记录和批次镜像共用同一个 list 对象，这就是闭环的物理载体，连同步都省了。[/S2]

[S3] 新 token 变成下一拍的输入——闭环了？[/S3]

[S2] 闭环了。采样出来的 token，下一拍就是输入，模型就是这么一句句「续写」下去的。[/S2]

[S1] 让我来捋一下这个闭环：采出来的 token 先进账本，下一拍从账本搬回 GPU 当输入——这一拍喂下一拍，环环相扣。那我顺势问一句：execute model 具体在 GPU 上怎么执行的？你光说「把活发下去」——发下去之后呢？[/S1]

[S2] 那是后面专门一期要拆的：GPU worker 上的真实执行，CUDA graph、kernel 分派，水很深，先记个账。今天只到「发下去、收回来」这一层。[/S2]

[S1] 行。四步就差最后一步：update from output<break 300ms>。这名字我一听就懂——拿输出回头更新状态，把这一拍的结果收进账里。[/S1]

[S2] 对，反馈环的另一半。调度器吸收 sample tokens<break 300ms>的输出，给每个请求更新「已算 token 数」——已经算到第几颗，账记得清清楚楚。[/S2]

[S3] 然后呢？就记个数？那这账不就白记了——记完总得拿它干点正事吧？[/S3]

[S2] 没白记。账记完，第一件事就是 check_stop<break 300ms>——也就是停止判定。四道关卡，分两拨：一拨是模型自己的事，它觉得说完了，就吐个结束符，EOS；另一拨是你定的规矩——你指定的停止词、你指定的停止编号，还有 max tokens 这个硬上限，到数就停。[/S2]

[S3] 等等，先说说 EOS——我猜这是模型自己觉得话说完了，主动吐的一个句号？它不想说了，总得有个信号吧。[/S3]

[S2] 对，模型觉得自己说完了，就吐一个特殊的结束 token。但模型觉得说完，跟你要求的停止，是两回事——stop strings 就是你手动补的保险丝。[/S2]

[S1] 那 max tokens 呢？我猜是硬上限——防话痨的，不管说不说完，到数就停。[/S1]

[S2] 对，防的就是话痨。四道关卡各管一摊：EOS 管模型自觉，停止词和停止编号管你指定，max tokens 管硬上限。[/S2]

[S3] 停一下，那「指定的停止词」是什么？我刚才听你念到就觉得怪——模型自己不会停吗，怎么还要我们手动给个停止词？[/S3]

[S2] 光靠模型吐的结束符不够——很多场景你要按自己给的字符串停。这个「停止词」其实就是你指定的字符串，命中即停。停止编号也是一个道理——你给的不是字符串，是 token 的编号，命中一样停。[/S2]

[S1] 那判定停了的请求，怎么处理？笔记还占着显存，总不能一直挂着吧。[/S1]

[S2] 标记 FINISHED——完成态有好几种，但判起来很快：请求状态是个整型枚举，是不是结束，一个「大于」的比较就判完。然后调 KV 缓存管理，把它占的笔记全释放，显存还回来。[/S2]

[S1] 完成态有好几种？我以为就正常收尾一种——除了正常说完，还有啥情况？[/S1]

[S2] 有被掐断的、被中止的……不细数了。你只要知道：完成是一整个状态家族，状态机管着，一个整型比较就判完。[/S2]

[S3] 等等，我复述一遍——完成不是一个状态，是一整个家族；状态存成整型，判完成就是一次大小比较；判完的，笔记全还回显存。对吧？[/S3]

[S1] 笔记释放，这是显存呼吸的出口——不释放，显存只进不出，早晚挤爆。那没停的呢？[/S1]

[S2] 没停的从 running 队列摘下来，下一轮 schedule 的阶段一重新加入——按优先级或先到先得，再竞争一次预算。[/S2]

[S1] 我来总结一下：调度定人，前向算分，采样选词，写回记账——四步一圈，正好闭合。那这一圈转完，下一圈还从调度开始？[/S1]

[S2] 对——没完成的请求，下一轮阶段一重新加入；这一拍算完的 token，就是下一拍排队的依据。这一圈的产物叫 Engine Core Outputs<break 300ms>，经 IPC 回传前端，投进每个请求的信箱——上期说的「喂饱还是饿死」，全在这一圈里定了。一圈套一圈，这就是心跳。[/S2]

[S3] 那我问个憋了一整期的：8192 这个默认值，到底谁定的？为什么不是 16384？还有抢占之后重算的浪费，有没有人量化过？[/S3]

[S2] 这个我们也没搞清楚——显存、批形状、GPU 型号，一堆权衡搅在一起，真推起来很复杂。抢占之后重算的浪费到底有多大，我们也没见到系统的数。评论区有懂的说说。[/S2]

[S1] 好，记账上。那问最后一个问题：这一拍谁上桌、谁被踢、谁被饿——折腾一圈，最终都落在哪件事上？[/S1]

[S2] 显存。KV cache 块够不够——够，就有得算；不够，就抢人、就排队。这一期把一拍拆到了骨头，但这一拍能转起来，前提是那块显存管得明白。[/S2]

[S1] 下一期，就是你上期说「往后排」的那件事？我这一期可一直记着这笔账。[/S1]

[S2] 这期真的排到了。下一期我们从操作系统偷一个主意：把 KV cache 像虚拟内存一样切成固定大小的页，换入换出，甚至跨请求共享相同的前缀。[/S2]

[S3] 那我先把话放这儿：到时候你可能会说，显存不是被模型吃光的，是被笔记吃光的。[/S3]

[S2] 被谁吃光的，下一期见分晓。[/S2]

[S1] 好，下期见。[/S1]
