# 128000 个分数，只放一颗出门：采样管线的最后一站

[S1] 大家好，我是老张，欢迎回来。这季大结局——一个请求从进门到一颗 token 出门，今天走最后一站：采样。老两位：阿凯，这本书的作者，AI infra 一线老兵；阿哲，传统后端程序员，替你们读者来的。[/S1]

[S2] 大家好。先给阿哲开奖——上期他押的：九道关卡里肯定有温度、惩罚这些旋钮。押对了，这期一道一道过。[/S2]

[S3] 我是阿哲。先交代立场：我写过后端，抽奖、限流这些带随机的活干过，我就想知道，大模型挑下一个词，跟我印象里的「按权重随机」差在哪。谁讲快了，我随时喊停。[/S3]

[S1] 行，摆钩子。GPU 每拍算出 128000 个 logits——十二万八千个词的打分。可你要让模型输出 JSON，这十二万八千个候选里，十二万七千九百九十九个都是非法的。[/S1]

[S3] 等会儿——十二万七千九百九十九个非法？就剩一个能选？那直接挑分最高的，不等着翻车吗？[/S3]

[S2] 十有八九翻车。所以这期的主角不是「怎么挑」，是「怎么不让它挑错」：你写的 JSON 格式说明，被实时编译成一张 GPU 位掩码，采样之前，就把非法 token 的打分打成负无穷。[/S2]

[S1] 这张掩码得多大？十二万八千个判决，每拍都来一遍，不贵吗？[/S1]

[S2] 压成 4000 个 32 位整数——小到每拍跑一次都感觉不到。但这条线背后藏着个 bug：有个东西明明被关了，可能还在偷偷跑。扣子系上，讲到那儿再解。[/S2]

[S1] 九道关卡、一张掩码、一个偷偷跑的东西。从哪儿开始？[/S1]

[S2] 从采样被叫醒那一刻开始。前向算完，logits 躺在卡上，谁去取、什么时候取？这里有个反直觉的设计：发起前向，却不等结果。[/S2]

[S3] 不等结果？前向发了不算完？——等等，这话我耳熟，是不是第一期那个「不等着」的句式又来了？[/S3]

[S2] 耳熟就对了。前向是 execute model<break 300ms>发出去的，当场返回空；logits 装进代码里那个盒子——Execute Model State，十个字段。等引擎腾出手，sample tokens<break 300ms>把盒子打开，采样。[/S2]

[S1] 发了前向不等结果，那中间这段空档，引擎干嘛？[/S1]

[S2] 干别的——把下一拍的活先排好。两阶段解耦就为这个：GPU 算的时候，CPU 别闲着。前向是跑腿，采样是拍板；跑腿的先出门，拍板的等货到再上场。[/S2]

[S3] 我能不能这么理解——跟点外卖一样：下单后后厨开火，你不用站窗口等，菜好了叫号，中间该干嘛干嘛？[/S3]

[S2] 对，说到点子上了。而且这单有规矩：盒子单槽。前向开跑前必须空——上一拍的货没取走，不许装新的；取货前必须非空——没货不许取。两头拿断言锁着，严格配对。[/S2]

[S1] 让我来捋一下：execute model<break 300ms>发车装盒，sample tokens<break 300ms>开盒采样，中间引擎排下一拍；盒子单槽，断言配对。对吧？[/S1]

[S2] 一字不差。[/S2]

[S3] 那我趁这儿讨笔旧账——上期说前向走「录像」重播，可你挂了笔账：prefill 常吃不到录像的红利。今天能还吗？[/S3]

[S2] 能，三句话还清。录像重播要形状固定、地址固定。decode 清一色一颗 token，形状稳，吃得到红利；prefill 的 prompt 有长有短，形状回回不一样，对不上录像，只能回退逐算子老实跑——上期的 NONE 档。[/S2]

[S3] 懂了——变长的 prefill 对不上固定的录像，只能干瞪眼。这笔我销账了。[/S3]

[S1] 旧账清完，进主线。盒子打开之后，九道关卡登场？[/S1]

[S2] 登场。九步采样管线，别被数字吓着——归拢起来四类活：留底、改分、分路、交卷。整批请求的旋钮，温度、惩罚这些，打包成一批张量喂进来。一步步走。[/S2]

[S1] 留底是？采样前还要拍照？[/S1]

[S2] 对，第一步，抢救原始概率。logits 一会儿要被各道工序改得面目全非，可有的请求要 logprobs——「你凭什么选这个词」的证据。所以趁没改，先整个存下来。[/S2]

[S3] 先拍照留底，后面改的是副本，交证据拿原图——是这么个意思吧？[/S3]

[S2] 对。然后进改分区。五道处理器工序，先讲四道——这四道都能换掉冠军：偏置、禁词、长度门槛、三种惩罚。[/S2]

[S1] 偏置我熟，给某些词加分减分。[/S1]

[S2] 对，代码里叫 logit bias，直接改分——被加分的词，可能从亚军变冠军。[/S2]

[S2] 禁词更有意思。bad words<break 300ms>这道，只在「快补全成禁词」时才动手：脏话的词根刚冒头，马上掐掉；普通句子里无辜的字母，不受牵连。[/S2]

[S1] 这不就是把某些词弄没吗？跟偏置有啥区别？[/S1]

[S2] 区别在「怎么弄」：偏置是改分，冠军可能换人；禁词是精确封杀，一票否决。第三道更狠——min tokens：没凑够指定长度，禁止发结束符。让它最少写两百字，它写到五十字想停？结束符的打分打成负无穷，憋着也得写完。[/S2]

[S3] 哈哈，字面意义上的「憋作文」——小时候老师盯着凑字数，现在轮到模型了。这个我记下来了。[/S3]

[S2] 第四道：三种惩罚，照 OpenAI 的定义算。频率惩罚，按出现次数累计扣；存在惩罚，出现过就扣一刀；重复惩罚，专打连续重复。这几道的存在本身就是题眼：光选最大，要它们干嘛？[/S2]

[S3] 我怎么听着，这第四道整个是冲「复读机」去的？[/S3]

[S1] 那第五道呢？你刚说五道。[/S1]

[S2] 第五道叫 min p——m-i-n，下划线，p。把概率明显垫底的尾巴整段砍掉：不到「最高概率乘 min p」的，全砍。性子特别：砍谁都不影响冠军。所以有专门归类——argmax 不变的处理器。[/S2]

[S3] 等等，「argmax 不变」我还不太懂——argmax 就是「选最大」那个动作吧？动不了冠军，就叫 argmax 不变？[/S3]

[S2] 对，你这个词拆得准。这个分类是整个管线最关键的分叉，我展开来说。——能换冠军的四道，必须在贪心快路之前跑完，快路才敢直接选最大；动不了冠军的 min p，留到温度之后、随机路上再生效——快路直接跳过它，跳过也不影响结果。[/S2]

[S2] 先判整批：全是贪心，走快路——温度都不上，直接选最大；只要有一个请求要随机，整批走随机路。这一拍走哪条道，由最「不贪心」的那个决定。[/S2]

[S3] 一颗老鼠屎坏一锅汤？一个要随机的，全桌跟着抽？[/S3]

[S2] 批处理就这样，取所有人要求里最贵的那个。[/S2]

[S3] 我试着接一句：快路的假设是「直接选最大就对」——所以能换冠军的工序必须先跑完，不然快路就是骗人的。对吧？[/S3]

[S2] 对，就这个理。动不了冠军的，快路放心跳过。[/S2]

[S1] 我来总结一下：留底拍照；四道能换冠军的先跑；整批判贪心，全贪走快路；有一个要随机，整批上温度走随机路。那随机路上还有什么？[/S1]

[S2] 温度——头一回正经见它，给句定义：把打分整体缩一缩再选，温度越低越认死理，越高越野。温度之后是 min p，再往后是 top-k、top-p 截断。[/S2]

[S3] top-k、top-p 这俩我网上见了一年了，一直没细究。能不能展开说说，不太理解这俩到底怎么截？[/S3]

[S2] top-k 截断：只从前 K 个里选，数人头。top-p 截断：从最高的开始累加概率，够了就停，看分量。都是怕选到垫底的尾巴。这两道在卡上按设备备了好几套后端，构造时绑死。[/S2]

[S3] 截断完，就抽了？[/S3]

[S2] 抽也有讲究。两条路：一条 random sample——r-a-n-d-o-m，下划线，s-a-m-p-l-e；另一条走一个叫 flash infer 的库。目的同一个：避开同步。抽样要随机数，随机数一生成，GPU 就得停下来等 CPU——老朋友，GPU 空转。[/S2]

[S3] 「别让 GPU 闲着」——这句式我耳朵听出茧了，全季的跟头全栽在它身上。[/S3]

[S2] 说明它真是病根。最后交卷：把原始概率的 top-k 收集回来——从留的底里取前几名，交给要 logprobs 的请求。开头那步留底，就这会儿用的。[/S2]

[S3] 我复述：留底、四道改分、判贪心分路、温度、min p、截断、抽、交卷。对吧？[/S3]

[S2] 对，记群组比记编号牢靠。[/S2]

[S1] 行，九步齐了。采样参数这套旋钮——温度、top-k、惩罚、偏置——今天各归各位。可你开场说的主角，还没登场？[/S1]

[S2] 对。它不在九步里——它是采样之前的一道闸门：语法位掩码。[/S2]

[S3] 闸门……在采样之前就拦？这跟「先采样再校验、不对就重抽」比，好在哪？[/S3]

[S2] 好在不重抽。核心一句话：约束不改采样，只加一层掩码。你的 JSON 约束被编译成语法状态机——每吃一颗 token 跳一个状态，状态决定下一步允许哪些词；「允许」翻译成 0 和 1 的掩码，非法的全打成负无穷。[/S2]

[S3] 状态机我懂，跟正则表达式的自动机一个思路。0 和 1 的掩码——1 放行、0 拦下，是吧？那坑在哪？[/S3]

[S2] 坑一：编译慢。格式约束编译成状态机，可能上百毫秒——堵在调度循环里，一拍直接卡死。[/S2]

[S1] 上百毫秒？GPU 一拍才几毫秒。——欸，这话耳熟，好像哪期埋过这个扣？[/S1]

[S3] 我笔记里有：第二期挂的账——「语法编译要上百毫秒，不能堵在调度循环里」。挂了三期了，今天该还了。[/S3]

[S2] 还。它根本不进调度循环——编译扔进线程池，请求先进等候区，状态名很长：waiting for structured output grammar，等语法编译完成。引擎每拍顺路瞄一眼：只等 0.1 毫秒，没熟就回去干活，下一拍再瞄。[/S2]

[S1] 0.1 毫秒？这跟不等有啥区别？[/S1]

[S2] 区别大了。死等是线程睡着，一睡一拍就废了；0.1 毫秒是瞄一眼——路过厨房问句「好了没」，没好回客厅看电视，过会儿再来。等有代价，瞄一眼没代价。[/S2]

[S3] 那编译的这上百毫秒里，这个请求一颗 token 都不出？[/S3]

[S2] 对，它还没上牌桌，谈不上出 token——编译好了才排队进场。[/S2]

[S1] 坑二呢？[/S1]

[S2] 坑二：约束写法有六种，引擎只认一种。json、正则、choice、grammar——给结构、给正则、给选项、给语法规则。[/S2]

[S2] 还有两个带尾巴的：json object，强制整段是 JSON 对象；structural tag，管「先自由发挥、到指定段落必须守规矩」的混排。六种归一成一个编译键：约束类型加规格字符串。[/S2]

[S3] 六种压成一个键？等于引擎眼里只有一种请求？[/S3]

[S2] 对，最绝的是 choice。用户写「从这几个里挑一个」，校验期被原地改写成一段 EBNF——E-B-N-F，描述语法规则的格式。请求到引擎时，choice 字段清空、grammar 字段填好——引擎压根没见过它。[/S2]

[S1] 你交的是申请表，前台转手翻译成内部单子，你还以为原样递上去了？[/S1]

[S2] 就这个意思。你交请求那一刻，参数就被原地改造——引擎收到的，从来不是你写的原版。[/S2]

[S3] 坑三？[/S3]

[S2] 坑三最深：状态机怎么跟投机解码共存。状态机有六个方法的契约——接收、试走、倒带、填掩码、判终、重置。接收正式推进；试走只验不推，拿几颗 token 试一遍，状态不动；倒带最特殊，是给投机解码留的口子。[/S2]

[S3] 停——状态机还能倒带？走过了还能退回去？[/S3]

[S2] 能，而且倒带的上限跟投机草稿的长度绑定：草稿最多猜几颗，状态机就允许回退几颗。因为投机一次猜好几颗，猜错要被拒，语法状态就得跟着退回上一步。[/S2]

[S1] 试走是给草稿做预检的？先拿草稿在状态机上空走一遍？[/S1]

[S2] 对。预检用试走，不推进；正式采样用接收，才推进——代码里一对孪生：validate tokens 和 accept tokens。真正采出来那颗，由调度器收尾时调接收推进。这一对，是语法和投机一起开的钥匙。[/S2]

[S1] 钥匙有了，看锁——掩码怎么落到 GPU 上？四千个整数，怎么变成十二万八千个判决的？[/S1]

[S2] 分两头。调度侧按请求排队装配：每个请求占一行，投机时每个草稿位置占一行。一个 32 位整数装 32 个词的判决，十二万八千个词，一行四千个整数。不受约束的行，整行填 -1，全放行。[/S2]

[S3] 等等——投机的时候，为啥每个草稿位置都要占一行？[/S3]

[S2] 因为每颗草稿都要验，验的时候同样得过语法这道闸——所以逐位置配行。[/S2]

[S2] 填这些行也有讲究：最大批量超过 128，才建线程池走并行填充，十六行一组，每行独写，线程安全；没过 128，线程池压根不建，纯走串行。[/S2]

[S3] 并行还挑客？这个 128 的门槛，哪来的讲究？[/S3]

[S2] 线程不是免费的：批量小，开线程比填掩码还贵——128 就是值回票价的线。[/S2]

[S2] 再看 worker 侧。预分配卡上缓冲，用一条独立传输流——copy stream，c-o-p-y 下划线 s-t-r-e-a-m——把掩码异步搬上卡。搬的同时 GPU 还在算前向：传输和计算两头并进。[/S2]

[S1] 这手法全季用了八百回了——说穿了还是那句：别让 GPU 闲着。[/S1]

[S2] 好用的手法才值得用八百回。到卡上就是位运算：算完 logits、进采样器之前，一个自写的 Triton 内核把打包的整数一位位拆开，看到 0，就把对应 token 的打分原地写成负无穷。[/S2]

[S3] 等等——你说「负无穷」，不是「一个很大的负数」？这俩有区别？[/S3]

[S2] 有，这是全章我最喜欢的细节。后面还有温度、top-k、top-p 要动这些分：一个很大的负数，温度一缩，可能又被拉回可选范围；只有负无穷，任何变换下概率都是零，永远选不到。[/S2]

[S1] 就好比拉黑跟不回消息的区别——不回消息，对方还能再发；拉黑，物理上发不进来。大负数是「不回消息」，负无穷才是「拉黑」。[/S1]

[S2] 这个比喻我记下了——拉黑两个字一出来，负无穷就立住了。[/S2]

[S3] 我补个较真：这套自写内核，是默认就跑的吗？你别又是高级玩法。[/S3]

[S2] 问得好，不是。默认走另一条路：先把掩码摊平，再交给 x grammar 的库函数——它是 vLLM 默认的语法后端库。自写内核那条是 V2 路径，默认关，得自己开。最怕把默认和高级路径搅成一锅粥。[/S2]

[S1] 好，掩码落地讲完。现在解扣——「关掉了还在偷偷跑」，到底什么东西在偷偷跑？[/S1]

[S2] 草稿模型。先把投机解码讲清楚：拿个便宜小模型先猜好几颗 token，大模型一次验证——猜对了，白赚速度。[/S2]

[S2] 草稿有两类来源。一类纯 CPU：n-gram，在当前上下文找最长匹配的重复片段，找到就把后面的词抄过来当草稿。它用的算法是 KMP——K-M-P，字符串匹配的老算法。另一类是模型类，像 EAGLE、MTP，吃大模型的中间状态，跑一遍小模型前向，吐出草稿。MTP 展开说是 M-T-P，多 token 预测。[/S2]

[S3] n-gram 抄作业？就是「这句话我上次这么说过，这回多半还这么说」？[/S3]

[S2] 对，抄作业。社区里有位作者剖析 vLLM 时点过这块，他是这么说的——{{voice:voice-019}}V1 当时没走 LLM 级草稿模型，用 n-gram、EAGLE、Medusa 这些更轻的方案；n-gram 首次匹配就返回，带「最近偏差」。——原话大概这个意思。那是去年的剖析，现在 MTP 这类也进来了。[/S2]

[S1] 抄来的作业，大模型怎么验？[/S1]

[S3] 我也插一句——变长的草稿，怎么塞进一个批次？长短不一啊。[/S3]

[S2] 用几组下标间接对齐：谁的几颗草稿、对应的 logits 在哪行，索引说清楚。大模型只跑一次前向，每个草稿位置的目标概率全出来。然后逐颗验收：大模型算的概率跟草稿给的概率比一比，够高——接受，白赚一颗；不够——拒绝。[/S2]

[S3] 拒绝就完事了？[/S3]

[S2] 没完，这是命根子。拒绝时，从「大模型觉得行、草稿没猜到」的那部分概率里，补采一颗——数学上叫残差分布：两个分布相减，负数归零。有这一步，输出分布跟「压根没用投机」一模一样。[/S2]

[S3] 等会，我较真一下——拒绝之后直接停，不行吗？为啥非得补这一颗？[/S3]

[S2] 直接停，分布就变了：模型本来有概率说一些话，被草稿带沟里就没了。补采这颗，是把「被草稿偷走的概率」还回去。加速可以，绝不许改变模型说话的习惯——这是投机解码能进生产的底线。[/S2]

[S1] 你这话我得记下来：加速不许改分布。那验收这一步，代价不小吧？[/S1]

[S2] 问到点子上了。今年 MLSys 有篇口头报告论文，系统测了投机解码——{{voice:voice-033}}批大小 1 时，EAGLE 加速 1.73 倍；批涨到 128，只剩 1.21 倍。700 亿参数的 Llama 3 上，从 1.96 倍掉到 1.72 倍。更狠的：验证开销占总运行时间 42% 到 95%。——大意就是这些。[/S2]

[S1] 批越大越不划算？跟我直觉反着来。[/S1]

[S3] 我猜猜——批一大，大模型自己就能把 GPU 喂个差不多，草稿省的余量就不值钱了？[/S3]

[S2] 对。所以论文结论：投机解码真正的瓶颈不是草稿准不准，是验证本身。[/S2]

[S3] 那社区里有真人踩过坑吗？[/S3]

[S2] 有。GitHub 上有人报过——{{voice:voice-018}}草稿接受率一低，生成反而变慢：同时为两个模型付费，几乎没收益。——大意是这样。这事到现在还有跟踪单在跟。[/S2]

[S1] 那到底开不开？给个准话。[/S1]

[S2] 给不了。草稿猜多长、接受率做到多少才划算，跟模型、批大小、硬件全缠在一起，书里也没给能抄的答案。这个我们也没搞清楚——评论区有懂的说说。[/S2]

[S1] 行，记下了。解扣吧——「关掉了还在偷偷跑」，怎么回事？[/S1]

[S2] 前两周有人在 GitHub 报了个 bug——{{voice:voice-034}}一台 GB10 机器上，动态投机解码在批大小跨过阈值后把投机关了，吞吐从每秒 232 颗掉到 24 至 157 颗；整批的墙钟时间从 6.3 秒涨到 40 至 60 秒。——这是报告的大意。[/S2]

[S2] 他追到的根因更扎心：就算投机已经关了，草稿模型每步还在跑一次完整前向。「已关闭」这个判断，发生在草稿模型前向之后——不是之前。[/S2]

[S3] 我确认一下——「关没关」这个判断，排在草稿前向的后面？那就算判出来是「关」，那次前向也已经跑完了，白跑一趟。[/S3]

[S1] 闸门拉了，水龙头还在流？关了个寂寞？[/S1]

[S2] 关了个寂寞——钱照付，货没拿到。不过说清楚：这是报告者自己追的根因，官方还没确认，修复也没影。但它印证了主线：投机解码每一环都有隐藏成本，关掉不等于不付钱。[/S2]

[S3] 这 bug 跟前面说的状态机倒带，是一根线上的吗？[/S3]

[S2] 一根线上，而且这正是最后一块拼图：结构化输出跟投机解码同时开的时候，整个引擎得绕一个大圈。[/S2]

[S1] 怎么个绕法？[/S1]

[S2] 你想：掩码的行，一行对应一个草稿位置。可草稿是大模型刚猜出来的——调度器要配掩码，得先知道上一步草稿猜了哪几颗，不然行数都对不齐。[/S2]

[S3] 所以采样得等草稿回来？这不就卡住了吗？[/S3]

[S2] 对，这就是 deferred sampling——推迟采样，被逼着等一拍。链条是：草稿先传回调度器，用「试走」做语法预检；不合法的直接扣掉；剩下的按位置配掩码行；然后才正式采样。[/S2]

[S1] 我捋一下：草稿回来、语法预检、扣掉非法的、配好掩码、正式采样；验收被拒的，再触发倒带，语法状态退回上一步。[/S1]

[S2] 一步不差。咬合紧到调度器要专门打两个标记：这批有结构化输出请求、这批采样必须等上一步草稿落定。链条断一环，行数对不齐，掩码白配。[/S2]

[S3] 我联系一下前面的：这就是为啥状态机契约有「试走」和「倒带」——没有这俩，语法跟投机根本没法一起开。这设计是成对长的。[/S3]

[S2] 对，这个闭环你自己合上了。[/S2]

[S1] 那这套细节，面试会问吗？我最近刷面经，感觉这个方向越来越热。[/S1]

[S2] 会，而且问得深。牛客上有位作者记过一串追问——{{voice:voice-020}}MTP 多 token 预测的大致流程？实测接受率多少？优化的是首 token 延迟还是逐 token 延迟？引入额外计算，为什么吞吐还能涨？——原话大概这样。[/S2]

[S1] 最后一个问题，你能答吗？[/S1]

[S2] 这本书就答了它：一次前向验一整批草稿，等于把好几颗 decode 压成一次，验证的边际成本摊薄，吞吐才涨。追问到接受率这层，靠背概念接不住。[/S2]

[S3] 这条我记本上了：面试要的是这笔账，不是名词。[/S3]

[S1] 机制全讲完了，该吵一架了。我憋了个问题：这套东西真比「先采样再校验」快？我怎么听说，结构化输出整体更慢？[/S1]

[S2] 你听说的没错，这是社区吵得最凶的地方。vLLM 官方论坛的版主公开承认过——{{voice:voice-017}}结构化输出整体比无约束解码慢，瓶颈在 CPU 和 GPU 的同步：状态机允许的 token 列表翻译成 GPU 掩码张量，这一步就是瓶颈。——他的大意。[/S2]

[S2] 他还点了更具体的：xgrammar 在 RTX 4090 上，因为同步开销，反而比 outlines 还慢——outlines 是另一家做结构化输出的库。他还说，真正异步的处理还在开发中。官方认账，路没走完。[/S2]

[S3] 版主亲口说慢？我本来挺吃这套设计的——几千个整数管住十几万个词，多漂亮。这我不能当没听见。[/S3]

[S2] 还有第二份数据。去年有支团队做过系统评测——{{voice:voice-016}}XGrammar 在简单重复格式下吞吐最高，动态复杂格式下被 LLGuidance 反超。而且 XGrammar 能编译的格式，不少被 vLLM 集成层拒掉，实际可用覆盖率低于编译数字。——大意是这样。LLGuidance 是另一个引导解码库，跟 XGrammar 唱对台的。[/S2]

[S1] 编译能过、集成不过？那不全白编译了吗？[/S1]

[S2] 两个数字之间隔着一条缝。再叠上刚才论文那 42% 到 95%——批判方的话就一句：这套组合，理论很美，实测全是坑。[/S2]

[S1] 那你站哪边？别光转述。[/S1]

[S2] 我站「看遮挡」。反方最扎心的点我全认：瓶颈都是真的。但注意共性——全卡在 CPU 和 GPU 的同步上。而这期的设计，恰恰都在把同步赶出热路径：掩码才四千个整数，独立流传输，跟前向重叠，自写内核在卡上直接拆。[/S2]

[S3] 我插一句——版主说的病根是同步，你说的药方也是赶同步。病根和药方，是同一个词？[/S3]

[S2] 同一个词。所以才说「正在被击破」，不等于「已经击破」。上期那组数也算证据：800 行 Triton 跑出七万行 C++ 的 100.7%，kernel 层的功夫是真的。[/S2]

[S3] 那判据呢？给个能带走的。[/S3]

[S2] 一条：在你的 GPU、你的格式复杂度下，掩码的填充加传输，能不能被前向计算完全遮盖。遮得住，结构化输出就是免费的；遮不住，它就是真的慢，别硬吹。[/S2]

[S1] 那我怎么知道遮不遮得住？总不能每种格式都上机测吧。[/S1]

[S2] 上机测最靠谱。但选型有个更阴的坑：量化。几个月前有份评测——{{voice:voice-035}}700 亿参数的 Llama 3.3，FP16 下函数调用评分 0.91，AWQ 的 INT4 量化后跌到 0.78；JSON 遵守率从 0.94 跌到 0.83；自由文本几乎没退化。——大意是这样。[/S2]

[S1] 量化对聊天没影响，专咬 JSON 一口？什么原理？[/S1]

[S2] 原理我们也没完全吃透，这个真没搞清——评论区有懂的说说。但现象是实打实的：你拿 INT4 跑 Agent 的活，可能恰恰在最需要精确的地方，悄悄降级。[/S2]

[S3] 好，这个「没搞清」我连问号一起记本上。能记住的结论就一条：量化过的模型跑结构化输出，得自己上手测过才算数。[/S3]

[S1] 我来收个口：结构化输出不是免费，也不是原罪——看遮不遮得住，还得防量化补刀？[/S1]

[S2] 对。遮得住就是免费，遮不住就是慢，量化再来补一刀。选型之前，三笔账都得算。[/S2]

[S3] 我替听众把这三笔账摆齐：掩码开销遮不遮得住、能编译和能集成的缝、量化补刀——选型前挨个过。[/S3]

[S1] 好，说点这期之外的。五期走完，从一个请求进门到一颗 token 出门，这条路到头了。我回头看，每期背后好像是同一个句式。[/S1]

[S2] 你是不是想说——不是「这样更好」，是「不这样就跑不动」？[/S2]

[S1] 对。拆三段，不是好玩，是不拆 GPU 就饿着；数 token 不数请求，不是公平，是不这样 GPU 吃不饱；KV cache 切成页，不是省事，是不切就爆显存。[/S1]

[S3] 后两期也是：Python 编译成录像，不是炫技，是 Python 太慢；JSON 约束变成位掩码，不是花活，是模型自己守不住规矩。[/S3]

[S2] 所以一本四十来章的源码书值得读——不是教你 API，是让你看见一个推理引擎的每一滴汗。「为什么这么设计」的答案，全在汗里。[/S2]

[S1] 那这些汗，值不值得普通程序员去啃？我翻面经，感觉各家要的东西还不一样。[/S1]

[S2] 不一样。牛客上有位作者比较过几家——{{voice:voice-023}}字节覆盖推理优化、推荐、多模态，考系统化思维；腾讯偏重推理框架，vLLM 和 Paged Attention 是独立高频考点，面腾讯得把源码啃透。——他的大意。[/S2]

[S3] 也就是说，奔着推理方向去，啃源码绕不开——这句我记死了。[/S3]

[S2] 我至少敢这么说：啃完这本书，你再看那 128000 个分数，看到的不是黑盒，是一条有血有肉的流水线——有人抢救概率，有人改分，有人砍尾巴，有人守闸门，有人抄作业，有人验收。[/S2]

[S1] 最后一句送给大家：下次你让模型吐一段 JSON，记住——不是它学会了规矩，是它身后有一整个引擎，在替它把关。[/S1]

[S2] 从一颗 token 出发，看见一个引擎的全部汗。这季就到这里，下季见。[/S2]

[S1] 下季见。[/S1]
