# 第 1 期：一条「你好」，两趟跨进程——三段式异步解耦

> 三段式的本质不是拆开更好玩，是不等切字就把 GPU 喂饱。

## 本期简介

你给本地 vLLM 发了俩字「你好」，一秒不到就回了。但这条请求不是在一个程序里算完的：先在当前进程切成 token——模型认识的编号——跨进程扔给一个叫 EngineCore 的独立进程做推理，算完再跨进程传回来，拼回汉字。同一条请求，跑了两次进程间通信。

俩字寄两趟跨进程快递，是不是脱了裤子放屁？本期拆完你会看到：这不是折腾，是服务一千个并发用户时，唯一能让 GPU 不等 CPU 的架构。

## 本期要点

- **为什么非要拆进程**：GPU 最贵的状态是空转——上万个核同时闲着。切字、拼字是 CPU 的活，模型前向是 GPU 的活，挤在同一个进程里同步排队，GPU 算完一拍只能干等。拆的粒度是进程而不是函数：线程共享内存就是互相拖累，进程是操作系统级的物理隔离，收请求的进程再忙也碰不到引擎一根汗毛
- **v0 到 v1，内核没废**：v0 是单进程同步，功能优先；v1 把 CPU 的活留在收请求的进程、GPU 的活锁进独立子进程。同一套引擎内核，两种驱动——离线批量进程内直连（InprocClient），线上服务跨进程异步投递（AsyncMPClient）。对外两个使用面：LLM 与 AsyncLLM
- **三段式扇出**：请求从 add_request 同时走三条路——输入处理在本进程（验三道票、归一化切字、多模态展平、组装标准载荷 EngineCoreRequest），引擎段跨进程投递给独立子进程，输出处理由后台任务 output_handler 把混装结果按请求编号拆开、投回每个请求的信箱
- **信箱模型**：每个请求进门先建一个专属小邮箱，跟快递柜一个道理——投的投、取的取，generate 全程只摸自己那个格子，引擎进程长什么样它根本不关心。要是所有人共用一个队列，谁取慢了后面全堵
- **ZMQ 那座桥**：引擎进程除干活的主线程外，起两个守护线程管收发——收的一头走 DEALER 套接字，发的一头走 PUSH，中间靠两条队列传话，GPU 前向与网络收发叠着走。张量传输走多帧零拷贝：小张量内联进消息主帧，大张量直接传内存地址，多模态张量走共享内存带外通道
- **引擎的心跳**：忙循环 run_busy_loop 一拍四步——调度、执行模型前向、采样、更新状态。正在算的这一拍谁来了都不让，新请求和撤销都排队等这一拍跑完
- **争议账本**：SGLang 架构简单得多、唯一 prompt 场景只差 2-4%，那多出来的进程边界图什么？——37% 的差距（p50 首 token 延迟 195ms vs 310ms）是前缀缓存的账，不是拆三段的账；7GB vs 21GB 显存是参数口径乌龙，对齐后基本相同。判据只有一条：并发量有没有跨过单进程同步路径的 GPU 饥饿点——低于十个并发，同步更简单更快；三位数并发往上，不解耦就是让 GPU 天天空转
- **「我不知道」**：大张量走零拷贝旁路的分界线具体是多少字节，书里没写死，主播也没搞清楚——评论区有翻过代码的朋友，说说那条线画在哪

## 引用的社区声音

- **牛客面经（AI Infra 实习岗，2026-03）**：vLLM 问到了 PagedAttention、连续批处理、v0/v1 架构，还有 chunked prefill、prefix caching；SGLang 代码没怎么看、问的不多——考的是「你懂不懂为什么这么设计」，不是背名词
- **Aleksa Gordic（vLLM 架构剖析，2025-09）**：拆进程不是过度设计，是服务千万并发请求时唯一经得起拷问的架构选型；数据并行时还要再挂一个协调进程，彼此靠 ZMQ 消息和共享内存传话。他也认账：进程边界一多，调试排错的复杂度跟着涨
- **Spheron（GPU 云服务商实测，2026-06）**：唯一 prompt 场景两家只差 2-4%，几乎打平；但 80% 共享前缀、50 并发时，SGLang 的 p50 首 token 延迟 195ms，vLLM 310ms——差了 37%。主播提醒：卖 GPU 云的自己下场跑对比，有没有倾向性，心里留个秤
- **vLLM 用户实测（GitHub 讨论帖）**：同一个模型，SGLang 只吃 7GB 显存、vLLM 吃 21GB？事后查明是参数口径不对——两家限制长度的参数根本不是一回事，对齐再测，显存占用基本相同。但光凭一句「谁更省」就准备迁移的人已经一堆——框架迁移的成本被严重低估
- **技术媒体消融实验（HackerNoon）**：把 vLLM 的核心优化一个个摘掉、量性能损失——全文没抓到，具体数字给不出，但「摘掉试试」这个思路，比吵架有用
- **Marcus Chen（生产环境 trace，2026-05）**：开了连续批处理，p50 延迟从 340ms 降到 190ms，但 p99 从 1.2 秒飙到 9.8 秒、p99.9 从 2.1 秒跳到 27 秒；根因是一次 60ms 的 prefill 让 23 个在飞的请求全部排队——GPU 利用率只有 81%，瓶颈不在算力，在调度

## 下期预告

那个被锁在独立进程里的引擎，咱们一整期都在它门口转悠，没进去。它里面那个忙循环，一拍四步——调度、前向、采样、更新——到底怎么排兵布阵？每一步，都可能决定一个请求是被喂饱，还是被饿死。下一期，把它拆开。
