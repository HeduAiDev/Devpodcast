# 第 1 期：一次「你好」，跨两次进程——三段式异步解耦

> 三段式的本质不是「拆开更好玩」，是「不等 tokenization 就把 GPU 喂饱」。

## 本期简介

你给本地 vLLM 发了俩字「你好」，一秒不到就回了。但这条请求其实不在一个程序里算完：先在当前进程切成 token，跨进程扔给一个叫 EngineCore 的独立引擎进程做推理，算完再跨进程传回来，拼回「你好」——同一条请求，跑了两次进程间通信。

这不是脱了裤子放屁。本期拆完你会明白：它是服务一千个并发用户时，唯一能让 GPU 不等 CPU 的架构。

## 本期要点

- **为什么要拆**：GPU 最贵的状态是空转——几万个核同时闲着，那是它最贵的状态。切字（tokenize）和拼字是 CPU 的活，跟 GPU 前向挤在同一个进程里同步排队，并发一上来，GPU 就一直半饿着
- **v0 到 v1，内核没废**：v0 是单进程同步路径，功能优先；v1 把 CPU 的活和 GPU 的活拆开。拆的是进程，不是代码——同一套内核，两种驱动：离线批量进程内直连，线上服务经 ZMQ 异步驱动
- **三段式**：一条请求从 add_request 同时扇出三条路——第一段输入处理（校验、切字、组装标准载荷，CPU 活全在门口干完），第二段引擎段（独立子进程跑 GPU），第三段输出处理（后台任务解多路复用，投回每个请求自己的信箱）
- **信箱模型**：每个请求一个自己的小邮箱（快递柜）。投的投、取的取，generate() 全程只摸自己的格子，引擎进程长什么样它根本不关心；同一个 request_id 挂在两个进程的不同数据结构上，两边靠它对上号
- **ZMQ 那座桥**：引擎进程起两个守护 IO 线程——DEALER 先开口握手再收消息，PUSH 只管推；主线程不碰收发，只跑引擎核心的忙循环。张量传输走多帧零拷贝：小张量内联，大张量直接传内存地址，多模态张量走共享内存带外通道
- **引擎的心跳**：run_busy_loop 四步一拍——调度、前向、采样、更新状态。正在算的这一拍谁来了都不让，新请求只进队列排队，算完再轮
- **争议账本**：SGLang 同步路径 vs vLLM 进程边界——37% 的差距（195ms vs 310ms）是前缀缓存的账，不是拆三段的账；7GB vs 21GB 显存是参数口径乌龙，对齐后基本相同。判据只有一条：你的并发量有没有跨过单进程同步路径的 GPU 饥饿点——低于十个并发，同步更简单更快；三位数并发，不解耦等于让 GPU 每天空转
- **「我不知道」**：大张量走旁路的分界线具体是多少字节，书里没写死——评论区有懂的说说

## 引用的社区声音

- **牛客面经（AI Infra 实习岗）**：vLLM 问到了 pagedattention、连续批处理和 v0/v1 架构，SGLang 代码没怎么看、问的不多——考的是「你懂不懂为什么这么设计」，不是「你背没背过 API」
- **社区技术作者（vLLM 架构剖析）**：拆进程不是过度设计，是服务千万并发请求时唯一经得起拷问的架构选型；数据并行时还要再挂一个协调进程，互相靠消息和共享内存传话。他也认账：进程边界多了，调试排错复杂得多
- **GPU 云服务商（2026-06 实测）**：唯一 prompt 场景，vLLM 与 SGLang 差距只有 2-4%，几乎打平；但 80% 共享前缀、50 并发时，SGLang 的 p50 是 195ms，vLLM 是 310ms——差了 37%
- **vLLM 用户实测（A10 / Qwen 2.5-7B）**：SGLang 只吃约 7GB 显存、vLLM 吃约 21GB——事后查明白是参数口径不对（两家的长度参数不是一回事），对齐后基本相同。但光凭一句「更省显存」就想迁移的人已经很多——框架迁移的成本被低估了
- **技术媒体消融实验（HackerNoon）**：把 vLLM 的核心优化一个个摘掉、量性能损失——「摘掉试试」这个思路，比吵架有用
- **Marcus Chen（dev.to 生产 trace，2026-05）**：开了连续批处理，p99 从 1.2 秒飙升到 9.8 秒；一次 60 毫秒的 prefill 让 23 个在飞的请求全排队——GPU 利用率才 81%，瓶颈不在算力，在调度

## 下期预告

那个被锁在独立进程里的引擎，自己里面到底在干嘛？一个忙循环，四步心跳——调度、前向、采样、更新，每一步都可能决定一个请求是被喂饱还是被饿死。下一期，我们把它拆开。
