# 一次「你好」，跨两次进程：三段式异步解耦

[S1] 我昨天晚上干了件事：本地起了个 vLLM，给它发了俩字——「你好」。回得挺快，一秒不到。但我越想越不对劲：这俩字，好像不是在一个程序里算完的。[/S1]

[S2] 你感觉没错。它先在当前进程把这两个字切成 token，跨进程扔给一个叫 EngineCore 的独立引擎进程做推理，算完再跨进程传回来，拼回「你好」。同一条请求，跑了两次进程间通信。[/S2]

[S1] 等一下，俩字还要寄两次快递？我以为推理就是把文字喂给模型，它吐出来就完事了。[/S1]

[S2] 大多数人的第一反应都是这个。但这期拆完你会明白，它不是折腾——是服务一千个并发用户时，唯一能让 GPU 不等 CPU 的架构。这句话先钉在这儿，一会儿回来验证。[/S2]

[S1] 那这期标题我懂了：一次「你好」，两次快递。但我先赌一块钱——这期讲完，你会说这两趟快递比走路快。[/S1]

[S2] 赌注收下。但先别急着说快——先说「不这样会怎样」。[/S2]

[S1] 那我这期就盯一件事：这俩字从发出去到回来，中间那眨眼的工夫，经历了什么。[/S1]

[S2] 快是结果，不是原因。[/S2]

[S1] 行，那我先问个笨问题：以前不这样吗？没有独立引擎的时候，它是怎么跑的？[/S1]

[S2] 以前是 v0，单进程，一条路走到黑：请求进来，同一个进程里切字、送引擎、前向、采样、拼字、返回。你半夜发那俩字，v0 也能跑，就是撑不住很多人一起发。[/S2]

[S1] 等一下，「单进程同步」这个「同步」是什么意思？是不是一个请求算完，才能算下一个？[/S1]

[S2] 差不多。v0 里引擎直接驱动那套 step，一个请求的活没干完，下一个就进不来。更麻烦的是队里混着两种活——CPU 活和 GPU 活，谁都在等对方。[/S2]

[S1] 单进程听起来挺顺的，哪儿不好了？[/S1]

[S2] 坏在切字这一步，专业叫 tokenize，是 CPU 干的活；拼回文字也是。GPU 前向跟它们挤在同一个进程里，同步排队——GPU 算完一拍，回头看，CPU 还在切，只能干等。就像小饭馆里老板一个人又点单又炒菜，桌一多，后厨就饿着等前台。[/S2]

[S1] 那 v0 当初为什么要这么设计？傻吗？[/S1]

[S2] 不傻，是「先把推理跑起来」的阶段，功能优先。用户量上来，GPU 空转开始烧钱，才动刀拆——很多架构是逼出来的。[/S2]

[S1] GPU 等 CPU？我一直以为是反过来，瓶颈都在 GPU。[/S1]

[S2] 单用户看不出来，空转几毫秒无所谓。但服务场景下，切字和拼字都在热路径上，并发一上来，每个请求都让 GPU 等一下，累计起来，GPU 就一直半饿着。所以 v1 干的第一件事：把 CPU 的活和 GPU 的活拆开。[/S2]

[S1] 那到底多严重？给个数呗，不然我没概念。[/S1]

[S2] 精确的数书里没给，但方向是死的：并发每涨一倍，GPU 空等的时间就涨一倍——排队的人越多，前面的人越等。这已经足够让 vLLM 动刀了。[/S2]

[S1] 拆成两个函数不行吗？为什么非要拆进程？[/S1]

[S2] 你问到点子上了。拆的粒度是进程，不是函数。CPU 的活留在收请求的进程——校验、切字、组装；GPU 的活锁进独立子进程。两边内存不共享，交换数据必须过桥。[/S2]

[S1] 等一下你刚才那句我没跟上——同一个进程里开几个线程，不也能各干各的吗？[/S1]

[S2] 线程共享内存，共享的意思就是互相拖累：一个崩，全崩；一个慢，全慢。进程隔离是物理隔离，引擎进程被操作系统单独调度，API 进程再忙也碰不到它。代价就是过桥要花钱，这笔账我们后面算。[/S2]

[S1] 听起来这个隔离还有个好处——引擎进程最怕被打扰？[/S1]

[S2] 对。收请求的进程再忙，哪怕排队排到天际，引擎照常一拍一拍算——服务端的抖动，到不了引擎门口。[/S2]

[S1] 那 v0 那套引擎代码，岂不是白写了？[/S1]

[S2] 这是最狠的地方：内核没废。v0 的引擎核心原封不动，只是开法变了——离线批量，进程内直接驱动，同步调；线上服务，经 ZMQ 异步驱动。一套内核，两种驱动，一套代码两处用。[/S2]

[S1] 也就是说，v0 不是被扔掉，是换了个姿势继续活？[/S1]

[S2] 对。拆的是进程，不是代码。记住这个「一套内核两种驱动」，它是理解整个引擎的钥匙，后面还会回来。[/S2]

[S1] 那这两个使用面，是不是一个叫 LLM、一个叫 AsyncLLM？[/S1]

[S2] 对，名字写在脸上了。LLM 是离线同步的，拿起来直接调；AsyncLLM 是服务异步的，走信箱那一套。同一个内核，一个进程内直连，一个跨进程投递。[/S2]

[S1] 哎，这个 v0 和 v1 的差异，面试要是问到，该答到什么程度？我最近刷面经，AI Infra 实习岗好像都在问这个。[/S1]

[S2] 确实是高频考点。牛客上一位面过 AI Infra 实习的同学写过一篇面经{{voice:voice-002}}，他原话的意思我转述一下：vLLM 问到了 pagedattention、连续批处理和 v0/v1 架构这些，最后补了一句——SGLang 代码没怎么看，问的不多。[/S2]

[S1] 他最后那句我注意到了：SGLang 代码没怎么看，问的不多。这意思是面试官也知道这块深？[/S1]

[S2] 有那个味道。作者自己都没看全 SGLang 的代码，照样过——说明考点是「你懂不懂为什么这么设计」，不是「你背没背过 API」。[/S2]

[S1] 行。那 v1 内部，到底怎么把一条请求拆成三段的？[/S1]

[S2] 从 add_request 这一步开始，一条请求同时扇出三条路。<break 300ms> 第一段，输入处理，在收请求的进程里干：校验、切字、组装成一个标准载荷。<break 200ms> 第二段，引擎段：载荷跨进程投给引擎，它算完，吐出一整批结果。<break 200ms> 第三段，输出处理：后台任务把整批结果解开，分回每个请求自己的信箱。[/S2]

[S1] 这三段是谁搭起来的？总得有个人接线吧。[/S1]

[S2] 程序一构造就全搭好了——输入处理、引擎、输出处理，初始化时各就各位；output_handler 这个后台任务，从出生那一刻起就在转，等第一个请求进门。[/S2]

[S1] 信箱？这词我喜欢，展开讲讲。[/S1]

[S2] 每个请求在 API 进程有个自己的小邮箱。你发请求，先给你建一个；引擎算完，第三段那个后台任务把结果投进来；你的 generate() 随时来取。投的投、取的取，两边根本碰不上面。[/S2]

[S1] 这不就是快递柜嘛！你放进去，我随时取，不用等快递员当面签收。[/S1]

[S2] 对，而且这个比喻能承重：快递柜解决的是「不用干等」。generate() 只盯自己那个格子，引擎那边同时跑着几百个请求，跟它没关系。要是共用一个队列，一个取慢了，全堵。[/S2]

[S1] 那投递员是谁？谁把结果放进柜子的？[/S1]

[S2] output_handler，一个后台任务，程序一启动它就在转。引擎每算完一批，它把混在一起的结果按请求 id 拆开，挨个投进对应信箱——这个拆活，专业叫解多路复用，一会儿单独拆。[/S2]

[S1] 那我取件，取到什么？一口吃下一整句话？[/S1]

[S2] 模型是逐 token 吐的，信箱里先有第一颗、再有第二颗。你 generate() 每次取到最新那颗，拼起来就是一句话。引擎吐一颗、投递员投一颗、你取一颗——三段同时都在动。[/S2]

[S1] 还有，两边怎么对上号？引擎进程那边可没有这个信箱。[/S1]

[S2] 靠 request_id。同一个请求，API 进程挂一份档案，引擎进程挂一份，两边靠同一个 id 对号。引擎算完，结果里带着 id，投递员一看 id，就知道投哪个柜子。[/S2]

[S1] 就是说一个请求，两边各记一份账？[/S1]

[S2] 对。add_request 这一步，本进程建好档案和信箱，引擎进程那边同步也建一份——同一个 id，挂在两个进程的不同数据结构上。你的 generate() 全程只摸自己的信箱，引擎进程长什么样，它根本不关心。[/S2]

[S1] 好，骨架有了。钻进第一段看看：这个「输入处理」，到底干了些啥？[/S1]

[S2] 一句话：把 CPU 的活全在门口干完，组装成一个标准载荷，才放它出门。进门先验三道票：空不空、超不超长、越不越界；然后归一化，该透传透传，该补切就补切；多模态字段展平排序；采样参数克隆补全。[/S2]

[S1] 第一段叫「输入处理」——我理解就是把人的输入变成引擎的输入？[/S1]

[S2] 对，而且变完的那一版，是引擎眼里唯一的版本——引擎不认你的原始话，只认这个标准载荷。[/S2]

[S1] 三道票都查啥？举个具体的。[/S1]

[S2] 空请求、超长请求、字段越界——三种死法，在门口就拦下来了。拦下来总比跨进程跑一趟再被退货便宜。[/S2]

[S1] 你前面说「该透传透传，该补切就补切」——切字还能透传？[/S1]

[S2] 对，有的输入自带切好的编号，就不用再切一遍，直接透传；没有的才现场补。能省一刀是一刀，CPU 的活每一刀都算钱。[/S2]

[S1] 可我还是没懂：为什么这个规矩这么重要？在引擎那边切，不也一样吗？[/S1]

[S2] 不一样。引擎进程里住的是 GPU，它最怕等人。切字要是挪进去，GPU 每拍开始前都得等 CPU 切完——每一拍都等，等于每一拍都在让 CPU。在门口做完，两边的活彻底错开：你切你的，我算我的。[/S2]

[S1] 那这个载荷，打包有讲究吗？不能直接扔个字典过去？[/S1]

[S2] 专门为跨进程设计的，讲究多了：数组直接透传不复制，没用的字段不序列化，垃圾回收也绕开。为什么？它天天跨进程，一天跑几亿次，每个字段多花一纳秒，都是真金白银。[/S2]

[S1] 明白。还有一个问题：一个请求想要三个候选答案，那种「并行采样」是在哪儿裂开的？[/S1]

[S2] 就在第一段。组装载荷的时候，采样参数里写着要几份，第一段直接把它裂成几路——不是引擎那边裂。所以引擎看到的永远是标准活，多倍采样的复杂度，在门口就消化掉了。[/S2]

[S1] 那多模态呢？图片、音频也走这套？[/S1]

[S2] 走，但得先展平——把图片、音频这些非文字输入统一摊成一个有序的列表，排好序，引擎才吃得下。这个活也是第一段干，CPU 活，在门口消化。[/S2]

[S1] 那过了桥之后——桥那边长什么样？[/S1]

[S2] 桥是 ZMQ，一个跨进程通信的库。引擎进程那边起两个守护线程：一个专门收消息——接住、解码、扔进内部队列；一个专门发消息——从输出队列取、编码、发出去。主线程不碰收发，只跑引擎核心那个忙循环。[/S2]

[S1] 三个干活的人，两条队列？那不得互相抢？[/S1]

[S2] 不抢，这正是目的：收发和 GPU 计算并行。GPU 算这一拍的时候，收消息的线程同时把新请求接进队列；GPU 算完，发消息的线程已经把上一拍的结果送出去了。三个动作叠起来，谁都不等谁。[/S2]

[S1] 你刚说收消息那个线程叫 DEALER？这名字听着就有讲究。[/S1]

[S2] 有讲究。ZMQ 的规矩，DEALER 得先开口打招呼——发一条 ready 消息，对面才知道你上线了；握手没完成，消息一律不发。发的那个线程叫 PUSH，只管往外推，引擎算完的结果一件不落全推出去。[/S2]

[S1] 合着一个是懂礼貌的，先开口；一个是直肠子，只管倒。[/S1]

[S2] 对，一收一发，中间全靠那两条队列撑着。[/S2]

[S1] 那消息里传的啥？张量那么大，每次都复制一遍？[/S1]

[S2] 这就是第二个心眼：多帧零拷贝。小张量直接内联进消息主帧；大张量走旁路，不复制内容，直接跨进程传内存地址；多模态张量更狠，走共享内存带外通道。[/S2]

[S1] 那「零拷贝」到底省了什么？就省了一次复制？[/S1]

[S2] 省的不止一次——大张量要是复制，得先拷进消息缓冲区，跨进程再落一份，到对面还得再读一遍。旁路直接传地址，那几次拷贝全省了。大模型一拍就是几百兆，这笔账不用我算吧。[/S2]

[S1] 这桥讲得这么细——两个守护线程加一个主线程，这不就是传说中的线程爆炸吗？[/S1]

[S2] 三个线程，爆炸不了——真正会爆的，是「每个请求开一个线程」那种设计。这里呢？三个线程管所有请求，全进程就这仨。[/S2]

[S1] 那给我个数：多大算大，走旁路？[/S1]

[S2] 这个分界线具体是多少字节，书里没写死，我们俩也没搞清楚，评论区有懂的说说。但设计意图是清楚的：能省一次拷贝就省一次，大张量的搬运费最贵。[/S2]

[S1] 行，记账上。但我还有个担心：一条请求过这么多桥、这么多队，出了错怎么查？错在哪一段都不知道。[/S1]

[S2] 对，这就是三段式的代价，它自己心里也有数。这笔账我们先记着，争议环节专门算。[/S2]

[S1] 好，回第三段。投递员那个活，凭什么说它不简单？[/S1]

[S2] 引擎一次算完一整批，几十个请求混在一起回来。output_handler 先按请求 id 拆开——解多路复用；再增量拼字，把编号拼回文字；检测停止串，看该停了没有；最后组装成结果，投进对应信箱。[/S2]

[S1] 引擎一次算一批，不是一次算一个？[/S1]

[S2] 对，GPU 最擅长一次算一大批，一批塞得越满越划算。但一批回来是混装的，必须有人拆。整个输出处理就一个循环——一条函数管整批，一条队列喂一个流。[/S2]

[S1] 一个循环管整批，那这个循环要不要管「谁先谁后」？[/S1]

[S2] 不用管。循环只认请求 id，谁先到谁先拆，顺序是引擎那边定的。它就是个纯流水线：进来混装货，出去分拣好的快递。[/S2]

[S1] 一个循环管几十个请求？万一某个请求吐得慢，它不得卡死？[/S1]

[S2] 两道闸门：结果太多就攒一攒、按节奏发，省得每颗 token 都去唤醒用户；能合并的合并成增量，只发新部分，不重复发历史。所以你取件永远不卡。[/S2]

[S1] 那要是一个请求要三个候选答案呢？第三段怎么投？[/S1]

[S2] 归拢着投。三个候选属于同一个请求，第三段在循环里聚成一个父结果，再投进那一个柜子。还有收尾：请求结束，档案和信箱都清理，不然堆一屋子死档案。[/S2]

[S1] 等于说，引擎吐混装货，第三段在门口拆成一件件快递，投进各家的柜子。[/S1]

[S2] 对，而且拆货这活也是 CPU 干的——你看，又印证了那个设计：CPU 的活全在外面，GPU 只管算。[/S2]

[S1] 行。那第二段，那个被锁在独立进程里的引擎，天天在里面干嘛？[/S1]

[S2] 跑一个忙循环，叫 run_busy_loop：从输入队列取请求，调一次 step，结果投输出队列，再取下一个。不睡觉，一直转。它是整个引擎进程的心跳。[/S2]

[S1] 我捋一下：收消息线程往队列塞，忙循环从队列取，算完往输出队列塞，发消息线程再从输出队列取——全进程就靠两条队列串起来？[/S1]

[S2] 对。三个执行单元，谁也不直接跟谁说话，都通过队列传话。这就是解耦的另一面：想改其中一个，另外两个不用动。[/S2]

[S1] 就这么简单？取一个、算一下、扔出去？[/S1]

[S2] 循环简单，但每一次 step 里有四步：调度一批，决定这一拍谁上桌；执行模型前向，GPU 真刀真枪算一遍；采样，从算出来的概率里挑一颗 token；更新状态。<break 200ms> 四步合起来，叫引擎的一拍。[/S2]

[S1] 四步里的第一步「调度」——就是决定谁上桌？[/S1]

[S2] 对，这一拍算哪些请求、算多少，它说了算。这一桌能坐多少人，得看 GPU 吃不吃得下。这块水很深，今天先不蹚。[/S2]

[S1] 四步一拍。那它算到一半，新请求来了怎么办？打断？[/S1]

[S2] 排队。新到的请求只进输入队列，绝不打断当前这一拍——想打断也不行，GPU 前向一旦起跑，中途插不了队。这一拍算完，下一拍再轮它。中止请求也一样，撤销也是消息，排队等这一拍跑完。引擎的原则就一条：正在算的这一拍，谁来了都不让。[/S2]

[S1] 那它怎么下班？一直转到地老天荒？[/S1]

[S2] 有状态机管着：正常跑、请求关停、正在关停三档，还有暂停状态。但今天不展开——重点是这一拍的四步，每一步都可能决定一个请求是被喂饱还是被饿死。就这四个字，够下一期讲一整集。[/S2]

[S1] 那最后一步「更新状态」更新个啥？[/S1]

[S2] 这一拍算完，每个请求走到哪、下一步干嘛，全记下来——下一拍就踩在这些记录上跑。四步就是一口气：排、算、选、记。[/S2]

[S1] 你说「喂饱还是饿死」……那要是有人分不到位置呢？比如显存不够，KV cache 的块分不出来？[/S1]

[S2] KV cache 就是每颗 token 在显存里留的笔记，模型靠它接上下文。块分不出来怎么办——那一拍怎么算、抢谁的、踢下去怎么排队回来，是后面要专门拆的题。今天先把「为什么拆三段」这笔账算完。[/S2]

[S1] 好，算账。账本翻开：两次进程间通信、三个线程、两条队列、独立进程、调试地狱。值吗？[/S1]

[S2] 有位社区技术作者把 vLLM 的架构从头剖过一遍，结论很硬——{{voice:voice-001}}——他原话大意是：拆进程不是过度设计，是服务千万并发请求时唯一经得起拷问的架构选型。他写那篇剖析的时候，除了收请求的进程和引擎进程，数据并行时还要再挂一个协调进程，互相靠消息和共享内存传话。同一个剖析，他也认账：进程边界多了，调试排错复杂得多，绕不过去。[/S2]

[S1] 那我换个问法：这套跟 SGLang 比，到底是「更好的设计」，还是「更贵的实现」？[/S1]

[S2] 这正是争议所在。社区里两种声音都有：一种说进程边界是必要的恶，一种说同步路径足够快。咱们接着摆数据。[/S2]

[S1] 那我直接问：SGLang 走同步路径，架构更简单，性能也不差——这多出来的进程边界，不是过度设计吗？[/S1]

[S2] 看数据。今年六月，一家 GPU 云服务商跑了组实测——{{voice:voice-036}}——他的结论是：唯一 prompt 场景，两家差距只有 2% 到 4%，几乎打平；但 80% 共享前缀、50 并发时，SGLang 的 p50 是 195 毫秒，vLLM 是 310 毫秒——差了 37%。[/S2]

[S1] 你看！打平！那折腾这么多进程，图什么？[/S1]

[S2] 图的是后半段。这 37% 是结构性的：SGLang 的前缀索引天生自动，vLLM 那套要手动开，还只认平铺的前缀。注意，这是共享前缀场景的账。[/S2]

[S1] 37%……这个数字对 vLLM 不友好啊。[/S1]

[S2] 对，不友好。但注意：这个差距是前缀缓存的账，不是「拆三段」的账——人家赢在索引，不是赢在同步。拿这个数说三段式是过度设计，打偏了。[/S2]

[S1] 说到比数据，我听说早前还有个段子：同一个模型，SGLang 只吃 7GB 显存，vLLM 吃 21GB，把一堆人吓跑了？[/S1]

[S2] 那事后来反转了，但反转过程特别值得讲。当时那位用户发帖说——{{voice:voice-025}}——原话大意：同一个模型，SGLang 只用了约 7GB 显存，vLLM 用了约 21GB，差了三倍。后来查明白是参数口径不对：SGLang 的「最长长度」默认值，跟 vLLM 的「最大长度」不是一回事。对齐之后，两边基本相同。[/S2]

[S1] 合着 7 比 21 是乌龙？那两边显存其实差不多？[/S1]

[S2] 修正之后基本相同。但反过来想：光凭一句「SGLang 更省显存」，多少人已经准备迁移了？这说明框架迁移的成本，被低估了。[/S2]

[S1] 那你这不是避重就轻吗？人家质疑的是「解耦值不值」，你跟我扯参数口径？[/S1]

[S2] 不是扯，是把秤先校准——单位没对齐，后面所有「谁更快、谁更省」都是废纸。秤校完了，再谈值不值。[/S2]

[S1] 那有没有人真的把每个设计拆开称过重？[/S1]

[S2] 有人干过——一家技术媒体把核心优化一个个摘掉、量性能损失——{{voice:voice-021}}——不过那篇文章我们没抓到全文，具体数字给不出。但「摘掉试试」这个思路，比吵架有用。[/S2]

[S1] 好，那「过度设计」这个罪名，到底成不成立？给我个硬证据。[/S1]

[S2] 看一条生产环境里的实测记录。技术博主 Marcus Chen，今年五月在自己线上系统抓的——{{voice:voice-027}}——他原话大意：开了连续批处理，p99 从 1.2 秒飙升到 9.8 秒；根因是长请求的 prefill 堵路——prefill 就是第一次把整段提示词喂给模型的那一步——一次 60 毫秒的 prefill，让 23 个在飞的请求全排队。结论：GPU 利用率才 81%，瓶颈不在算力，在调度。[/S2]

[S1] 等一下，这个不是连续批处理的坑吗？跟三段式有啥关系？[/S1]

[S2] 问得准。他的 trace 是长请求堵住短请求，但道理是同一个：CPU 的活和 GPU 的活搅在一条同步链里，一个慢活就能堵死一整批。三段式把这些活拆开，GPU 不等切字，也不等任何 CPU 的活。[/S2]

[S1] 所以开场那俩字，跨两次桥，其实是在买保险？[/S1]

[S2] 对，买的是「GPU 永远不被 CPU 拖住」的保险。你发「你好」的时候，同一刻可能还有九百九十九个请求在路上——你那俩字愿意等，它们不愿意。[/S2]

[S1] 所以你的意思是，GPU 空转的代价，比两段进程间通信的代价大？[/S1]

[S2] 量级上差得远。一次通信是微秒到毫秒级；GPU 空转，是几万个核同时闲着，那是它最贵的状态。三段式的本质不是「拆开更好玩」，是「不等 tokenization 就把 GPU 喂饱」。[/S2]

[S1] 你这话我得记下来——「GPU 最贵的状态是空转」。那三段式买的，是不是 GPU 的「在岗时间」？[/S1]

[S2] 说得挺准。你付了 GPU 的钱，就是要它一直干活；每空转一毫秒，都是拿钱不干活。三段式就是让在岗时间最大化的办法。[/S2]

[S1] 好，最后给个判据。到底该不该拆？别给我说「看情况」。[/S1]

[S2] 判据就一条：你的并发量，有没有跨过单进程同步路径的 GPU 饥饿点。低于十个并发，同步更简单更快，拆了纯属找事；到了三位数并发，不解耦就等于让 GPU 每天空转等着 CPU 的活。选架构之前，先想清楚负载落在哪个区间。[/S2]

[S1] 那我要是就十个以内的用户呢？这套架构是不是白搭了？[/S1]

[S2] 十个以内，同步路径更快、更省事——v0 那套内核还在，进程内直连就是给这种场景留的。三段式是给「并发会涨」买的保险：涨了，这钱花得值；没涨，先别花。[/S2]

[S1] 行，账算平了。所以「你好」那俩字跑两段进程间通信——[/S1]

[S2] 是服务一千个并发用户时，唯一能让 GPU 不等 CPU 的架构。这句话，现在立住了。[/S2]

[S1] 行，赌局我输了，一块钱给你。这两趟快递，确实比走路快。[/S1]

[S2] 收下了。下一块，等你听完引擎里面那四步再押。[/S2]

[S1] 但话说回来——这套东西这么绕，值得普通开发者学吗？[/S1]

[S2] 值得。因为它拆的不是一个程序，是一种思路：把 CPU 的活和 GPU 的活分家，让贵的设备永远不等人。这套思路，换哪个推理框架都成立。[/S2]

[S1] 立住了。但我还有个惦记：那个被锁在独立进程里的引擎，它自己里面到底在干嘛？四步一拍——调度、前向、采样、更新，每一拍都有人被喂饱、有人被饿死？[/S1]

[S2] 下一期，我们把它拆开。一个忙循环，四步心跳，每一步都可能决定一个请求是被喂饱还是被饿死。[/S2]

[S1] 下期见。对了，那个显存不够、分不到 KV cache 块的——也是下期？[/S1]

[S2] 那个更得往后排，值得单独拆一整期。先留个扣——到时候连抢人和排队一起讲。[/S2]
