# 一条「你好」，两趟跨进程：三段式异步解耦

[S1] 大家好，我是老张。这档节目就干一件事：啃一本讲 vLLM 内部实现的源码书，四十来章，拆成五期，把一个大模型推理引擎从入口讲到出口。坐我旁边的两位：阿凯，这本书的作者，AI infra 一线老兵；阿哲，传统后端程序员，不懂 AI，是替你们来的。[/S1]

[S2] 大家好。我在一线跟 vLLM 的代码打了好几年交道，写了这本书。先声明：我讲快了，你们俩随时掐我。[/S2]

[S3] 我是阿哲。我的活儿就是替读者拍桌子——讲快了、讲飘了，我直接打断。先说好，谁也别想糊弄我。[/S3]

[S1] 好，进正题。我昨天晚上干了件事：本地起了个 vLLM，给它发了俩字——「你好」。回得挺快，一秒不到。但我越想越不对劲：这俩字，好像不是在一个程序里算完的。[/S1]

[S2] 你的感觉没错。它先在当前进程把这两个字切成 token——token 就是模型认识的编号——然后跨进程扔给一个叫 EngineCore<break 300ms> 的独立进程做推理。算完再跨进程传回来，拼回汉字。同一条请求，跑了两次进程间通信。[/S2]

[S3] 等等。俩字，寄两趟跨进程快递？这不是脱了裤子放屁吗？我理解的推理，就是把话喂给模型，它吐字就完事了。[/S3]

[S2] 大多数人的第一反应都是这个。但这期拆完你会看到——这不是折腾。是服务一千个并发用户时，唯一能让 GPU 不等 CPU 的架构。这句话先钉在这儿，一会儿回来验证。[/S2]

[S1] 你这话我得记下来。这期的钩子就在这儿：俩字凭啥跑两趟跨进程？你就算一辈子不写推理引擎，这个「怎么把贵的设备伺候好」的思路，写后端、做架构都用得上。[/S1]

[S2] 要回答这个，得先看以前。我来说说这东西怎么来的。——vLLM 的老版本，社区叫 v0，单进程同步：请求进来，同一个进程里切字、送引擎、前向、采样、拼字、返回。——一条路走到黑。[/S2]

[S3] 打断一下。「单进程同步」，这个「同步」是什么意思？是不是一个请求算完，下一个才能进来？[/S3]

[S2] 差不多。v0 里引擎被直接驱动。一个请求的活没干完，下一个就进不来。更麻烦的是，这条队里混着两种活——CPU 的活和 GPU 的活，互相等。[/S2]

[S3] 等等，还有一个词——「前向」？你刚顺口带过去了，这词是啥意思？[/S3]

[S2] 「前向」就是让模型算一遍：把这一批 token 喂进去，算出每个位置下一个词的概率。后面采样，就是从这份概率里挑一个。[/S2]

[S1] 让我来捋一下：切字、拼字是 CPU 的活，模型前向是 GPU 的活，它们挤在同一个进程里排队，对吧？[/S1]

[S2] 对。就好比——小饭馆里老板一个人，又点单又炒菜又上菜。两三桌没事，桌一多，后厨就闲着等前台——GPU 就是那个大厨：算完一拍回头看，CPU 还在切字，只能干等。[/S2]

[S3] 那 v0 当初为什么这么设计？是没想到这一天吗？[/S3]

[S2] 不是没想到，是阶段不同。先把推理跑起来的阶段，功能优先，一个进程最省事。等用户量上来，GPU 空转开始烧钱，才动刀拆。——很多架构不是设计出来的，是逼出来的。[/S2]

[S1] 拆我理解。但拆成两个函数不行吗？为什么非要拆进程？[/S1]

[S2] 拆的粒度是进程，不是函数。CPU 的活留在收请求的进程：校验、切字、组装；GPU 的活锁进独立子进程。两边内存不共享，要交换数据，必须过桥。[/S2]

[S3] 你这句我没跟上。同一个进程里开几个线程，不也能各干各的吗？为啥非得进程？[/S3]

[S2] 线程共享内存，共享的意思就是互相拖累：一个崩，全崩；一个慢，都慢。进程是操作系统级的物理隔离，引擎进程被单独调度——收请求的进程再忙，也碰不到它一根汗毛。[/S2]

[S3] 我听出另一层了：隔离还有个好处——引擎最怕被打扰。服务端排队排到天际，引擎照样一拍一拍算，抖不到它。[/S3]

[S1] 那 v0 那套引擎代码，岂不是白写了？[/S1]

[S2] 这是最漂亮的地方：内核没废。同一套引擎核心，两种驱动。——离线批量，进程内直接驱动，代码里叫 InprocClient<break 300ms>。——线上服务，走 AsyncMPClient<break 300ms>，经 ZMQ 异步驱动。一套内核，两种开法。[/S2]

[S3] 我能不能这么理解：内核没换，换的是开法——一个进程内直连，同步；一个跨进程投递，异步？[/S3]

[S2] 准。对外这两个使用面也有名字：一个叫 LLM<break 300ms>，离线同步，拿起来直接调；一个叫 AsyncLLM<break 300ms>，服务异步，走跨进程那套。名字就写在脸上。[/S2]

[S3] 那我问个实际的。v0、v1 这个架构差异，面试要是问到，该答到什么程度？我刷面经，AI infra 的实习岗好像都在问这个。[/S3]

[S2] 是高频考点。牛客上一位面过这类实习岗的同学写过面经——{{voice:voice-002}}——他原话大意是：vLLM 相关问到了 PagedAttention<break 300ms>、连续批处理、v0/v1 架构。——还有 chunked prefill、prefix caching。最后补了句：SGLang 代码没怎么看，问的不多。[/S2]

[S1] 最后那句有味道：SGLang 没怎么看，照样过了——说明考点是「你懂不懂为什么这么设计」，不是背名词。刚才那一串名词，今天不用全记，后面几期一个个拆。[/S1]

[S1] 那回到 v1 内部。一条请求，到底怎么被拆成三段的？[/S1]

[S2] 从一个函数开始。代码中叫 add_request<break 300ms>——a-d-d 下划线 r-e-q-u-e-s-t，加请求。请求一进来，它同时扇出三条路。——第一条，输入处理，在本进程干。——第二条，引擎段，载荷跨进程投给独立进程。——第三条，输出处理，把引擎吐回的结果拆开分回去。[/S2]

[S3] 等等，「同时」走三条路？一个请求怎么能同时在三个地方？[/S3]

[S2] 好问题。展开来说。——请求还是那个请求，但它被登记在了两个进程里：本进程这边，建一份档案、建一个信箱；引擎进程那边，收到一份标准载荷。两边靠同一个请求编号对号。[/S2]

[S1] 一个请求，两边各记一份账？[/S1]

[S2] 对。而且你取结果那一侧，也就是 generate<break 300ms> 这个函数，全程只摸自己那个信箱。——引擎进程长什么样，它根本不关心。取的是消费者，投的是生产者，两边异步，谁也不等谁。[/S2]

[S3] 信箱这个词，能不能展开说说？我还不太懂，每个请求一个信箱是什么意思？[/S3]

[S2] 代码里这个类叫 RequestOutputCollector<break 300ms>——请求输出收集器。每个请求进门，先给你建一个专属小邮箱；引擎算完一批，后台任务把结果按编号投进对应邮箱；你的程序随时来取。[/S2]

[S3] 这不就是快递柜吗？你放进去，我随时取，不用跟快递员当面交接。[/S3]

[S2] 对，而且这个类比扛得住压。快递柜解决的是「不用干等」：generate<break 300ms> 只盯自己那个格子。引擎那边同时跑着几百个请求，跟你没关系。要是所有人共用一个队列，谁取慢了，后面全堵。[/S2]

[S1] 那投递员是谁？谁把结果放进柜子的？[/S1]

[S2] 一个叫 output_handler<break 300ms> 的后台任务——o-u-t-p-u-t 下划线 h-a-n-d-l-e-r。程序一启动它就在转：引擎每算完一批，它把混在一起的结果按请求编号拆开。挨个投进对应信箱。这个拆的活，行话叫解多路复用。[/S2]

[S1] 我来总结一下这段。——请求进门，一分为二：本进程建档案、建信箱，引擎进程收标准载荷；引擎算完，output_handler<break 300ms> 拆混装货、投信箱；generate<break 300ms> 只从信箱取。三段异步，靠编号对号。[/S1]

[S3] 我也复述一遍确认：你说的「同时」，其实是登记了三份——输入处理一份活，引擎一份活，信箱一份档案。对吧？[/S3]

[S2] 对，就是这个意思。[/S2]

[S1] 骨架有了。钻进第一段：输入处理，到底干了些啥？[/S1]

[S2] 简单来说。——把 CPU 的活全在门口干完，组装成标准载荷，才放它出门。具体四步：先验三道票，空请求、超长、字段越界，门口拦下；再归一化切字，自带编号的透传，没切的现场补；多模态输入展平排序；采样参数克隆补全。[/S2]

[S3] 四步记下了。但「标准载荷」到底是个啥？[/S3]

[S2] 代码中叫 EngineCoreRequest<break 300ms>——引擎核心请求。它是引擎进程唯一认的输入格式：校验过、切好字、参数补齐，全打在一个包里。引擎不认你的原始话，只认它。[/S2]

[S3] 可我还是没懂最关键的：切字为什么非得在门口干？挪到引擎那边切，不也一样吗？[/S3]

[S2] 不一样。引擎进程里住的是 GPU，它最怕等人。切字要是挪进去，GPU 每拍开饭前都得等 CPU 切完——每一拍都等，等于每一拍都在让利。在门口干完，两边彻底错开：你切你的，我算我的。[/S2]

[S1] 那个载荷的打包有讲究吗？不能直接扔个字典过去？[/S1]

[S2] 讲究大了。它用的是一种叫 msgspec<break 300ms> 的结构，专门为跨进程优化：数组直接透传不复制，没填的字段不打包，连垃圾回收都绕开。为啥？它天天跨进程。——哪怕一处只省一纳秒，乘以几亿次，都是真金白银。[/S2]

[S3] 门口那三道票也是这个思路吧——空请求、超长这种，本进程拦下，总比跨进程跑一趟再退货便宜。[/S3]

[S2] 对。你已经开始用这套思维想问题了。[/S2]

[S1] 好，载荷出门，过桥。桥那边长什么样？[/S1]

[S2] 桥是 ZMQ，一个跨进程通信的库。打包格式用的是 msgpack<break 300ms>。引擎进程那边，除了干活的主线程，还起两个守护线程管收发：一个专门收，接住消息、解包、扔进内部输入队列；一个专门发，从输出队列取、打包、发出去。[/S2]

[S3] 三个线程，两条队列。那主线程干嘛？[/S3]

[S2] 主线程就一件事：跑引擎核心的忙循环。从输入队列取请求、算一拍、把结果扔进输出队列，再取下一个。收发线程跟它只通过队列传话，谁也不直接打扰谁。[/S2]

[S1] 等等，为什么不让主线程顺手收发？多开两个线程，图什么？[/S1]

[S2] 图的是并行。收发都是 IO 活。主线程自己干，GPU 算到一半，就得停下等网络。拆出去之后：GPU 算这一拍的时候，收线程同时接新请求；GPU 算完，发线程已经把上一拍的结果送出门了。三个动作叠着走，谁也不等谁。[/S2]

[S3] 我能不能这么理解：后厨配了专门的传菜员，厨师只管炒菜，菜出锅往窗口一放就走人，传菜员负责端出去？[/S3]

[S2] 对，跟小饭馆是同一个体系——窗口就是队列，传菜员就是守护线程。[/S2]

[S3] 那收和发，用的是同一种通道吗？[/S3]

[S2] 两种。收的那头走的是叫 DEALER<break 300ms> 的套接字，发的那头叫 PUSH<break 300ms>。一个收，一个发，中间全靠那两条队列撑着。[/S2]

[S3] 一个负责接，一个负责倒，名字还挺形象。[/S3]

[S1] 消息里传的是什么？张量那么大，每次复制一遍？[/S1]

[S2] 这就是第二个心眼：多帧零拷贝。小张量直接内联进消息主帧，跟着走；大张量不复制内容，直接把内存地址传过去，走旁路；多模态张量更狠，走共享内存的带外通道。[/S2]

[S3] 「零拷贝」到底省了什么？不就省一次复制吗？[/S3]

[S2] 不止一次。就好比——搬家：小件塞纸箱随车走；大件家具要是装箱，得先搬上车、运到、再搬下来，三趟力气。零拷贝是直接把家具的存放位置交给对方，一趟不搬。大张量一拍几百兆，这笔账很硬。[/S2]

[S3] 那多大算大？分界线是多少字节？[/S3]

[S2] 问到我了。这个阈值的具体数值，书里没写死，我凭记忆说不准，不敢瞎编。[/S2]

[S1] 我也不知道。这个我们俩都没搞清楚——评论区有翻过代码的朋友，说说那条分界线画在哪。[/S1]

[S2] 但设计意图是清楚的：能省一次拷贝就省一次，越大的张量，搬运费越贵。[/S2]

[S1] 行，记账上。现在跳第三段：投递员那个活，凭什么说它不简单？[/S1]

[S2] 引擎一次算的是一整批——GPU 最擅长这个，一批塞得越满越划算。但回来的结果是混装的：几十个请求的 token 混在一起。接混装货的那个处理循环，代码中叫 process_outputs。——一条函数管整批。[/S2]

[S3] 一条函数管整批，它都干什么？[/S3]

[S2] 四件事：按请求编号查档案；增量拼字，把新 token 拼回文字，行话叫去 token 化；检测停止串，看这个请求该不该停；最后组装成结果，投进对应信箱。整批几十个请求，一个循环全过完。[/S2]

[S1] 一个循环管几十个请求，万一哪个请求吐得慢，不全卡死了？[/S1]

[S2] 有两道闸门。第一道节流：结果来得太密就攒一攒，按节奏发，省得每颗 token 都去戳用户一下。第二道归并：只发新增的部分，不重复发历史。所以取件那侧永远不卡。[/S2]

[S3] 那要是一个请求要三个候选答案呢？投三个信箱？[/S3]

[S2] 归拢着投。三个候选同属一个请求，循环里聚成一个父结果，投进那一个信箱。请求结束还有收尾：档案和信箱都清掉，不然堆一屋子死档案。[/S2]

[S1] 我捋一下第三段。——引擎吐混装货，process_outputs<break 300ms> 一个循环：查档案、拼字、判停、装结果、投信箱，外加节流、归并两道闸门。这就叫：一条函数管整批，一条队列喂一个流。[/S1]

[S2] 而且你注意到没有——拆货、拼字这些，又是 CPU 的活。又印证了那个设计：CPU 的活全在外面，GPU 只管算。[/S2]

[S1] 好，最后看第二段。被锁在独立进程里的那个引擎，它自己在里面干嘛？[/S1]

[S2] 跑一个忙循环，代码中叫 run_busy_loop<break 300ms>——r-u-n 下划线 b-u-s-y 下划线 l-o-o-p。从输入队列取请求，调一次 step<break 300ms>，结果扔进输出队列。再取下一个。不睡觉，一直转。它是引擎进程的心跳。[/S2]

[S3] 就这么简单？取一个、算一拍、扔出去？[/S3]

[S2] 循环简单，但每一拍里有四步。——第一步，调度：决定这一拍哪些请求上桌。——第二步，执行模型前向，代码中叫 execute_model<break 300ms>。——e-x-e-c-u-t-e 下划线 m-o-d-e-l。——GPU 真刀真枪算一遍。——第三步，采样，从算出的概率里挑一颗 token。——第四步，更新状态。四步合起来，叫引擎的一拍。[/S2]

[S1] 它算到一半，新请求来了怎么办？打断？[/S1]

[S2] 排队。新到的请求只进输入队列，绝不打断当前这一拍——GPU 前向一旦起跑，中途插不了队。撤销请求也一样，是消息，排队等这一拍跑完。引擎的原则就一条：正在算的这一拍，谁来了都不让。[/S2]

[S3] 那它怎么下班？一直转到地老天荒？[/S3]

[S2] 有状态机管着：正常跑、请求关停、正在关停三档，外加一个暂停。这个今天不展开。[/S2]

[S3] 那四步里的第一步「调度」，决定谁上桌——要是有人总轮不上呢？比如显存不够，块分不出来？[/S3]

[S2] 先补个名词：KV cache 是每颗 token 在显存里留的笔记，模型靠它接上下文。你问的「块分不出来怎么办」——怎么抢、把谁踢下去、踢下去的人进哪条专门的队等着回来，是一套单独的机制。连同显存一起，第三期专门拆。[/S2]

[S3] 等等，「块」又是什么？我随口说了个「块分不出来」，其实这词我还不知道。[/S3]

[S2] 笔记不是散着放的，按块住进显存。块，就是笔记的最小存放单位。具体一块多大、怎么分，第三期拆。[/S2]

[S1] 那这四步，今天讲到什么程度？[/S1]

[S2] 今天先记住一句话：每一拍，都可能决定一个请求被喂饱还是被饿死。这四步怎么排兵布阵，是下一期的题。还有第三步采样。——先交代 logits 这个词：就是模型给每个词打的分数。从打分到挑出那一颗 token——那条路比你想的长。咱们最后一期专门走。[/S2]

[S1] 好，骨架搭完，该算账了。账本翻开：两次跨进程通信、两个守护线程、两条队列、一个独立进程。我问个尖锐的——错在哪一段都不知道，调试怎么搞？这套是不是过度设计？[/S1]

[S3] 对，我一路听下来也想问：一个推理引擎，怎么会变得这么复杂的？[/S3]

[S2] 这个质疑真实存在，社区一直在吵。先把证据摆上桌。社区技术作者 Aleksa Gordic 写过一篇很出名的 vLLM 架构剖析——{{voice:voice-001}}。——他是这么剖的——这套结构从头过一遍：收请求的进程、引擎进程，数据并行时还要再挂一个协调进程。彼此靠 ZMQ 消息和共享内存传话。[/S2]

[S1] 他的结论是什么？[/S1]

[S2] 他原话大意是：这不是过度设计，是服务千万并发请求时，唯一经得起拷问的架构选型。但他也认账：进程边界一多，调试排错的复杂度跟着涨，绕不过去。对了，他那篇是快一年前的文章。这项目迭代快，细节得以现在的代码为准。[/S2]

[S1] 这是正方。反方呢？[/S1]

[S2] 反方最硬的证据是实测。先交代一句：SGLang 是另一个主流推理框架。今年六月，GPU 云服务商 Spheron 跑了组 vLLM 和 SGLang 的对比——{{voice:voice-036}}。——他的数据是：唯一 prompt 场景，两家只差 2% 到 4%，几乎打平。但在 80% 共享前缀、50 并发时。——SGLang 的 p50 首 token 延迟是 195 毫秒，vLLM 是 310 毫秒。——差了 37%。[/S2]

[S3] 打住，两个词。p50 是什么？首 token 延迟又是什么？[/S3]

[S2] p50 就是把所有请求的延迟排个队，站正中间那个——一半人比他快，一半人比他慢。首 token 延迟，是从你发请求到看见第一个字的时间。体验上，就是转圈转了多久。[/S2]

[S1] 2% 到 4% 打平——你看，SGLang 架构简单得多，性能差不多。那多出来的进程边界，图什么？[/S1]

[S2] 先别急。注意 37% 那个数的前提：80% 共享前缀。SGLang 赢在前缀索引是树状的，跨请求自动匹配。——vLLM 的自动前缀缓存要手动开，还只认平铺的前缀。多轮对话，每轮还得重算历史。这是前缀缓存的账，不是拆三段的账——拿它说三段式过度设计，打偏了。这笔账第三期细算。[/S2]

[S1] 我插一句：Spheron 是卖 GPU 云的，自己下场跑对比，有没有倾向性，大家心里留个秤。[/S1]

[S3] 说到对比，我之前还吃过一个瓜：同一个模型，SGLang 只吃 7 个 G 显存，vLLM 吃 21 个 G，三倍，当时吓跑一堆人。真的假的？[/S3]

[S2] 那事后来反转了。是 GitHub 上一个公开讨论帖——{{voice:voice-025}}——发帖的用户最初测出来确实是 7 对 21。后来查明白，是参数口径不对：SGLang 那个限制总 token 数的参数，跟 vLLM 限制最大长度的参数——根本不是一回事。两边对齐再测，显存占用基本相同。[/S2]

[S1] 合着 7 比 21 是乌龙。但这事反过来吓人：光凭一句「谁更省」，多少人已经准备迁移了——框架迁移的成本，被严重低估。[/S1]

[S3] 可这不还是避重就轻吗？人家质疑的是「解耦值不值」，你光校准秤干嘛？[/S3]

[S2] 校准秤是吵架的前提——单位没对齐，后面所有「谁快谁省」都是废纸。秤校完，再看值不值。有人真把每个设计拆开称过：一家技术媒体做了消融实验，把核心优化一个个摘掉、量性能损失——{{voice:voice-021}}。——可惜那篇全文我们没抓到，具体数字给不出。但「摘掉试试」这个思路，比吵架有用。[/S2]

[S1] 那「过度设计」这个罪名，到底成不成立？给硬证据。[/S1]

[S2] 看一条生产实测。技术博主 Marcus Chen，今年五月在自己线上系统抓的——{{voice:voice-027}}——他原话大意是：开了连续批处理之后，p50 延迟从 340 毫秒降到 190 毫秒。——但 p99 从 1.2 秒飙到 9.8 秒。——p99.9 呢，从 2.1 秒跳到 27 秒。[/S2]

[S3] 连续批处理是什么？还有，p99 涨成这样，根因查到了吗？[/S3]

[S2] 连续批处理，就是不等一批凑齐，每拍往正在跑的批里塞新请求。细节下一期讲。他查到的根因，出在一个叫 prefill 的步骤上——第一次把整段提示词喂给模型那一步。一次 60 毫秒的 prefill，让 23 个在飞的请求全部排队。GPU 利用率只有 81%，瓶颈不在算力，在调度。[/S2]

[S3] 等等——这不是连续批处理的坑吗？跟咱们三段式有什么关系？[/S3]

[S2] 问得准，他的 trace 确实是调度层的账。但道理是同一个：一个慢活堵在 GPU 前面，后面一整批全挨饿。三段式把切字、拼字这些 CPU 慢活从 GPU 眼前挪走，保的就是这条——GPU 前面，永远不许站人。[/S2]

[S1] 所以开场那俩字，跨两次桥，是在买保险？[/S1]

[S2] 对，买的是「GPU 永远不被 CPU 拖住」的保险。量级上差得远：一次跨进程通信，是微秒到毫秒级；GPU 空转，是上万个核同时闲着——那是它最贵的状态。三段式的本质不是拆开更好玩，是不等切字就把 GPU 喂饱。[/S2]

[S1] 你这话我得记下来：GPU 最贵的状态是空转。三段式买的，就是 GPU 的在岗时间。[/S1]

[S1] 最后给个判据。到底该不该拆？别说「看情况」。[/S1]

[S2] 判据就一条：你的并发量，有没有跨过单进程同步路径的 GPU 饥饿点。低于十个并发，同步更简单更快，拆了纯属找事；三位数并发往上，不解耦就等于让 GPU 天天空转等 CPU 的活。选架构之前，先想清楚你的负载落在哪个区间。[/S2]

[S3] 那我要是就十个以内的用户呢？这套架构白搭了？[/S3]

[S2] 不白搭。十个以内，同步路径更快更省事——v0 那套内核还在，进程内直连，就是给这种场景留的后门。三段式是给「并发会涨」买的保险：涨了，这钱花得值；没涨，先别花。[/S2]

[S1] 好，账算到这儿，开场那句话能验证了：一次「你好」，两趟跨进程，不是折腾——是服务一千个并发用户时，唯一能让 GPU 不等 CPU 的架构。[/S1]

[S3] 我笔记上落了一行：把 CPU 活和 GPU 活分家，让贵的设备不等人。——这思路，我不写推理引擎，写后端也用得上。[/S3]

[S2] 对，这套思路换哪个框架都成立。[/S2]

[S1] 但我还惦记着：那个被锁在独立进程里的引擎，咱们一整期都在它门口转悠，没进去。它里面那个忙循环，一拍四步，到底怎么排兵布阵？[/S1]

[S2] 下一期就把它拆开。一个忙循环，四步心跳——每一步，都可能决定一个请求是被喂饱，还是被饿死。[/S2]

[S1] 好，下期见。[/S1]
