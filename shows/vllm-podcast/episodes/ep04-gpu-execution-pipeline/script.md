# 一行 Python，一段录像：模型是怎么变成融合 kernel 的

[S1] 上期你留的钩子我还记得：一个写在 Python 里的模型层，最后变成一段录像里反复重播的融合内核，中间连 Python 解释器都不经过。我回去翻了翻我写的代码——attention 层不就一行 scaled dot product attention 吗？这一行，是怎么变成 GPU 上的内核的？[/S1]

[S2] 这就是这期的路。而且先扔个更刺激的：vLLM 自己用 Triton 写的 attention 后端，约 800 行代码，在 H100 长 decode 场景下，跑出了 FlashAttention 3 七万行 C++ 的 100.7% 性能。100.7，比百分百还多零点七。[/S2]

[S1] 等一下——800 行跑赢七万行？这数字你确定不是小数点放错了？[/S1]

[S2] 官方博客的实测，H100、长 decode，数字就这么给的。所以这期就两条线：一条是这行 Python 怎么变成录像，一条是录像重播要付什么钱。怎么做到的，代价是什么——听完你自己算这笔账。[/S2]

[S1] 行，两条线我都盯着。我先押一块钱：这条路走到一半，你准会说「这里其实是个补丁」。[/S1]

[S2] 你赢面不小——补丁确实不少。但每个补丁底下，都压着一个为什么。先还两笔账：上上期你卖过关子，说 execute_model 在 GPU worker 上怎么执行、CUDA graph、kernel 分派，水很深，先记个账；上期又把镜头推到 GPU 上。两笔账，今天一起还。[/S2]

[S1] 那从哪一笔开始？[/S1]

[S2] 从「指令怎么到 worker 手上」开始。你还记得心跳四步吧——调度、前向、采样、写回。第二步前向，引擎是发一条指令让 GPU worker 去干的。可这个 worker，是谁？[/S2]

[S1] 对，这正是我想问的：GPU worker 是哪来的？引擎不是住在独立进程里吗，隔着进程还能喊话？[/S1]

[S2] 能，靠执行器。引擎启动时，按一个配置字符串三选一：uni，单进程，worker 直接住在引擎进程里，最简对照；mp，多进程，引擎拉出一群 worker 子进程；ray，分布式集群。一个字符串，定生死。[/S2]

[S1] 一个字符串定生死？这也太省事了吧。[/S1]

[S2] 省事是设计出来的：所有执行器共用同一套接口，换后端只换工厂返回的那个类。mp 模式下，引擎拉出 N 个 worker 子进程，每个进程生下来，走一条固定的流程。[/S2]

[S1] 什么流程？入职培训？[/S1]

[S2] 差不多。先初始化 worker。这里有个讲究：进程出生时只占个位、记个名字，到这一步才真正实例化干活的那个类——叫延迟出生。然后初始化设备，搭分布式环境、构造模型运行器；然后装载模型权重；一切就绪，发一个 READY 信号；最后进忙循环，一条接一条接指令。[/S2]

[S1] 延迟出生……就是不养闲人，用到谁再叫谁起床？合着 worker 的出生是：占位、点名、装备、报到、上岗，五步走。那引擎那么多指令，怎么发给一群 worker？挨个点名？[/S1]

[S2] 点名是挨个，这儿是广播。引擎所有指令统一成一种调用，叫 collective_rpc——像开会喊一嗓子，一条消息同时发给所有 worker，全组同时开工。多进程的实现就是一条广播队列：发一次，大家都收到；回复也按发出的顺序收回，一一对应，不会串账。[/S2]

[S1] 开会喊一嗓子这个比喻我留着——为什么必须广播？因为张量并行下，每个 worker 各算各的那份切片，指令必须同时到，谁慢了谁拖全组。那散会呢？一群进程下班的时候怎么收场？[/S1]

[S2] 三级关停。第一级，优雅排空——让在跑的活先干完，不抢工期；第二级，发 SIGTERM，喊话请它走；第三级，SIGKILL，直接断电拖走。先礼后兵，每一级都是给前一级留的补救机会。[/S2]

[S1] 下班三步走：先等手里的活干完，再喊话请人走，最后保安清场。对了，worker 要是干着干着死了呢？没人管？[/S1]

[S2] 有人管。父进程起了一条监控：worker 死了，第一时间发现、上报——是方法抛了异常，还是进程整个没了，两条失败路径分开报，不会装没事继续等。行，worker 有了，指令也到了。那它拿到 execute_model，怎么干？[/S2]

[S1] 这个上上期讲过壳了：发起前向、结果装进临时包、单槽断言、回头再采样。今天拆壳里的活？[/S1]

[S2] 对。execute_model 阶段一其实先干三件事：调和持久批次的状态，把二维的批次拍扁成 GPU 吃的输入，装配注意力要的元数据。三件齐了，才发起模型前向——出手前先验明正身：盒子必须是空的，上一拍没取走，这一拍不许放。产出还是塞进那个盒子，一共十个字段。logits、隐藏状态、槽位映射，都在里面。函数立刻返回，CPU 不等结果，转头就去规划下一拍。[/S2]

[S1] 这三件事，每件都不是白干的吧？[/S1]

[S2] 都不是。调和状态，是拿调度器这拍发的变更单，对上 worker 手里的快照——谁来了、谁走了、谁挪了位，一次对齐；拍扁，是把「一行一个请求」的二维板子，收成一条一维的 token 序列；装配元数据，是告诉注意力：每颗 token 的笔记住在哪块显存里。这三件事做完，前向一发，CPU 这边就空了。[/S2]

[S1] 我捋一下 worker 这一拍：收到广播，先对账，再拍扁，再定位笔记，然后前向一发起就交差——CPU 不等 GPU，GPU 不等采样。那这个「前向」，就是整期的主角了吧。它到底怎么在 GPU 上跑起来的？[/S1]

[S2] 对，接下来四步，就是它内部的路：模型长什么样、算子怎么选实现、整张图怎么编译成录像、录像怎么放。第一步，模型长什么样。[/S2]

[S1] 我写的那个模型？不就是一堆层叠起来吗？[/S1]

[S2] 书里拿 Llama 当最简参考，四级嵌套。最外层是整个模型，带语言模型头；往里是模型主体；主体里叠着几十个解码层；每一层里俩子模块——注意力块和前馈块。拆开一层，里面还有一层，像俄罗斯套娃。[/S2]

[S1] 为啥非得套四层？不能一层套到底吗？我这人看代码就爱平铺，好找。[/S1]

[S2] 因为每一级都得能单独换：换语言模型头、换解码层数、换注意力实现——改一级，别的不用动。为了撑起这个，所有子模块的构造契约统一成两个参数：一个配置，一个名字前缀。前缀告诉每个模块它注册在哪、叫什么，所有模型共用这一套构造逻辑。[/S2]

[S1] 名字前缀……就是给每个模块发个门牌号？[/S1]

[S2] 对，还是登记制的：子模块自己拿前缀注册自己，父模块不用挨个记。这门牌号还不只是给代码看的——装载权重的时候，几百个张量对着户口本找家，不报家门全靠猜，猜错一个，推理结果全乱。[/S2]

[S1] 户口本都出来了……那再往里看，注意力块里的封装，也是登记在册的？[/S1]

[S2] 对，这是关键的一层：模型只管调「注意力」这个统一封装，背后到底是分页注意力、FlashAttention 还是 Triton 写的后端，模型一概不知道。[/S2]

[S1] 这不跟酒店标准间似的？客人只管住，水电是谁供的不用管。[/S1]

[S2] 就是这个意思。为啥要这样？后端多、模型更多，让每个模型去适配每个后端，组合就爆炸了。标准间一统，换供应商不动图纸——模型定义跟 GPU 执行，在这儿彻底解耦。[/S2]

[S1] 解耦是解耦了，可问题还在：模型里那些算子，归一化、注意力——它们写在 Python 里，在 GPU 上到底怎么跑？[/S1]

[S2] 答案是一种叫 CustomOp 的东西，自定义算子。核心设计：同一个算子备两套实现，构造的时候一次性选死，之后就不变。[/S2]

[S1] 两套？哪两套？快的那套和慢的那套？——不过你先说说，选的时候靠什么挑？总得有把尺子吧，不能闭着眼抓阄。[/S1]

[S2] 一套叫 forward_cuda，预编译好的融合内核——好几步算子合成一个 GPU 内核一次算完，省掉反复读写显存。另一套叫 forward_native，纯 torch 算子串出来的，每一步都是标准算子，编译器看得清清楚楚。构造时按当前硬件平台选一次，之后每次调用零开销转发，连个判断都不做。[/S2]

[S1] 这听着像预制菜和现炒：预制菜出餐快，但后厨看不见里面放了什么。[/S1]

[S2] 就是这个代价。拿归一化举例：现炒那套是几个纯 torch 算子一步一步算——算平方、算均值、开根号、归一化；预制那套是一次融合内核直接出结果。问题是——编译路径下，默认走的是现炒。[/S2]

[S1] 等等，不选快的选透明的？你这不是把最好的藏着吗？[/S1]

[S2] 不是藏，是分场景。编译器的活儿是看菜谱优化：预制菜是个黑箱，编译器不知道里面干了啥，就没法和周围的算子融在一起；现炒每一步都摆在桌面上，编译器才能通盘优化。所以规矩是：编译开着，走现炒；用户点名要那个算子，才切预制；压根没开编译，才用预制。[/S2]

[S1] 所以看着慢的那个，反而是编译路径的默认答案——这话反直觉，但我记住了。那整张图呢？总不会一个算子一个算子地选吧？[/S1]

[S2] 整张图，就是下一层故事：分片编译。模型类上挂一个装饰器，给它套上可编译的外壳：从函数注解里推断哪些维度是动态的，再注入一个连 guard 都不装的包装。普通编译每次调用前要核对输入没变样，对不上就重新编译；这里干脆把核对整个扔掉——要的就是固定形状。[/S2]

[S1] 等一下，形状检查都不要了？这不是自废武功吗——输入变了怎么办？[/S1]

[S2] 这就是它跟录像绑定的地方——你先记着这个扣，讲到录像就明白了。首次前向会触发一个自定义的编译后端，它干的第一件事：切图。[/S2]

[S1] 好好一张计算图，切它干嘛？[/S1]

[S2] 因为图里有两类活，能力不一样。默认的切点选在 attention 算子那儿——就是那个统一封装背后调用的自定义算子。一刀下去，attention 是一段，剩下的是另一段。[/S2]

[S1] 这切法有啥讲究？为啥偏偏在 attention 这儿切？[/S1]

[S2] 因为 attention 是特殊件：后端那么多，分页注意力、FlashAttention、Triton 各写各的，塞给编译器一起优化，特别容易翻车。所以策略是：普通段交给 Inductor 编译，就是线性层、归一化、残差这些规规矩矩的活，编完再包一层图捕获；attention 段保持原样，直接跑。[/S2]

[S1] 那 attention 段不编译，性能谁出？它可是整条链上最重的活。[/S1]

[S2] 它有自己的家底：分页注意力、FlashAttention、Triton，各家后端的融合内核早就备好了，录录像之前人家就是熟的。编译器帮不上忙，也就不用它帮——切在 attention，是把它当不用操心的熟手。[/S2]

[S1] 标准件走流水线，特殊件手工精做——装修队也是这么分工的。那切开的两段，数据怎么接上？[/S1]

[S2] 缝就是张量：段与段之间拿张量对接，前一段的输出就是后一段的输入。切的是图，断的不是数据。但编译不是免费的——首次前向冷启动，大模型可能上百秒，之后走缓存才快。这笔账先记下，后面争议要还。<break 300ms>[/S2]

[S1] 上百秒？那第一个用户不得等到花儿都谢了？先记着，一会儿跟你算。那编出来的图，怎么变成录像的？[/S1]

[S2] 图捕获。把一串 GPU 命令完整跑一遍，录下来——录的过程叫捕获，之后每拍原样放一遍，叫重播。为啥值得录？每步启动内核都有开销，算子越短越亏；录成录像，每拍省掉一整串启动开销——decode 阶段一拍几十个算子，省下来的全是赚的。[/S2]

[S1] 录像能随便放吗？不会放错场次吧？[/S1]

[S2] 不能，挑观众。录像的形状是定死的：录的时候什么样，放的时候必须什么样，连显存地址都得一致。所以每拍放之前，得拿这一拍的形状去查录像库。[/S2]

[S1] 查库……按什么查？[/S1]

[S2] 一个叫批次描述符的东西：token 数、这一拍是不是清一色的 decode、有没有挂 LoRA——三样拼成一把钥匙。三级分派：第一级 FULL，完整录像，要求请求数精确匹配——录过一版 32 个请求的，这拍正好 32 个，完美命中，直接放。[/S2]

[S1] 那要是这拍 21 个请求，对不上 32 人的录像，怎么办？慢点就慢点？[/S1]

[S2] 中间还有一级 PIECEWISE，分段录像，要求宽松——请求数不要求精确对上，形状差不多就放。再不行，或者超过捕获上限，回退第三级 NONE：不放了，逐算子老实跑一遍。慢是慢，但正确——录像是个优化，不是个保证。[/S2]

[S1] 那能不能多录几版？32 人的、16 人的、8 人的，各录一版，按需放，不就不空转了？[/S1]

[S2] 多录一版，就多占一份固定显存和编译成本——录多了，显存先不答应。所以才有那个捕获上限：超了干脆不录，回退成逐算子老实跑。分级取舍，取舍的其实是显存和灵活。[/S2]

[S1] 有录像放录像，没录像现场演。这个「地址必须一致」我倒是见过——CSDN 上有人整理过一套 vLLM 面试题，有这么几道题，是这么问的。<break 200ms>{{voice:voice-015}}128K 上下文模型怎么分配显存？怎么平衡显存利用率和 OOM 风险？还有，CUDA graph 在捕获和重播期间，为什么要保证所有内存地址一致？——原话大概这个意思。[/S1]

[S2] 最后那道我现在就能答：录像里记的是地址。地址变了，放出来的就不是录的那场戏了——所以捕获时占的显存，重播时必须还在原位。这也是它跟「块表」那套内存设计绑在一起的原因：显存分配必须稳定，录像才放得稳。[/S2]

[S1] 那我算听明白了。但录像还有个隐蔽的代价吧？固定形状，是不是意味着放的时候不能变？[/S1]

[S2] 你抓到了。录像放起来快，但不能换台：固定网格的意思是，哪怕这一拍实际工作量变小了，录像还是按录的时候的最大配置启动，多余的部分空转浪费。这就是开头那个 100.7% 故事的另一半账——800 行很快，空转也实打实。<break 400ms>[/S2]

[S1] 空转我记下了。那这个固定形状，是不是还连累了一处地方？上期那个 Triton 内核——你说它是几十个自定义算子里的一个，也是最后一公里那个。[/S1]

[S2] 对，你记得真准。上期讲了公式：块号乘块大小，加块内偏移，物理槽位就出来了。今天补上那个「为什么」：这一行算出的槽位是要喂进录像里的，录像形状定死，每个位置都得有人站岗——请求没填满的行，尾巴拿一个占位符补齐，叫 PAD_SLOT_ID。[/S2]

[S1] 等一下你刚才那句我没跟上——PAD 占位符，就是给空位派个假地址，专门站岗用？[/S1]

[S2] 对，不指向任何真块，纯站岗。内核的网格固定，行不满也得站满。这内核本身是 Triton 写的，每个程序处理一个请求，一批请求一起算；块表在 CPU 和 GPU 各有一份镜像，改了先改 CPU 那份，攒够了一次性批量拷过去——上期讲过这对镜像的来龙去脉，今天它被录像绑得更紧了。[/S2]

[S1] 双镜像我捋一下：CPU 那份管记账，GPU 那份管干活，攒一批再同步。那这张表，就是阶段一「准备输入」那步干的事吧？[/S1]

[S2] 对，你串起来了。现在回头看就明白，两笔账为什么是一笔：阶段一里准备输入这步启动这个内核，算出每个 token 的槽位，装进注意力元数据。然后前向在录像里重播，logits 装进临时包，sample_tokens 解开采样，新 token 写回批次。从模型定义到 GPU 上的录像，一整个闭环。[/S2]

[S1] 那这条链就算收束了：上上期欠的 execute_model，上期欠的 Triton 内核，今天一笔还清。但我算总账的时候总觉得不对劲：又是编译又是录像，冷启动上百秒、guard 都扔了、空转也认了——这套东西真的免费吗？[/S1]

[S2] 不免费，这正是这期的争议。先摆债。GitHub 上一位社区成员专门测过 Inductor 分区方案。他是这么说的——{{voice:voice-012}}Inductor 分区方案带来 2-10% 的性能提升，但冷启动编译时间增加 2-5 倍，实测大模型冷启动编译可达 100 秒；还得靠大量 monkeypatch 和 workaround，attention 加量化的融合在 Blackwell 上甚至出现倒退——这是他的原话。[/S2]

[S1] 提升个位数，编译贵好几倍，还倒贴一堆补丁？那我先问个具体的：Blackwell 上为啥反而倒退？[/S1]

[S2] 这个我们也没搞清楚——issue 里给了复现、给了现象，根因还在查，社区没有定论。评论区有懂的，说说你的分析。而且后来的走向是：社区干脆默认不启用这个分区方案，改用优化级别分层——你自己品品，编译这条路，vLLM 自己都在打退堂鼓。[/S2]

[S1] 行，这个锅先留给社区。那回到最初的问题：这编译到底值不值？别含糊。[/S1]
