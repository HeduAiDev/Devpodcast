# 一行 Python，一段录像：模型是怎么变成融合内核的

[S1] 大家好，我是老张，欢迎回来。上期收尾，阿哲押了个题——块表那期反复提到的「固定网格」，他猜跟一个叫 CUDA graph 的录像机制有关。今天开盅。还是老两位：阿凯，这本书的作者，AI infra 一线老兵；阿哲，传统后端程序员，替你们读者来的。[/S1]

[S2] 大家好。先给阿哲开奖——押对了。这期就讲这个：你写在 Python 里的模型，怎么变成 GPU 上一段反复重播的录像，中间连 Python 解释器都不经过。[/S2]

[S3] 我是阿哲。这期我自带立场：我写过 PyTorch，我就想知道，我那一行注意力调用，到了 GPU 上到底经历了什么。谁敢快进，我喊停。[/S3]

[S1] 那就从那一行说起。我回去真翻了我写的模型——注意力层，不就一行调用吗？名字还老长，什么 scaled dot product attention。这一行，怎么就变成 GPU 上的内核了？[/S1]

[S2] 这就是这期的路。先扔个更刺激的：vLLM 官方拿 Triton 写了个注意力后端，大约 800 行代码，在 H100 上跑出了 FlashAttention 3 七万行 C++ 的 100.7% 性能——比百分之百还多零点七。[/S2]

[S3] 等等——800 行跑赢七万行？阿凯，这数你确定没念错？[/S3]

[S2] 官方博客的实测，H100、长 decode 场景，数字就这么给的。所以这期两条线：一行 Python 怎么变成录像；录像重播要付什么钱。怎么做到的、代价是什么，听完你自己算账。[/S2]

[S1] 行。那从哪头开始？[/S1]

[S2] 从「指令怎么到 GPU 手上」开始。还记得心跳四步吧——调度、前向、采样、写回。第二步前向，是引擎发一条指令，让 GPU worker 去干的。可这个 worker，是谁？[/S2]

[S1] 对，我正想问：引擎不是锁在独立进程里吗？隔着进程，怎么指挥 GPU？[/S1]

[S2] 靠执行器。引擎启动时，按一个配置字符串三选一：uni，单进程，worker 直接住引擎进程里；mp，多进程，引擎拉出一群 worker 子进程；ray，分布式集群。一个字符串，定生死。[/S2]

[S3] 停一下——一个字符串定生死？这也太随便了，写错一个字母呢？[/S3]

[S2] 写错了启动直接报错，不会默默跑歪。省事是设计出来的：所有执行器共用同一套接口，换后端只换工厂返回的那个类，引擎本体一行不动。[/S2]

[S1] 那多进程模式下，这群 worker 子进程，生下来就干活？[/S1]

[S2] 有一条固定流程。第一步初始化 worker——这里有个讲究：进程出生时只占个位、记个名字，到这一步才真正实例化干活的类，书里叫延迟出生。然后初始化设备，搭分布式环境、构造模型运行器；再装载模型权重；一切就绪，发个 READY 信号；最后进忙循环，一条接一条收指令。[/S2]

[S3] 等等，我捋一下——出生先占位，再装备，再报到，再上岗？为啥不出生时直接装备齐全？[/S3]

[S2] 不养闲人。子进程起来得早，干活的类到用的时候才实例化——用到谁，再叫谁起床。[/S2]

[S3] 延迟出生……是不是就我们写单例懒加载一个意思？构造函数里只登记、不干活？[/S3]

[S2] 对，一个意思——只是这儿懒的，是一整个干活的类。[/S2]

[S1] 那指令呢？引擎那么多指令，发给一群 worker，挨个点名？[/S1]

[S2] 广播。引擎把所有指令统一成一种调用，代码里叫 collective rpc——c-o-l-l-e-c-t-i-v-e，下划线，r-p-c。你就当开会喊一嗓子：一条消息同时发给所有 worker，全组同时开工。[/S2]

[S3] 为啥非得同时？一个先跑、一个后跑不行吗？[/S3]

[S2] 不行。张量并行下——大模型切成几片、几张卡各算一片——同一步计算，谁慢了谁拖全组。所以多进程的实现是一条广播队列：发一次大家都收到；回复按发出顺序一个个收回来，一一对应，不串账。[/S2]

[S3] 回复为啥非得按顺序收？谁先算完谁先回，不更快？[/S3]

[S2] 底下队列就是先进先出——答卷按发出顺序到，就按发出顺序收。真要谁先回先收谁，反而得额外记谁是谁。[/S2]

[S1] 那下班呢？一群进程，怎么收场？[/S1]

[S2] 三级关停。第一级优雅排空，在跑的活先干完；第二级发 SIGTERM，喊话请它走；第三级 SIGKILL，直接断电拖走。先礼后兵，每级都是给前一级留的补救机会。[/S2]

[S1] 先礼后兵，这个我记下了。那 worker 要是干着干着自己死了呢？没人管？[/S1]

[S3] 对啊。还有 SIGTERM、SIGKILL 这俩——Linux 信号嘛，这个我熟：十五号请你走，九号要你命。[/S3]

[S2] 死不了没人管的。父进程有监控盯着：是方法抛了异常、还是进程整个没了，两条失败路径分开上报——不装没事，也不傻等。[/S2]

[S1] 让我来捋一下 worker 这段：执行器一个字符串三选一；worker 延迟出生，占位、装备、报到、上岗；指令靠 collective rpc<break 300ms>广播，一嗓子全组同时开工；下班三级关停，先礼后兵。对吧？[/S1]

[S2] 对，全对。[/S2]

[S1] 那 worker 收到前向指令，就轮到上上期那笔账了——execute model<break 300ms>当时只讲到「把活发下去」。发下去之后呢？[/S1]

[S2] 今天还。worker 接到指令，先干三件事。第一件对账——拿调度器这拍的变更单，跟手里快照对齐，上期细讲过。第二件拍扁——把「一行一个请求」的二维批次，收成一条一维的 token 序列。第三件装配——告诉注意力，每颗 token 的笔记住在哪块显存。[/S2]

[S3] 停，第三件——告诉注意力笔记住哪，这不是上期块表的活吗？[/S3]

[S2] 就是块表那套，后半场拆到底，先挂个号。三件事齐了，才发起前向——发起之前再验明正身：那个十个字段的盒子必须是空的，上上期立过的规矩。[/S2]

[S3] 等等，返回空——GPU 还在那儿算着呢，CPU 就甩手了？[/S3]

[S2] 甩手去干正事：规划下一拍。这就是两阶段解耦的全部理由——GPU 算前向的工夫，CPU 把下一拍先想好，谁也不等谁。[/S2]

[S1] 盒子、断言、返回空，上上期都讲过，不重复。我关心新的：前向发出去，GPU 上到底怎么跑？[/S1]

[S2] 这就是今天的主角。接下来四步：模型长什么样、算子怎么选实现、整张图怎么编成录像、录像怎么放。第一步，模型长什么样。[/S2]

[S1] 我写的那个模型？不就一堆层叠起来吗？[/S1]

[S2] 书里拿 Llama 当最简参考，四级嵌套。最外层是整个模型，带语言模型头；往里是模型主体；主体里叠着几十个解码层；每个解码层里俩子模块——一个注意力块，一个前馈块。拆开一层里面还有一层，俄罗斯套娃。[/S2]

[S3] 为啥非得套四层？我写代码就爱平铺，一层到底多好找。[/S3]

[S2] 因为每一级都得能单独换：换语言模型头、换解码层数、换注意力实现——改一级，别的不用动。平铺是省事，改一处动全身。[/S2]

[S1] 那几百个模块，构造的时候谁跟谁对得上？[/S1]

[S2] 靠一份统一的构造契约：所有子模块，构造参数就俩——一个配置，一个名字前缀。前缀告诉每个模块它注册在哪、叫什么，所有模型共用这一套。[/S2]

[S3] 名字前缀……我能不能这么理解：给每个模块发个门牌号？那这门牌号，谁编的？[/S3]

[S2] 构造时一层层传下来的——外层传门牌，内层接自己的名字，登记制，子模块自己注册自己，父模块不用挨个记。这门牌号还不只是给代码看的——装载权重时，几百个张量对着户口本找家；不报家门全靠猜，猜错一个，推理结果全乱。[/S2]

[S1] 你这话我得记下来——前缀不是装饰，是权重装载的对账依据。那注意力块里呢？也登记在册？[/S1]

[S2] 登，而且这是关键一层：模型只管调「注意力」这个统一封装。背后是分页注意力、FlashAttention，还是 Triton 写的后端——模型一概不知道。[/S2]

[S3] 一概不知道？那它该调哪个后端，谁定？[/S3]

[S2] 不用它定。就好比酒店标准间：客人只管住，水电谁供的不用管。后端多、模型更多，让每个模型去适配每个后端，组合就爆炸了。标准间一统，换供应商不动图纸——模型定义跟 GPU 执行，就在这儿解耦。[/S2]

[S3] 我复述：四级套娃，为了每级能单独换；构造契约俩参数，前缀是门牌号、登记制，权重装载靠它对户口；注意力是标准间，模型对后端无感。全对我就过。[/S3]

[S2] 一字不差。[/S2]

[S1] 解耦是解耦了。可那些算子——归一化、注意力——写在 Python 里，到了 GPU 上到底怎么跑？[/S1]

[S2] 靠一个叫 Custom Op 的东西，自定义算子。简单来说——同一个算子，备两套实现，构造的时候一次性选死，之后不变。[/S2]

[S3] 两套？快的那套和慢的那套？[/S3]

[S2] 一套叫 forward cuda——f-o-r-w-a-r-d，下划线，c-u-d-a——预编译好的融合内核：好几步算子合成一个 GPU 内核一次算完，省掉反复读写显存。<break 300ms>另一套叫 forward native——下划线，n-a-t-i-v-e——纯 torch 算子串出来的，每一步都是标准算子，编译器看得清清楚楚。[/S2]

[S1] 选的时候靠什么挑？总得有个尺子，不能闭着眼抓阄。[/S1]

[S2] 看当前硬件平台，构造时选一次。之后每次调用零开销转发——连个判断都不做，选完就定死。[/S2]

[S3] 我能不能这么理解——预制菜和现炒：预制菜出餐快，可后厨看不见里面放了啥；现炒每一步都摆台面上。对吧？[/S3]

[S2] 你这比喻能承重。拿归一化举例，代码里叫 RMS Norm。现炒那套，几个纯 torch 算子一步一步来：算平方、算均值、开根号、归一化；预制那套，一次融合内核直接出结果。[/S2]

[S1] 那按性能选，肯定预制菜啊。[/S1]

[S2] 偏偏不是。编译路径下，默认走的是现炒。[/S2]

[S3] 啊？不选快的，选透明的？这不是把最好的藏着吗？[/S3]

[S2] 不是藏，是分场景。展开来说——编译器的活，是看菜谱做优化：预制菜是个黑箱，它不知道里面干了啥，就没法跟周围的算子融在一起；现炒每一步摆在桌面上，它才能通盘优化。所以规矩是：编译开着，走现炒；用户点名要某个算子的融合版，才切预制；压根没开编译，才用预制。[/S2]

[S1] 让我来捋一下——看着慢的那个，反而是编译路径的默认答案，因为编译器要看见全过程才能优化。这话反直觉，但我记下了。[/S1]

[S3] 我补一刀：零开销转发，就是调用时连判断都不走、直接跳选好的那套；所以「选死」不是选最快的，是选最适合这条路径的。对吧？[/S3]

[S2] 对。[/S2]

[S1] 那整张图呢？一个算子一个算子选完，整模型的计算图怎么编？[/S1]

[S2] 这就是分片编译。模型类上挂一个装饰器，给它套上可编译的外壳：从函数注解里推断哪些维度是动态的，再注入一个连 guard 都不装的包装。[/S2]

[S3] guard 是啥？这词我没跟上。[/S3]

[S2] 形状核对。普通编译每次调用前，先核对输入形状没变样，对不上就重新编译。这个包装把核对整个扔掉——要的就是固定形状。[/S2]

[S3] 等等，形状检查都不要了？输入变了咋办？这不是自废武功吗？[/S3]

[S2] 好问题。——这正是它跟录像绑定的地方，先记着这个扣，讲到录像就明白了。[/S2]

[S1] 外壳套上之后，第一次跑会发生啥？[/S1]

[S2] 首次前向，触发一个 vLLM 自己的编译后端。它干的第一件事：切图。代码里叫 split graph——s-p-l-i-t，下划线，g-r-a-p-h。默认切点选在注意力算子那儿——一刀下去，注意力一段，剩下的一段。[/S2]

[S1] 好好一张图，切它干嘛？[/S1]

[S2] 图里两类活，能力不一样。注意力是特殊件：后端那么多，各家写各的，塞给编译器一起优化特别容易翻车。所以策略是——普通段交给 Inductor 编译。Inductor 就是 torch.compile 的编译后端，专门把算子图变成高效机器码；编完再包一层图捕获。注意力段保持原样，直接跑。[/S2]

[S3] 停一下——注意力段不编译，性能谁出？它不是整条链上最重的活吗？[/S3]

[S2] 它有自己的家底。分页注意力、FlashAttention、Triton，各家后端的融合内核早就备好了——录录像之前，人家就是熟的。编译器帮不上忙，也就不用它帮。切在注意力，是把它当不用操心的熟手。[/S2]

[S1] 标准件走流水线，特殊件手工精做——装修队也是这么分工的。切开的两段，数据怎么接上？[/S1]

[S2] 缝就是张量：前一段的输出，就是后一段的输入。切的是图，断的不是数据。之后每次前向走缓存，不再触发编译。但编译不是免费的——首次前向冷启动，大模型可能上百秒。这笔账先记下，后面争议要还。[/S2]

[S1] 等等，上百秒？那第一个用户不得等到花儿都谢了？[/S1]

[S3] 就是……先记着吧。我复述这段：装饰器套壳，形状核对扔掉；首次前向触发自家后端，在注意力处切图；普通段编译加图捕获，注意力段直接跑；之后走缓存。过？[/S3]

[S2] 过。[/S2]

[S1] 好，到录像了。图捕获到底录的是什么？[/S1]

[S2] 我来说说这东西怎么来的。每步启动内核都有开销，算子越短越亏。所以把一串 GPU 命令完整跑一遍，录下来——录的过程叫捕获，之后每拍原样放一遍，叫重播。录成录像，每拍省掉一整串启动开销。decode 一拍几十个算子，省下来的全是赚的。[/S2]

[S3] 录像能随便放吗？不会放错场次吧？[/S3]

[S2] 不能，挑观众。录像的形状是定死的：录的时候什么样，放的时候必须什么样——连显存地址都得一致。所以每拍放之前，得拿这拍的形状去查录像库。[/S2]

[S1] 地址还得一致——巧了，阿哲前两天给我看了一套面试题，CSDN 上有博主整理的，里头正好考到这条。是这么问的——{{voice:voice-015}}128K 上下文的模型怎么分配显存？怎么平衡显存利用率和爆显存的风险？CUDA graph 在捕获和重播期间，为什么要保证所有内存地址一致？——原话大概这个意思。[/S1]

[S2] 最后那道我现在就能答：录像里记的是地址。地址变了，放出来的就不是录的那场戏了——捕获时占的显存，重播时必须还在原位。这也是它跟块表那套绑在一起的原因：显存分配必须稳，录像才放得稳。[/S2]

[S3] 等等，那是真面试还是题集？别拿真题吓唬我。[/S3]

[S1] 题集，博主汇总整理的，不是哪家现场。但能进题集，说明这条已经是考点清单上的常客。[/S1]

[S2] 那查库按什么查？一个叫批次描述符的东西，三样拼一把钥匙：token 数、这一拍是不是清一色的 decode、有没有挂 LoRA。[/S2]

[S3] LoRA 又是啥？[/S3]

[S2] 一种外挂的微调插件，给模型别个小补丁。这期不展开——你只记一条：挂没挂，计算形状不一样，所以钥匙上得有它。[/S2]

[S1] 钥匙有了，锁怎么开？[/S1]

[S2] 三级分派。第一级，完整录像——要求请求数精确匹配：录过一版 32 个请求的，这拍正好 32 个，完美命中，直接放。[/S2]

[S1] 那这拍 21 个请求，对不上 32 人的录像呢？[/S1]

[S2] 中间还有一级，分段录像，要求宽松——请求数不精确对，形状差不多就放。再不行，或者这批太大、超过捕获上限，回退第三级：不放了，逐算子老实跑一遍。慢是慢，但正确——录像是个优化，不是个保证。[/S2]

[S3] 那能不能多录几版？32 人的、16 人的、8 人的各录一版，按需放，不就都有得放了？[/S3]

[S2] 多录一版，就多占一份固定显存和编译成本——录多了，显存先不答应。所以才有那个捕获上限：超了干脆不录。分级取舍，取舍的其实是显存和灵活。[/S2]

[S3] 等等，那 decode 拍到后头，请求一个个完成，批越跑越小——套着最大配置的录像放，不就越放越亏？[/S3]

[S2] 问到点子上了，这是录像最隐蔽的代价：空转。放的时候，内核按录的时候的最大配置启动——这拍实际工作量小了，多余的部分照跑。所以分级才存在：完整的对不上换分段的，分段也亏得离谱，就回退老实跑。亏与不亏，是拿空转跟启动开销比出来的。[/S2]

[S3] 那我追问一个：decode 形状稳，好录；prefill 呢？每个请求 prompt 长短都不一样，形状每拍都变——prefill 是不是根本吃不到录像红利？[/S3]

[S2] 你问到这期最大的一笔余账了。对——prefill 形状多变，常常对不上录像，只能回退逐算子老实跑。这里头水有多深，先挂账，下期连本带利还你。[/S2]

[S1] 我来总结一下录像这段：捕获一次、重播省钱；形状、地址都得一致；三样拼钥匙查库，完整的精确匹配、分段的宽松兜底、都不行就老实跑；代价是空转，外加 prefill 那笔挂账。——账记完，该还上期那笔了：「固定网格」跟块表，到底什么关系？[/S1]

[S2] 关系大了。上期讲过公式：块号乘块大小，加块内偏移，物理槽位就出来了。今天补上为什么：这行算出的槽位，是要喂进录像的——录像形状定死，每个位置都得有人站岗。请求没填满的行，尾巴拿占位符补齐——不指向任何真块，纯站岗。[/S2]

[S3] 所以我押对了：块表尾巴上那些占位符，就是给录像的固定形状站岗的。[/S3]

[S2] 对。这个内核本身也值得两句：Triton 写的，每个程序处理一个请求，一批请求一起算；块表还是那对双镜像——CPU 记账、GPU 干活，攒够了一次性批量拷过去。上期那对镜像，今天被录像绑得更紧了。[/S2]

[S3] 双镜像我再钉一遍：CPU 管记账，GPU 管干活，中间攒一批再同步——上期学过，今天它伺候的对象多了个录像。[/S3]

[S1] 那这个内核，在整条链里站哪一环？[/S1]

[S2] 就是阶段一「装配」那步：启动它，算出每颗 token 的槽位，装进注意力的元数据。然后前向在录像里重播，logits 装进盒子，sample tokens<break 300ms>解开采样，新 token 写回批次——从模型定义到 GPU 上的录像，整个闭环。[/S2]

[S3] 我就纳闷——一个算槽位的内核，又是双镜像又是占位符，作者的思路是什么，怎么会变得这么复杂？[/S3]

[S2] 每一处都是被录像的固定形状逼的——占位符伺候网格，双镜像伺候每拍同步。不是没人想过简单方案，是跑不动。[/S2]

[S3] 行。我复述闭环：块表双镜像，Triton 内核按公式算槽位，占位符给固定网格站岗；槽位装进元数据，前向进录像，出来装盒、采样、写回。今天两笔账一起还清：execute model<break 300ms>这笔是上上期的，块表这笔是上期的。过？[/S3]

[S2] 过。[/S2]

[S1] 账是还清了，可我算总账总觉得不对劲：又是编译又是录像，冷启动上百秒、形状核对扔了、空转也认了——这套东西，真像你说得那么值吗？[/S1]

[S2] 不全是，这正是这期的争议。先摆债。GitHub 上有位社区成员专门开过 issue，测的就是这套编译分区方案。他是这么说的——{{voice:voice-012}}这方案带来 2% 到 10% 的性能提升，但冷启动编译时间增加 2 到 5 倍，实测大模型冷启动编译可达 100 秒。还得靠大量猴子补丁和绕行手段，注意力加量化的融合，在新一代 Blackwell 显卡上甚至出现倒退——大意就是这样。[/S2]

[S3] 提升个位数，编译贵好几倍，还倒贴补丁？——先问个具体的：Blackwell 上为啥反而倒退？[/S3]

[S2] 这个我们也没搞清楚。issue 里给了现象、给了复现，根因社区还没定论。评论区有懂的，说说你的分析。[/S2]

[S1] 行，这题挂起来，评论区见。那这套方案后来什么走向？[/S1]

[S2] 后来社区干脆默认不启用这个分区方案，改用优化级别分层——想激进，自己往上开。你品品：编译这条路，vLLM 自己都在打退堂鼓。[/S2]

[S3] 等等，「猴子补丁」是啥？刚才那串里就这个词我不认识。[/S3]

[S2] 不改源码，运行时从外边硬塞一段替换实现进去——能跑，但脆。一个正经框架要靠一堆这个才能编译，本身就说明这套编译还没成熟。[/S2]

[S1] 债还没完吧？[/S1]

[S2] 没完，还有一笔更底层的。官方论坛上有场讨论，有人问：分片编译里，为什么不能用原地归约？——就是算完直接写回原内存，省一份拷贝。答话的大意是——{{voice:voice-013}}编译路径下的自定义算子，不能安全支持原地修改：原地改会破坏计算图的假设和别名分析，编译器没法可靠推断张量的生命周期——基本就是这个意思。[/S2]

[S3] 别名分析……你先别甩术语，给个直觉：为啥原地改就不行？[/S3]

[S2] 直觉是：编译器要记账——这张纸谁在用、什么时候用完。原地改，等于有人偷偷在账本上涂改，账就乱了。所以有些优化不是不想做，是编译器这道天花板，vLLM 绕不过去。[/S2]

[S1] 债摆完了：编译贵、补丁多、新卡倒退、天花板压顶。那说好的 800 行跑赢七万行呢？这笔账怎么算？[/S1]

[S2] 算给你看。官方博客发过这个后端的实测，原话是——{{voice:voice-031}}Triton 注意力后端，在 H100 长 decode 场景下，达到了 FlashAttention 3 的 100.7% 性能，只用了约 800 行代码；而 FlashAttention 3，约七万行——就这组数。[/S2]

[S1] 800 对七万——这对比我从开场记到现在，等的就是这笔账。[/S1]

[S2] 账要算两头。100.7% 有前提：H100、长 decode，换个场景数字未必是这个；空转的代价，前面也认了。但维护成本是结构性的——下一张新显卡出来，调 800 行 Triton，跟重写七万行 C++，工程代价不在一个量级。Custom Op 的两级 dispatch，就是为这留的后门：新硬件上编译翻车了，退回纯 torch，让编译器自己发挥。[/S2]

[S3] 那判据到底是啥？你不能两头都占——又快又稳的好事，轮不到咱。[/S3]

[S2] 判据不是「编译优化跑得快不快」，是「跨显卡架构的表现一不一致」。Inductor 在 H100 上可行、在 Blackwell 上倒退——说明编译优化还没到「一行代码吃所有卡」的程度。两级 dispatch 这个开关，就是为这种不确定性留的。[/S2]

[S1] 所以本质是：编译在赌架构，Custom Op 在留退路？[/S1]

[S2] 对。赌得起就编，赌不起退回纯 torch，让编译器跟新硬件慢慢磨。开关交你手上，不替你赌。[/S2]

[S3] 我一开始还纳闷，怎么会搞得这么复杂——现在通了：每一层都是在给硬件的不确定性留退路。这句我记本上了。[/S3]

[S1] 行，判据立住了。那这套手艺值钱吗？我听说现在面试都到手写内核的份上了。[/S1]

[S2] 值钱，还在涨。牛客上有位面过 AI Infra 实习的同学写过面经，他是这么写的——{{voice:voice-014}}推理方向的实习面试，手撕代码不是 LeetCode，是 Triton 和 CUDA：归一化前向、大矩阵规约求和、在线 Softmax——大意就是这样。[/S2]

[S3] 手撕 Triton？就是今天说的那个、拿 Python 语法写 GPU 内核的框架？面试现场写这个？[/S3]

[S2] 就它。一家面试备考平台对今年 coding 环节的预判，写得更全——{{voice:voice-032}}可能是：实现一个小型注意力内核；一个带优先级和抢占的请求调度器；一个可变大小 KV cache 的内存分配器。资深岗位要求能读或写 Triton、CUDA 片段——不是加分项，是基本功——这是他们的原话。[/S2]

[S1] 从加分项到基本功……不过话说回来，这是备考平台的整理，不是哪家的一手面经——当个市场信号看。[/S1]

[S2] 对，信号看方向：能在一张卡上跑不算本事，在所有卡上都别翻车，才是这门手艺的价——跟刚才的判据，同一条。[/S2]
