# 你省的不是 token，是物理块：一块显存的一生

[S1] 大家好，我是老张，欢迎回来。上期我们把引擎的一拍拆到了骨头——调度定人、前向算分、采样选词、写回记账。但结尾欠了一笔账：这一拍能转起来，前提是那块显存管得明白。今天还账。还是老两位：阿凯，这本书的作者，AI infra 一线老兵；阿哲，传统后端程序员，替你们读者来的。[/S1]

[S2] 大家好。这期全程就盯一样东西：一块显存，从生到死。我尽量讲慢点，你们俩随时掐我。[/S2]

[S3] 我是阿哲。上期结束我放了个话——显存不是被模型吃光的，是被笔记吃光的。今天我来对答案，顺带替读者拍桌子。[/S3]

[S1] 赌局待会儿开盅。我先念一道面试题，前两天看到的，差点被绕进去。——面试官问：你给 vLLM 加了 KV cache 压缩，淘汰了 90% 的不重要 token，重启服务，显存几乎没降，同样的长度照样爆显存。为什么？[/S1]

[S2] 这题我第一次看到也愣了一秒。腾讯云开发者社区有篇解析专门拆它，是这么说的——{{voice:voice-029}}答案不在于淘汰了多少 token，而在于释放了多少个完整的物理块。PagedAttention 的块大小是 16 颗 token，只要一个块里还剩一颗没淘汰，整块就释放不了——原话大概这个意思。你省的是 token，可显存是按块还的。[/S2]

[S3] 等等，淘汰了 90%，显存没降？合着省了个寂寞？[/S3]

[S2] 省是真省了，但没省到「块」这个粒度——块还在，显存就在。这就是这期的题眼：你省的不是 token，是物理块。[/S2]

[S1] 你这话我得记下来。那除了把这道题讲透，这期还讲啥？[/S1]

[S2] 讲这块显存的完整一生：从块池出发，排队、共享、被抢，住进一个叫持久批次的地方，最后被一张块表送进 GPU。面试题是入口，全景是地图。[/S2]

[S3] 行，我跟紧。先开赌局吧——显存到底被谁吃光的？笔记是个啥，我还一知半解。[/S3]

[S2] 开盅。先钉死一个东西：KV cache 是什么。简单来说——模型生成的时候，每颗 token 都在显存里留一笔笔记：前面算过的注意力、说过的话，都记下来，供后面的 token 参考。这笔笔记，就是 KV cache。[/S2]

[S1] 那这笔记能占多少显存？[/S1]

[S2] 占得吓人。模型权重是死的，放那儿不动；笔记是活的，随对话长度长——聊得越长，笔记越多。长上下文场景，笔记才是显存里的大头，显存优化全围着它转。[/S2]

[S3] 所以我赌赢了——显存是被笔记吃光的。那聊完了呢？笔记一直占着？[/S3]

[S2] 请求结束，块还回去——怎么还，后头讲。先把「笔记只增不减」钉在这儿，这是后面所有故事的地基。[/S2]

[S1] 那为啥不干脆按最长长度，给每个请求一次留够？多省心。[/S1]

[S2] 省心，但费显存。不切块的话，每个请求都得按最大长度预留一整段：你服务开着 128K 上下文，每个请求照 128K 留位——哪怕它只问一句「今天天气咋样」。大部分格子空着，还不让给别人。[/S2]

[S3] 128K 是啥概念？[/S3]

[S2] 十二万八千颗 token 的笔记位子。一个短请求占着长位子，并发一高，空着的地方比住着的还多。[/S2]

[S1] 而且连续大块，是不是还怕碎片？[/S1]

[S2] 怕。请求长短不一，用完释放，留下一地碎块——新请求可能凑不出一整段连续的。[/S2]

[S3] 停一下，这听着怎么这么耳熟。我能不能这么理解——这就是操作系统管内存的路子？程序以为自己独占整片内存，实际切成一页一页的。[/S3]

[S2] 对。我来说说这东西怎么来的——就是从操作系统偷的主意。虚拟内存切成固定大小的页，用到哪页才真占哪页。vLLM 把笔记当虚拟内存管，切成固定大小的块，这就是 PagedAttention 最核心的那一下。Paged，分页的。[/S2]

[S1] 这比喻得留着——没它，「为什么切块」根本答不上来。那一块多大？[/S1]

[S2] 16 颗 token。GPU 上一段连续的显存，就装 16 颗 token 的笔记。一个长请求的笔记，散落在好多块里，互相不连续。[/S2]

[S3] 不连续没关系吗？我们写程序的都知道，连续内存才快。[/S3]

[S2] 有关系，所以注意力那一步要按块的索引去拼。PagedAttention 这个算子存在的意义就在这：专门吃散落的块，把「在哪一块、块内第几个」翻译成显存里的真实位置。切块是管账，算子是算账。[/S2]

[S3] 我问个现实的——这东西面试真考吗？我听说有考到手写级别的。[/S3]

[S2] 有这说法。一个博主转述过他群里的经历，是这么讲的——{{voice:voice-009}}面试官让手写 PagedAttention 的实现逻辑，再讲讲它跟 KV cache 的区别和优化点，群里一位同学当场被问懵，只能尴尬地说没听过——大意就是这样。这事快一年前了，而且是转述，咱没法核实。但「手写 PagedAttention」能进面试题，本身就说明切块是理解 vLLM 的入场券。[/S2]

[S1] 让我来捋一下：笔记只增不减，按最长预留太费，所以切块——一块 16 颗，散落着存，算子按块去拼。对吧？[/S1]

[S2] 对，全对。[/S2]

[S1] 那这些块，谁管？[/S1]

[S2] 一个全局的块管家，叫块池。手里三样东西：所有块的名单、一个空闲块队列、一张前缀缓存的查表。谁要块找它，谁还块找它，发不出就说不行。[/S2]

[S3] 每块本身长什么样？总得有点档案吧。[/S3]

[S2] 有，一小块元数据，四样：编号、引用计数、哈希值，还有俩指针——指前一块、指后一块。[/S2]

[S3] 前后指针？块还排队？[/S3]

[S2] 排。空闲的块串成一条双向链表，头尾各站一个哨兵——就是不装真数据的假节点，省得边界判断写特例。队头是最久没被用过的，队尾是最近刚释放的。显存一紧张要腾地方，从队头开始赶人。[/S2]

[S3] 从队头赶——这就是 LRU 吧？最久没用先走。这个我熟，刷题刷过。[/S3]

[S2] 对，LRU 驱逐。你刷题刷的那个 LRU，在这儿管的是真金白银的显存。[/S2]

[S3] 那我问个工程问题：拿 Python 列表存不行吗？删中间一个元素，不得 O(n) 搬家？[/S3]

[S2] 你问到点子上了。展开来说——这条链表不新建 Python 对象，直接操作块自己身上那两个指针，中间删除是 O(1) 的。为什么在乎这个？前缀缓存命中时，得把命中的块从「驱逐候选」里摘出来——刚有用的块，不能转头就被赶走。摘得够快，这套才转得动。[/S2]

[S1] 那驱逐是平时就盯着赶，还是不够了才赶？[/S1]

[S2] 惰性的。取新块先拿空闲块，不够了，才从队头赶走最久没用的缓存块。平时没人动它，要紧时候才动手。[/S2]

[S1] 被赶走的缓存块，里面的内容就废了？[/S1]

[S2] 被赶走，意思是被划出缓存账本、变成「可分配」——不是销毁。它腾出来的地儿，下一拍可能就有新请求住进去，旧内容被覆盖。[/S2]

[S3] 等等，那查表里那把钥匙呢？块都可分配了，钥匙还留着，别的请求一查命中，不就指向一个不住人的块了？[/S3]

[S2] 必须同步删，账要两边对齐。你这句「不住人的块」，说得比我清楚。[/S2]

[S3] 那刚还回去的块排哪？队头还是队尾？[/S3]

[S2] 队尾。刚还回来的等于「刚刚才闲着」，轮不到先被赶。[/S2]

[S3] 我复述一遍：块池是总账房。空闲块串双向链表，队头 LRU 先赶、队尾最近释放；链表写在块自己身上，删除 O(1)；驱逐是惰性的，赶走等于可分配、不销毁，钥匙同步删。对吧？[/S3]

[S2] 一字不差。[/S2]

[S1] 好，块的「住与退」清楚了。可前缀缓存到现在只露了个头——俩请求凭什么能共享？我发的每句话都不一样啊。[/S1]

[S2] 系统提示词一样。就好比一个客服机器人，一千个客户，开头都是同一段系统提示词——前几百颗 token 的笔记，每个请求都重算一遍，纯浪费。前缀缓存就是：这段算过了，后来的请求直接挂上去。[/S2]

[S1] 咋知道「这段算过了」？总得有个对账的办法。[/S1]

[S2] 块级哈希。一块攒满 16 颗 token，把内容算个哈希值，再带上模型分组的编号，组成一把钥匙，写进查表。新请求来了，沿着哈希链找最长的一段前缀命中——命中越多，要重算的越少。[/S2]

[S3] 最长前缀命中——那命中了前五块，后三块呢？[/S3]

[S2] 前五块的笔记直接挂上，后三块新算。要是整段都命中，笔记这块一分钱不用花。[/S2]

[S3] 为啥非得攒满 16 颗才算哈希？不满的块不能算吗？[/S3]

[S2] 不满的块，内容还在长——这拍算的哈希，下拍就不一样了，缓存了也白缓。设计上只认满块，满块才是稳定状态。[/S2]

[S1] 等等，两块内容一模一样、哈希一样，干嘛不合并成一块？省一块是一块啊。[/S1]

[S2] 这里设计得很克制：不去重。同一把钥匙可以对应多块，各用各的。为什么？合并就得动块的编号——编号一动，块表就乱套了。块表这张对照表有个死规矩：只增不改。宁可多占一块显存，换编号纹丝不动。[/S2]

[S3] 我能不能这么理解：块表只增不改，就像账本只许往后记、不许涂改——涂改一次，所有对账的人都得重来？[/S3]

[S2] 对，就是这个理。拿一块显存换一致性，值。[/S2]

[S1] 那好几个请求共用一块，谁用完了能还吗？[/S1]

[S2] 引用计数。一块被几个请求共享，计数就是几。每个请求释放时减一，减到零，才真正还回空闲队列。计数还有一，这块就还在岗。[/S2]

[S3] 引用计数我熟啊——不就是智能指针那套吗：几个指针共用一块内存，归零才释放。那我可就要问了：计数要是忘减了，不就泄漏了？[/S3]

[S2] 你这一问，问出了本期最大的一颗雷。设计上归零才还，可真要出了 bug，计数永远不为零，块就永远不还。先记下，后面真爆给你看。[/S2]

[S3] 好，记账上。对了，前缀缓存我刷面经还真见过，问得挺细。[/S3]

[S2] 见过，而且这考点能追得很细。牛客上一位面过 AI Infra 实习的同学记过，前缀缓存是当场考点——{{voice:voice-024}}这类追问一般会细到：哈希粒度是什么？不满一个块的前缀能不能缓存？系统提示词固定但用户 query 不同时，命中率怎么估算？——大致就这个方向。前两问的答案，今天已经到手了：满块才算哈希，不满的进不了缓存表。[/S2]

[S1] 第三问呢？命中率咋估算？[/S1]

[S2] 按块估。命中是整块整块的——你的共享前缀折成满块有几块，就省几块的重算。所以先数你的共享前缀有几个满块、占总长度几分之几。思路就这个，准数得拿真实流量测。[/S2]

[S1] 满块才算数、不满白搭——两个答案都拿到了。那一个新请求要开工，块怎么发到它手上？[/S1]

[S2] 一条函数走完。代码里叫 allocate slots——a-l-l-o-c-a-t-e，下划线，s-l-o-t-s。发块的一条龙，三段式：先还债，再挂命中的，最后才开新的。[/S2]

[S3] 停一下，能不能展开说说——还债还啥？请求还没跑呢，欠谁的了？[/S3]

[S2] 有的模型只看最近 N 颗 token 的笔记——滑动窗口。窗口滑走了，窗外的旧块就没用了：把位子标空，块还给空闲队列。先还后借，顺序反了等于白开。[/S2]

[S3] 滑动窗口……就是注意力只看最近一段的那种模型？窗外的笔记直接扔？[/S3]

[S2] 对，扔给池子。顺带还查一遍预算：这拍能用的块不够，直接打回——这个「打回」是个引子，先记着。[/S2]

[S1] 第二段呢，挂命中的？[/S1]

[S2] 查前缀缓存，命中的块直接挂上，引用计数加一。不管是自己缓存里的，还是外边送过来的，一视同仁。[/S2]

[S3] 等等，外边送过来的？还有别人给它喂块？[/S3]

[S2] 有。预填充和生成拆开跑的部署里——就是常说的 PD 分离——预填充那边算好的块，通过一个连接器直接送过来挂上，引用计数照加，跟本地命中一模一样。[/S2]

[S1] 第三段，总该开新块了吧？[/S1]

[S2] 开新块，外加一个叫 lookahead 的预留——给这一拍马上要生成的 token，先把位子占好。[/S2]

[S3] 啊？还没算呢，先占位子？[/S3]

[S2] 对，免得算到一半没地方放——这就是预留的全部理由。[/S2]

[S1] 那三段走完还不够呢？[/S1]

[S2] 函数就回你俩字：不行。——注意，这不是报错，是「这拍我发不出来」的正常返回值。allocate slots<break 300ms>返回空，调度器收到这个信号接着干它的活，谁也不炸。[/S2]

[S3] 失败不当异常、当返回值——我们写业务代码谁敢这么写。但在这儿，调度器正好拿它当发令枪。[/S3]

[S1] 让我来捋一下这三段：先还窗外的旧块，再挂缓存命中的块，最后开新块加提前占位；不够就回个「不行」，不当异常。顺序是先还后借。[/S1]

[S2] 对。那「不行」之后呢？——这就到上期留的扣了，今天兑现。[/S2]

[S1] 上期的扣我记得：调度器把谁踢出这一拍，最终落地在显存能不能分到块。今天从显存这头看。[/S1]

[S2] 对。调度器里有个循环：allocate slots<break 300ms>返回空，就把正在跑的队尾请求拽下来一个——块归还池子，状态打回「被抢占」，重新插回等待队列的队头。腾出块，再试一遍。[/S2]

[S3] 上期讲过，踢队尾是因为它算得最少、重算成本最低。今天我追的是：它的块还回去了，那它已经吐出来的那些 token 呢？白算了？[/S3]

[S2] 字还在，块全还了。重新上桌，重新排块、接着往下算——多花的时间，就花在重新上桌这趟。这就是「拿时间换显存」里，那个时间的去向。[/S2]

[S1] 那抢完这一拍，还放新请求进来吗？[/S1]

[S2] 不放。显存刚挤爆过一次，再塞新的只会更糟。这一拍先消化，下一拍再开门。[/S2]

[S3] 那我再较个真：被抢的排回队头，下一拍又分不到块呢？再抢下一个？这不死循环吗——跟早高峰堵车一样，队头那辆动不了，后头一长串全陪着等。[/S3]

[S2] 怕的就是这个，所以有第二条队。有的请求不是被抢，是这拍 token 预算不够、又轮不到抢它——它得等。可要是把它放回普通队头，它一卡，后面全跟着等。这叫队头阻塞。[/S2]

[S1] 队头阻塞——上期银行柜台那例子：材料不齐的先请到旁边，后面的人继续办。[/S1]

[S2] 对。这个「旁边」，代码里是个独立的小队，叫 skipped waiting——s-k-i-p-p-e-d，下划线，w-a-i-t-i-n-g。预算不够的请求挪进去，不许堵在队头。一条大路一条侧道，谁也不挡谁。[/S2]

[S3] 我复述：分配失败就抢队尾——块还池子、状态打回、回队头补偿，本拍不再放新人；预算不够又没被抢的，挪进 skipped waiting<break 300ms>这条侧道，不许堵队头。全对我就过。[/S3]

[S2] 全对，过。[/S2]

[S1] 好，块有了，队也排了。那上 GPU 的时候——这一拍一批，批次是每拍现搭的？[/S1]

[S2] 不是。这期最反直觉的一步来了：持久批次。请求批不每拍重建——一个跨拍存活的二维容器，一行一个请求，每行一条全长度的整数缓冲。代码里这个容器叫 Input Batch。[/S2]

[S3] 等等，每行一条全长度的缓冲——这不跟开头骂的预分配一个毛病吗？[/S3]

[S2] 两码事。这缓冲是 CPU 侧的记账板，不是 GPU 上那块笔记——笔记还是分页的。板子开得再大，行是复用的：请求走了，行还在，下个请求住进来。[/S2]

[S3] 我能不能这么理解——酒店客房：房间不重建，客人来了入住、走了退房、收拾完再住新的？[/S3]

[S2] 你这比喻能承重。为什么每拍重建是浪费？等于每天拆楼盖楼：重新分配整片内存、重新复制数据，GPU 干等 CPU 搬。持久批次赌的是「大部分请求活着跨拍」——这赌注几乎每拍都赢。[/S2]

[S1] 那旧请求每拍状态都变，账怎么更新？[/S1]

[S2] 差量更新。调度器每拍发一张变更单：新拿了哪些块、算到第几颗、输出了几颗。worker 拿单子在原来的行上就地改，不整行重写。[/S2]

[S3] worker 咋知道这请求原来长啥样？总不能每拍让调度器重发一遍吧？[/S3]

[S2] 不用。worker 那边每个请求存一张快照：prompt 是啥、算到第几颗、输出过几颗。调度器只发变更单，worker 拿快照对着改。[/S2]

[S3] 又跟 git 一样——第一次全量 clone，之后只推变更。上期那张单子就是这思路。[/S3]

[S1] 对，同一个思路——上期他这么比喻的时候，我就记过一回。那每拍开头，先干啥？[/S1]

[S2] 先对账。代码里这一步叫 update states——名字前面带个下划线，Python 的规矩，下划线开头就是内部方法，外人别直接调。它干的事：调度器说这拍谁在跑、谁完成了，worker 拿这份账跟自己的快照对齐，然后才准备输入。账不对齐，后面的活全白干。[/S2]

[S3] 那退房留下的洞呢？空行怎么办？[/S3]

[S2] 有个记账本，记着这拍谁走了、谁来了、谁挪了位。新请求来了，先填空出来的洞；洞攒多了，一次性压实——把还在的往前挪，空行统一赶去尾巴。[/S2]

[S1] 要是每拍都压实呢？[/S1]

[S2] 搬来搬去，白省了。跟酒店保洁一个节奏：没必要天天大扫除，攒一块收拾一次。[/S2]

[S3] 我复述：批次是酒店，行是客房，不拆楼；变更单就地改，快照对账；走了留洞，新客填洞，洞多了一次压实。对吧？[/S3]

[S2] 对，全对。[/S2]

[S1] 好，请求住进批次了。最后一站：GPU 怎么知道每颗 token 的笔记在哪？[/S1]

[S2] 靠块表——把逻辑块号翻译成物理地址的那张对照表。它代码里叫 block table——b-l-o-c-k，下划线，t-a-b-l-e。这张表是双镜像的：CPU 一份管记账，GPU 一份管干活。[/S2]

[S3] 双镜像？两边各一份，同步不麻烦吗？[/S3]

[S2] 改了先改 CPU 这份，攒够了，一次性批量拷给 GPU——这个动作代码里叫 commit。为什么？GPU 每拍读、CPU 每拍改，各拿各的，中间批量同步，不一趟一趟过桥。[/S2]

[S1] 那最后一公里的映射，谁算？[/S1]

[S2] 一个 Triton 写的内核。Triton 就是那种拿 Python 语法写 GPU 代码的框架。它把每颗 token 的位置翻译成物理槽位：块表里查第几块，块号乘 16 得起始位置，再加块内第几个——物理槽位就出来了。[/S2]

[S3] 等等，你刚才那句我没跟上——块号乘 16，加块内偏移，就完了？[/S3]

[S2] 就完了。一条公式：逻辑块号乘块大小，加块内偏移，一行一行批量算。尾部不够满的，拿占位符补齐——一个特殊标记，不指向任何真块。[/S2]

[S1] 为啥非得补齐？[/S1]

[S2] 因为这内核要在固定的网格上跑，网格不能缩。这牵扯到 CUDA graph——一段录好的 GPU 命令，原样重播，录的时候网格多大，放的时候就多大。为啥要录这玩意，是下期的账。先记着「固定网格」四个字。[/S2]

[S3] 行，记下了。我复述最后这站：块表双镜像，CPU 记账、GPU 干活，批量 commit 同步；Triton 内核按公式算槽位；尾部拿占位符补齐，适配固定网格。过？[/S3]

[S2] 过。[/S2]

[S1] 争议？一个数还能打出争议来？[/S1]

[S2] 有，还不小。先上反面教材。前不久牛客一篇面经，转述了面试官的递进追问，是这么问的——{{voice:voice-008}}块大小设为 1，碎片是没了，但块表会暴涨。设得太大，短序列场景下严重浪费。默认的 16，一块只用了 15 颗 token，剩下一个空位就浪费了——原话大概这个意思。这就是内部碎片，开头那道面试题的病根。[/S2]

[S3] 等等，块的事还没完——内核自己就干净吗？我听说分组查询注意力下，那内核有重复加载的毛病？[/S3]
