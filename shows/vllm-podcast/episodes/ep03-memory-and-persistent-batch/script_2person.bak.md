# 你省的不是 token，是物理块：一块显存的一生

[S1] 我前两天看到一道面试题，差点被绕进去。说你给 vLLM 加了 KV cache 压缩，淘汰了 90% 的不重要 token，重启服务——显存几乎没降，同样的长度，照样把显存爆了。气不气人？[/S1]

[S2] 这题我第一次看到也愣了一秒。答案不在淘汰了多少 token，在淘汰的单位。腾讯云开发者社区有篇解析专门拆这道题，他是这么说的——{{voice:voice-029}}答案不在于淘汰了多少 token，而在于释放了多少个完整的物理块。PagedAttention 的块大小是 16 token，只要一个块里还剩一个 token 没淘汰，整块就释放不了——原话大概这个意思。你省的是 token，可显存是按块还的。[/S2]

[S1] 合着我辛辛苦苦淘汰 90%，省了个寂寞？[/S1]

[S2] 也不是。省了 90% 的 token，没省到「块」这个粒度——块还在，显存就在。这句话就是这期的题眼：你省的不是 token，是物理块。[/S2]

[S1] 那这期，除了把这道题讲透，还讲啥？[/S1]

[S2] 讲这块显存的完整一生：从块池出发，经过缓存、抢占，住进持久批次，最后被块表送进 GPU。面试题是入口，全景是地图。[/S2]

[S1] 那这期咱就盯一块显存的一生：它从哪来，怎么排队，怎么共享，怎么被抢，怎么住进 GPU，最后怎么死。[/S1]

[S2] 行，而且这是上期的欠账。上期结尾说，调度器把谁踢出这一拍，最终落地在一件事上——显存能不能分到足够的 KV cache 块。今天就从这块显存讲起。[/S2]

[S1] 行。先问最笨的：KV cache 到底是啥？上期就提了一嘴。[/S1]

[S2] 模型生成的时候，每颗 token 都在显存里留一笔笔记——前面算过的注意力、说过的话，都记下来，供后面的 token 参考。这笔笔记就是 KV cache。聊得越长，笔记越多，显存吃得越狠。[/S2]

[S1] 那这笔记能占到多少显存？每颗 token 都记一份，那不得越记越多？[/S1]

[S2] 占得吓人。模型权重是死的，放那儿不动；KV 是活的，随对话长度长——长上下文场景，KV 才是显存里的大头，显存优化全围着它转。而且它分两个阶段长：第一颗 token 出来之前，整段 prompt 的笔记一口气算完，叫 prefill；之后每出一颗新 token 追加一笔，叫 decode。KV 只增不减，聊得越长，显存越吃。[/S2]

[S1] 那聊完了呢？笔记一直占着？[/S1]

[S2] 请求结束，块还回去——这就是后头要讲的引用计数和空闲队列。先把「只增不减」钉在这儿，后面所有故事的地基。[/S2]

[S1] 那为啥不干脆按最长长度，每个请求一次留够？多省心。[/S1]

[S2] 省心，但费显存。一个请求可能就聊三句话，你按最长上下文给它留位——大部分格子空着，还不让给别人。而且留多少全凭猜，猜错不是浪费就是爆显存。[/S2]

[S1] 这浪费能浪费到什么程度？[/S1]

[S2] 你服务开着 128K 上下文，每个请求就照 128K 的位子预留——哪怕它只问一句「今天天气咋样」。一个短请求占着长位子，并发一高，空着的地儿比住着的还多。[/S2]

[S1] 而且连续大块，是不是还怕碎片？[/S1]

[S2] 怕。请求长短不一，用完释放，留下一地碎块——新请求可能凑不出一整段连续内存。切块之后，碎一点没关系，块就是最小单位，哪块空着都能装。[/S2]

[S1] 等等，这听着怎么这么耳熟……操作系统管内存是不是就这么干？[/S1]

[S2] 就是从那儿偷的主意。虚拟内存：每个程序以为独占整片地址空间，实际切成固定大小的页，用到哪页才真占哪页。vLLM 把 KV cache 当虚拟内存，切成固定大小的块——这就是 PagedAttention 最核心的那一下。[/S2]

[S1] 这比喻我得留——没它，「为什么切块」你根本答不上来。那页多大？[/S1]

[S2] 一块 16 个 token。GPU 上一段连续的显存，就装 16 颗 token 的笔记。一个长请求的 KV 散落在好多块里，不连续。[/S2]

[S1] 不连续没关系吗？以前不都说连续内存才快？[/S1]

[S2] 有关系，所以注意力那一步要按块的索引去拼——PagedAttention 这名字，Paged 就来自这儿。换来的是显存利用率的大幅提升，值。[/S2]

[S1] 那 GPU 上的注意力算子，认不认这种散落的块？[/S1]

[S2] 这正是 PagedAttention 算子存在的意义：它专门吃散落的块，按块寻址去算注意力——把「在哪一块、块内第几个」翻译成显存里的真实位置。切块是管账，这个算子是算账。[/S2]

[S1] 我听说有人面试真被要求现场手写 PagedAttention 的实现逻辑？[/S1]

[S2] 有个博主转述过群里的经历，他是这么说的——{{voice:voice-009}}面试官让手写 PagedAttention 的实现逻辑，再讲讲它跟 KV cache 的区别和优化点，群里一位同学当场被问懵，只能尴尬地说没听过——原话大概这样。这事咱没法核实，但「手写 PagedAttention」能出现在面试里，本身就说明切块是理解 vLLM 的入场券。[/S2]

[S1] 行，入场券收下。那这些块，谁管？[/S1]

[S2] 一个全局的块管家，叫块池。手里三样东西：所有块的名单、一个空闲块队列、一张前缀缓存的查表。每块本身是个小块元数据：编号、引用计数、哈希、还有前后指针。[/S2]

[S1] 块池这名字，听着像管钱的。[/S1]

[S2] 就是管钱的：谁要块找它，谁还块找它，一手记账一手发牌。发不出就说不行——逼着调度器去抢人，这是后话。[/S2]

[S1] 这些块是现用现切，还是提前备好的？[/S1]

[S2] 不是现用现切的。跟 GPU 要一大片显存，提前切成 16 token 的小块码在池子里——不是用一块问 GPU 要一块。池子属于所有人，谁用都行。[/S2]

[S1] 前后指针？块还排队？[/S1]

[S2] 排。空闲块串成一条双向链表，两个哨兵占头占尾。队头是最久没被用过的，队尾是最近刚释放的。显存一紧张要腾地方，从头开始赶人——最久没用的先走，最不亏。[/S2]

[S1] 那用 Python 列表存不行吗？删中间一个不得 O(n) 搬家？[/S1]

[S2] 你问到点子上了。链表直接写在块自己的指针上，不新建 Python 对象，中间删除是 O(1) 的。为什么在乎这个？前缀缓存命中时，得把命中块从「驱逐候选」里摘出来——刚有用的块不能马上被赶走。摘得够快，这套才转得动。[/S2]

[S1] 那驱逐是盯着赶，还是不够了才赶？[/S1]

[S2] 惰性的。取新块先拿空闲块，不够了，才从队头赶走最久没用的缓存块。平时没人动它，要紧时候才动手。[/S2]

[S1] 那被赶走的缓存块，里面的内容就废了？[/S1]

[S2] 被赶走，就是被划出缓存账本了——它腾出来的地儿，下一拍可能就有新请求住进去，旧内容被覆盖。驱逐的意思不是销毁，是「可分配」。[/S2]

[S1] 「可分配」，不是销毁——这区分挺关键。那驱逐它之前，查表里那把钥匙，也得删掉吧？[/S1]

[S2] 必须删，账要两边对齐。查表里还留着它，别的请求来命中，指向的却是已经可分配的块，那就出大事了。[/S2]

[S1] 行，账记明白了。说到前缀缓存——俩请求凭什么能共享？我发的每句话都不一样啊。[/S1]

[S2] 系统提示词一样。一个客服机器人，一千个客户开头都是同一段系统提示词——前几百颗 token 的笔记，每个请求都重算一遍，纯浪费。前缀缓存就是：这段算过了，后来的请求直接挂上去。[/S2]

[S1] 咋知道「这段算过了」？总得有个对账的办法。[/S1]

[S2] 块级哈希。一块攒满 16 颗 token，把内容算个哈希，再带上模型分组的编号，组成一把钥匙，写进查表。新请求来了，沿着哈希链找最长的一段前缀命中——命中的越多，要重算的越少。[/S2]

[S1] 最长前缀命中——那命中了前五块，后三块呢？[/S1]

[S2] 前五块的笔记直接挂上，后三块新算。命中越靠后省得越多——要是整段都命中，KV 这块一分钱都不用花。[/S2]

[S1] 为啥非得攒满 16 颗才算哈希？不满的块不能算吗？[/S1]

[S2] 不满的块内容还在长——这拍算的哈希，下拍就不一样了，缓存了也白缓。设计上只认满块，因为满块才是稳定状态。[/S2]

[S1] 等等，两块内容一模一样，哈希一样，干嘛不合并成一块？省一块是一块啊。[/S1]

[S2] 这里设计得很克制：不去重。同一把钥匙可以对应多块，各用各的。为什么？合并得动块的编号，编号一动，块表就乱套——块表是只增不改的。拿一块显存换一致性，值。[/S2]

[S1] 行，宁可浪费一块也不动编号——图个稳。那查表本身不花钱吗？[/S1]

[S2] 哈希查表，一块一把钥匙，O(1) 级别，便宜到可以忽略。拿 CPU 上一点点查找，换 GPU 上整块整块的重算——这笔账谁都会算。[/S2]

[S1] 那好几个请求共用一块，谁用完了能还吗？[/S1]

[S2] 引用计数。一块被几个请求共享，计数就是几；每个请求释放时减一，减到零，才真正还回空闲队列。计数还有一，这块就还在岗。[/S2]

[S1] 那这计数要是忘减了，不就泄漏了？[/S1]

[S2] 你猜对了——设计上归零才还，可要是出了 bug，计数永远不为零，块就永远不还。这是后头要爆的雷，先记下。[/S2]

[S1] 计数减到零还回去，那还回的块排哪？队头还是队尾？[/S1]

[S2] 队尾。队列的规矩：最久没用过的在队头，最先被赶；最近释放的排队尾。刚还回来的块等于「刚刚才闲着」，轮不到先被赶。[/S2]

[S1] 这前缀缓存，我刷面经好像见过？[/S1]

[S2] 见过，还问得挺细。牛客上一位面过 AI Infra 实习的同学写过面经，说面试官是这么问的——{{voice:voice-024}}前缀缓存的哈希粒度是什么？不满一个块的前缀能不能缓存？系统提示词固定但用户 query 不同时，命中率怎么估算？——原话大概这个意思。前两个的答案，咱今天都讲到了：满块才算哈希，不满的进不了缓存表。[/S2]

[S1] 满块才算数、不满白搭——这两个答案今天都拿到了。行，那一个新请求要开工，块怎么发到它手上？[/S1]

[S2] 一条函数，三段式分配，一次走完。第一阶段先还债，第二阶段挂命中的，第三阶段才开新的。顺序不是随便排的。先还后借，顺序要是反了，等于白开。[/S2]

[S1] 一段段拆。还债还啥？[/S1]

[S2] 有的模型只看最近 N 颗 token 的笔记，窗口外头的旧块就没用了——把位子标空，块归还空闲队列。顺带查一遍预算：这拍能用的块不够，直接打回，触发后面要讲的抢占。[/S2]

[S1] 行，还债明白了。那第二段，挂命中的？[/S1]

[S2] 查前缀缓存，命中的块直接挂上，引用计数加一——不管是自己缓存的，还是外部预填充那边送过来的，都算。[/S2]

[S1] 等等，外部预填充？还有别人给它喂块？[/S1]

[S2] 对，预填充和生成拆开跑的部署里，预填充那边算好的块，通过连接器直接送过来挂上——引用计数照加，跟本地命中一视同仁。[/S2]

[S1] 第三段呢？总该轮到开新块了吧？[/S1]

[S2] 开新块，还得给马上要生成的 token 提前占位，这个预留叫 lookahead。[/S2]

[S1] 提前占位？GPU 还没算呢，先占好茅坑？[/S1]

[S2] 对。这一拍窗口里要生成几颗，先占着，免得算到一半没地方放。三段走完还不够，函数就一句话：不行。<break 300ms>[/S2]

[S1] 那「不行」俩字，是报错吗？[/S1]

[S2] 不是错误，是「这拍我发不出来」的正常返回值。调度器收到这个信号，才启动抢占循环——你看，分配函数把失败当返回值，调度器接着干活，谁也不炸。[/S2]

[S1] 失败不当异常当返回值——业务代码谁敢这么写？但在这儿，调度器正好拿它当发令枪。「不行」之后呢？请求就干等着？[/S1]

[S2] 上期留的扣，今天兑现：抢人和排队。调度器里有个循环——分配失败，就把正在跑的请求拽下来一个：块归还、状态打回待命、重新插回等待队列的队头，循环再来一遍，腾出块再试。[/S2]

[S1] 插回队头？那不是插队吗？被抢的反而先跑？[/S1]

[S2] 是故意的。它被抢不是因为它错，是显存不够——块一够，它马上就能接着跑，从队头进去，下一拍就轮它。这叫抢占，拿时间换显存。[/S2]

[S1] 被抢下来，它已经吐出来的 token 咋办？白算了？[/S1]

[S2] 字还在，块全还了。重新上桌，重新排块、接着往下算——多花的时间就花在重新上桌这趟。这就是「拿时间换显存」里那个时间的去向。[/S2]

[S1] 请求状态来回切，那判断「完没完事」还得查表？[/S1]

[S2] 不用。请求状态就是个整数，完成判定靠比大小——一个整数比较完事，热路径上连查表都省了。[/S2]

[S1] 那抢完这一拍，还放新请求进来吗？[/S1]

[S2] 不放。这一拍抢过人，就先把坑填平再说——本拍不再放新请求。[/S2]

[S1] 那要是被抢的排回队头，又分不到块呢？再抢下一个？这不死循环吗？——跟早高峰堵车一个样，队头那辆动不了，后头一长串全陪着等。[/S1]

[S2] 对，怕的就是这个，所以才有第二条队。有的请求不是被抢，是这拍 token 预算不够，它得等。可要是把它放回普通队头，它一卡，后面所有请求全跟着等——这叫队头阻塞。[/S2]

[S1] 队头阻塞……前面一个堵着的，后面一长串陪着。这词我得记着。[/S1]

[S2] 对。所以有个独立的小队，预算不够的请求挪进去，不许堵在队头。普通队照常往前跑，它等得起。一条大路，一条侧道，谁也不挡谁。[/S2]

[S1] 那这队是先进先出吗？还是能插队？[/S1]

[S2] 默认先进先出，抢占的请求是唯一的插队特例——插回队头，块一够，下一拍就先轮到它。[/S2]

[S1] 行，块有了，请求也排上队了。那要上 GPU——这一拍一批，批次是现搭的？[/S1]

[S2] 不是。这期最反直觉的一步来了：持久批次，请求批不每拍重建。一个跨拍存活的二维容器，一行一个请求，每行一条全长度的缓冲。[/S2]

[S1] 那这容器开多大？会装不下吗？[/S1]

[S2] 定长，开多大配置说了算，启动时就定死了。所以持久批次的上限是提前算好的，不是临时长出来的——装不下，回到抢占那套逻辑。[/S2]

[S1] 一行一条全长度的缓冲——这不跟预分配一个毛病？[/S1]

[S2] 两码事。这缓冲是 CPU 侧的记账板，不是 GPU 上那块 KV——KV 还是分页的。板子开得再大，行是复用的：请求走了，行还在，下个请求住进来。[/S2]

[S1] 这不就是酒店客房吗？房间不重建，客人来了入住、走了退房、收拾完再住新的。[/S1]

[S2] 你这比喻能承重——为什么每拍重建是浪费？等于每天拆楼盖楼：重新分配整片内存、重新复制数据，GPU 干等 CPU 搬。持久批次赌的是「大部分请求活着跨拍」，这赌注几乎每拍都赢，省下的就是赚到的。[/S2]

[S1] 那旧请求每拍状态都变，怎么更新？[/S1]

[S2] 差量更新。调度器每拍发一张「变更单」：新拿了哪些块、已经算到第几颗、输出了几颗。worker 拿单子在原来的行上就地改，不整行重写。[/S2]

[S1] 那 worker 咋知道这请求原来长啥样？[/S1]

[S2] worker 端每个请求存一张快照：prompt 是啥、算到第几颗、输出过几颗。调度器发变更单，worker 拿快照对着改——调度器不用把整个请求重发一遍。[/S2]

[S1] 那每拍开头，先干点啥？[/S1]

[S2] 先对账：调度器说这拍谁在跑、谁完成了，worker 拿这份账跟自己的快照对齐，然后才准备输入。账不对齐，后面的活全白干。[/S2]

[S1] 那退房留下的洞呢？空行怎么办？[/S1]

[S2] 有个记账本记着这拍谁走了、谁来了、谁挪了位。新请求来了先填空出来的洞；洞攒多了，一次性压实——把还在的往前挪，空行赶去尾巴。要是每拍都压实，搬来搬去白省了。[/S2]

[S1] 合着洞留着填，填满了再打扫。[/S1]

[S2] 跟酒店保洁一个节奏。好，最后一站：请求住进批次了，GPU 怎么知道每颗 token 的笔记在哪儿？[/S2]

[S1] 这板子是两维的，GPU 算子吃的可是一条一维序列——怎么喂？[/S1]

[S2] 拍扁。把每个请求、每个位置的 token 收集成一条一维序列，再配上一张「谁在哪」的坐标单，一起交给算子。持久批次管「住」，这一步管「出门」。[/S2]

[S1] 不是有块表吗？逻辑块号对物理地址。[/S1]

[S2] 对，但这块表是双镜像的：CPU 一份，GPU 一份。每拍改了先改 CPU 这份，攒够了，一次性批量拷给 GPU。为什么？GPU 每拍读、CPU 每拍改，各拿一份，中间批量同步，不一趟一趟过桥。[/S2]

[S1] 那最后一公里的映射，谁算？[/S1]

[S2] 一个 Triton 写的内核。Triton 就是那种用 Python 语法写 GPU 代码的框架。它把每颗 token 的坐标翻译成物理槽位：块表里查第几块，块号乘 16 得起始位置，加块内第几个，物理槽位就出来了。[/S2]

[S1] 等一下你刚才那句我没跟上——块号乘 16 加偏移，就完了？[/S1]

[S2] 就完了，一条公式：逻辑块号乘块大小，加上块内偏移。一行一行批量算，尾部不够满的拿占位符补齐——因为这内核要在固定的网格上跑，网格不能缩。[/S2]

[S1] 占位符是啥？往哪儿指？[/S1]

[S2] 一个特殊标记，不指向任何真块，专门填空位。内核的网格形状是固定的，行没填满也得有东西站着，就填它。[/S2]

[S1] 固定的网格……这词怎么听着像下期的钩子？[/S1]

[S2] 被你抓到了。这块表映射，只是 vLLM 里几十个自定义算子中的一个。而这一个算子背后，是 GPU 上一整套执行管线。<break 400ms>[/S2]

[S1] 好，机制讲完了。但我憋了一路的问题：16 这个数，谁定的？为啥不是 8、不是 32？[/S1]

[S2] 先交代出处：它是 PagedAttention 论文里的缺省值。可论文测的是基准负载，生产环境五花八门——所以这期争议，就是围绕这个 16 打的。[/S2]

[S1] 争议？一个数还能打出争议来？[/S1]

[S2] 有，还不小。先上反面教材。牛客上一篇面经，转述了面试官的递进追问——{{voice:voice-008}}块大小设为 1，碎片是没了，但块表会暴涨；设得太大，短序列场景下严重浪费。默认的 16，一块只用了 15 颗 token，剩下一个空位，整块也释放不了——大意就是这样。这就是内部碎片，开头那道面试题的病根。[/S2]

[S1] 那面试官这么一路追问，到底想听啥？[/S1]

[S2] 想听你有没有 trade-off 的体感——16 不是圣旨，是某组约束下的折中。你能说出「我这是短序列场景，块该往小调」，比背出 16 强一百倍。[/S2]

[S1] 等等，块的事还没完，内核自己也未必干净？我听说 GQA 下那内核有重复加载的问题？[/S1]

[S2] 这事儿有。GitHub 上有人拿性能剖析工具抓过，大意是——{{voice:voice-006}}分组查询注意力下，8 个线程块重复加载同一份 KV 头数据，L1、L2 之间的流量跑了 800 多 MB，实际 KV 数据只有 64 MB——他贴的就是这组数。他给的新内核，性能提升约三成。[/S2]

[S1] 800 对 64，这数据挺吓人。后来修了没？[/S1]

[S2] 他给了新内核实现，提升约三成。但那 issue 是去年三月的，kernel 迭代过几轮，现在什么样，我们俩没盯着，不敢替人打包票。[/S2]

[S1] 一面夸 PagedAttention 是最漂亮的创新，一面内核自己这么费流量。还有更狠的吗？[/S1]

[S2] 有，这个更狠。今年六月，Mistral AI 在生产环境发现 vLLM 的 CPU 内存泄漏，他们查出的根因是——{{voice:voice-022}}UCX 钩子和前缀缓存里的请求引用循环，最后 GPU worker 进程直接内存溢出被杀——原话大概这么说的。引用计数这套设计漂亮，真出循环引用，一样漏。[/S2]

[S1] 那这泄漏最后咋收场的？[/S1]

[S2] 社区按根因修了——引用循环拆掉，泄漏路径堵上。但「生产环境被内存溢出杀掉」这种体验说明：再成熟的框架，内存也得自己盯监控。[/S2]

[S1] 行，坏话说完了。那说好的「分页是共享的前提」呢？给个数。[/S1]

[S2] 给你个数。llm-d 团队在 16 块 H100 上跑 Qwen-32B，150 个客户，每客户 6000 token 共享系统提示词。他们贴出的数字是——{{voice:voice-007}}精确前缀缓存感知调度，相比随机调度，P90 首 token 延迟从 93 秒降到 0.542 秒，差了 170 倍。KV cache 命中率，是生产级 AI agent 唯一最重要的指标——原话如此。[/S2]

[S1] 170 倍……这数字是不是有点太漂亮了？[/S1]

[S2] 单机、专门场景、可重复前缀——最有利条件。真实负载要打折扣，但量级不会骗人。[/S2]

[S1] 93 秒降到半秒……这已经不是快慢，是能不能用的问题。[/S1]

[S2] 而且不止性能。FutureAGI 那家第三方评估团队拿 RAG 应用做过评测，他们看一个叫 Groundedness 的分，就是答案靠不靠谱的分。他们的结论是——{{voice:voice-030}}KV cache 命中率低于 0.55 时，Groundedness 评分从 0.88 跌到 0.69。系统提示词里的工具调用参数开始丢失，检索结果开始引用错误文档——原话大概这个意思。<break 300ms>[/S2]

[S2] 这话得品一品：命中率低不只是慢，是模型开始犯傻。[/S2]

[S1] 那集群呢？单机好用到飞起，上了集群呢？[/S1]

[S2] 集群是另一回事。同一个团队也承认——{{voice:voice-026}}自动前缀缓存在单实例里高效运行，首 token 延迟从 4.3 秒降到 0.6 秒；但一旦挂上传统负载均衡器，相同前缀被分散到不同机器，缓存反复被驱逐和重算——分布式前缀缓存，还不是 vLLM 开箱即用的能力——这是他们的原话。[/S2]

[S1] 所以这账是：单机 170 倍，集群开箱拿不到。[/S1]

[S2] 对，要拿得自己搭全局索引。vLLM 单机把这活儿干得漂亮，分布式这块还欠着。[/S2]

[S1] 行，两边账都摆平了。那 16 这个数本身——到底怎么定出来的？别告诉我拍脑袋。[/S1]

[S2] 这个我们俩真没搞清楚。书里给的是「默认 16」这个实现事实，没给推导；论文里是实验选的，但换个硬件、换个负载还成不成立，我们说不准。评论区有懂的，说说你的块大小怎么选的。[/S2]

[S1] 难得有你答不上来的。那给个判据，别和稀泥。[/S1]

[S2] 判据不是「你有没有碎片」，是「你的前缀共享率，盖不盖得住碎片开销」。每个人各聊各的——唯一 prompt 场景，分页只有碎片没收益，块越小越好。多租户 Agent 场景，80% 共享系统提示词——170 倍的差距，不是块大小能换回来的。选块大小，本质是判断你的负载属于哪种。[/S2]

[S1] 所以开头那道面试题，标准答案其实就是这个判据？[/S1]

[S2] 对。淘汰 90% 的 token，显存为啥没降——省的不是 token，是物理块；块为啥没释放——一块里还剩一个 token。这道题考的不是压缩算法，是分页的物理模型。[/S2]

[S1] 行，账算平了。收个尾：这期咱管了一块显存的一生。[/S1]

[S2] 从切块、排队、共享、抢占，到住进持久批次，再到块表把它映射成物理槽位——最后这一步，是那个 Triton 内核干的。而它，只是几十个自定义算子里的一个。[/S2]

[S1] 几十个里的一个……那 GPU 上那一整套，到底怎么转起来的？[/S1]

[S2] 下一期，把镜头推到 GPU 上：一个你写在 Python 里的模型层，怎么变成一段在 CUDA graph 里反复重播的融合内核——就是一段录好的 GPU 命令，原样放——中间连 Python 解释器都不经过。<break 400ms>[/S2]
